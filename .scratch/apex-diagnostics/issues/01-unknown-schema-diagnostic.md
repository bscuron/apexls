## Question

Wire `Resolution::UnknownSchema` (already computed during binding via `schema_index`/`resolve.rs`, whenever a SOQL/SOSL query references an object or field with no matching local or standard schema entry -- e.g. `FROM Unknown_Object__c`, a bad `WHERE` field) into a new `unknown_schema_diagnostics` source in `crates/apexls-server/src/capabilities.rs`, following the exact same shape as `unresolved_reference_diagnostics` (range from the binder's own recorded span, `ERROR` severity, `source: "apexls"`). Add it to the merged `publish_diagnostics` call in `crates/apexls-server/src/lib.rs` alongside the three existing sources. This is purely a "surface already-computed data" ticket -- no new binder analysis is needed, matching BACKLOG.md's own note that this is the cheapest candidate.

Definition of done: a protocol-level test (mirroring `crates/apexls-server/tests/*diagnostics*.rs`'s existing pattern) confirming a bad SOQL object/field produces the diagnostic and a `didChange` fix clears it; confirm no regression against the real NPSP corpus's existing `resolution_regression_baseline.rs` counts.

## Answer

Implemented as `apexls_server::capabilities::unknown_schema_diagnostics` (`crates/apexls-server/src/capabilities.rs`), wired into the merged `publish_diagnostics` in `crates/apexls-server/src/lib.rs` alongside the three existing sources. One `ERROR`-severity diagnostic per `Resolution::UnknownSchema` recorded for the file.

**Scope decision, not in the original ticket text -- discovered while implementing:** `Resolution::UnknownSchema` is produced by five call sites, not just SOQL/SOSL ones. Two of the other three are *not* errors at all: `bind_field_expr`'s `<Object>.fields`/`<Object>.fields.<Field>` describe-token hop (`fields` is real, compiler-magic Apex syntax -- e.g. `Schema.SObjectField f = Account.fields.Name;` -- not a genuine field access; surfacing it here would have been a guaranteed false positive on totally valid, common Apex) and `bind_sobject_field_init`'s SObject-constructor field-init check (a real, separate gap, but out of this ticket's literal "SOQL/SOSL" scope -- left as a natural follow-on, not folded in silently). Fixed by scoping the diagnostic to `ptr.kind() == SyntaxKind::SoqlFieldName` specifically -- confirmed via `apex-syntax`'s own AST that every genuine SOQL/SOSL object-or-field reference (`SoqlFromList::entries`, `SoslFieldSpec::object`, every select/where/order-by/group-by field, a `TYPEOF ... WHEN` type name) is exactly that one node kind, and neither excluded producer ever is. A trigger's `ON <object>` (also routed through the same underlying `schema_index::resolve_object`) was left out too, for the same reason: it's a `TriggerUnit`-kind ptr, not `SoqlFieldName`, so staying narrowly scoped to the ticket's literal title was the simpler, more defensible call for a `task` ticket with no discussion round.

**A real binder bug this surfaced, fixed as part of the same change (matching this project's established precedent -- `unresolved_reference_diagnostics` similarly "found and fixed six real, general binder/stdlib gaps" per BACKLOG.md's own history):** wiring this diagnostic up immediately produced false positives on real NPSP code querying `Level__c.Name`-shaped fields on **local custom objects**. Root cause: a custom object's implicit `Name` field is declared once on the *object* itself, via `.object-meta.xml`'s own `<nameField>` block (confirmed against the real `Level__c.object-meta.xml` fixture in the NPSP corpus -- `<nameField><type>Text</type></nameField>`, no corresponding `fields/Name.field-meta.xml` anywhere), never as a regular `fields/*.field-meta.xml` file the way every other custom field is. `apex_metadata::discover_sobjects` never read `.object-meta.xml`'s *content* at all (only its path, for `is_custom`/`object_path`), so every locally-declared custom object's `Name` field was silently absent from `SchemaIndex`, and `schema_index::universal_field`'s fixed 8-field fallback (`Id`/`OwnerId`/...) correctly doesn't include `Name` either (it isn't truly universal across *every* object the way those are). Fixed generally in the shared metadata layer, not patched per-diagnostic or special-cased for NPSP: added `apex_metadata::xml::parse_object_meta_name_field` (extracts `<nameField><type>` into a synthetic `FieldSchema { api_name: "Name", .. }`), wired into `discover_sobjects`'s existing object-meta-file loop. Unit-tested in `crates/apex-metadata/src/xml.rs`.

Tests: `crates/apexls-server/tests/unknown_schema_diagnostics.rs` (bad `FROM` object -- including its expected cascading diagnostic for the `SELECT` field checked against that same bad object, matching `unresolved_reference_diagnostics.rs`'s own `QUALIFIED_TYPE_SRC` precedent for "one root-cause typo, flagged twice, redundant but not incorrect"; bad field on a known object; the `.fields` describe-token shorthand does *not* misfire; `didChange` clears the diagnostic once fixed). Full `apexls-server`/`apex-binder`/`apex-metadata` suites pass, including `resolution_regression_baseline.rs` (no regression) and the real-NPSP-corpus zero-`ERROR` smoke tests (`a_real_npsp_lvl_level_edit_test_file_has_no_error_severity_diagnostics` and siblings), which is what caught the `Name`-field bug above in the first place.
