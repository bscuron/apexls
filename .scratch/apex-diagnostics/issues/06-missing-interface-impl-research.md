Type: research
Status: resolved

## Question

Survey exactly what `crates/apex-binder/src/inherit.rs`'s existing `extends`/`implements` chain resolution already gives you toward a "does this concrete class implement everything its supertype chain requires" check, versus what's genuinely missing. Specifically establish:

- Does `inherit.rs` already expose, per project-local class, a fully-resolved flat list of every abstract method/interface method it's obligated to implement (walking through multiple abstract superclasses and multiple implemented interfaces)?
- How are interface default/static methods (if Apex interfaces support anything like them) and generic interface implementations (`implements Comparable<Foo>`-shaped) handled today, if at all?
- What happens today, concretely, for a real concrete class that fails to implement a required abstract/interface method -- does anything already detect this (e.g. as a byproduct of some other resolution), or does it silently pass through?
- Does resolution stop cleanly (as `Unresolved`/some existing signal) when a supertype or interface itself can't be resolved, so the new check can safely skip those cases without guessing (matching this project's zero-false-positive bar)?

This ticket is fact-finding only -- it does not implement anything. Its answer determines [Implement the missing-interface/abstract-method-implementation diagnostic](07-missing-interface-impl-implement.md)'s real scope and edge cases.

## Answer

### 1. Is there already a flattened "required methods" view? No -- only a resolved ancestor-id chain exists.

`inherit.rs::resolve_inheritance` (`crates/apex-binder/src/inherit.rs:32-93`) produces exactly two per-type outputs, both stored on `SymbolTable`:

- `inherited_chain` (`inherit.rs:65-71`, stored via `SymbolTable::set_inherited_chain`/`inherited_chain`, `crates/apex-binder/src/symbol_table.rs:343-354`): every `SymbolId` transitively reachable from a type through *resolved* `extends`/`implements` names, flattened and cycle-guarded by `flatten` (`inherit.rs:101-116`). This walks through multiple abstract superclasses *and* multiple implemented interfaces uniformly -- both feed the same `raw_extends: Vec<(SymbolId, Vec<SmolStr>)>` input (see `collect.rs:200-215` for classes, `collect.rs:252-261` for interfaces' own `extends` list), so a class's chain already contains every ancestor class and every ancestor/implemented interface, transitively.
- `direct_super` (`inherit.rs:44-49`, `symbol_table.rs:356-364`): a class's single direct `extends` target only, for `super(...)` resolution -- deliberately narrower, never includes `implements` targets.

Neither is a *method* list. `inherited_chain` is a set of **type ids**. Turning it into "every abstract/interface method this concrete class must implement" requires a new pass that, for each ancestor type id in the chain, filters its `members_of(ancestor)` (`symbol_table.rs:325-330`) down to methods that are either interface-declared or `is_abstract`, then checks whether the concrete class (or some ancestor closer to it in the chain) already provides a satisfying override. **This flattening does not exist anywhere in the codebase today** -- confirmed by grepping `apex-binder/src` for stub/override-generation logic (`override_stub`, `implement_interface`, `unimplemented`, etc. -- no matches) and by reading `completion.rs`/`call_hierarchy.rs` in full (see §3).

What a new check *can* build on directly:
- `inherited_chain(class_id)` for "every ancestor type to scan," already resolved and cycle-safe.
- `members_of(ancestor_id)` for each ancestor's own direct methods.
- `Symbol.modifiers.is_abstract` (`crates/apex-binder/src/symbol.rs:101`) for abstract-class methods.
- **Interface methods are implicitly abstract without the `abstract` modifier bit ever being set** -- confirmed by the parser's own doc comment, "interface methods never have a body" (`crates/apex-parser/src/grammar/declarations.rs:376-378`), and by `resolve.rs`'s existing `is_dynamically_dispatchable` helper (`crates/apex-binder/src/resolve.rs:359-381`), which treats "declared directly on an `Interface`" as a *separate* disjunctive case from `m.is_abstract`. Any new "is this method a requirement" test must replicate that same disjunction (`is_abstract || container.kind == SymbolKind::Interface`), not just check `is_abstract` alone.
- `Symbol.kind` on the class itself (`SymbolKind::Class` with `modifiers.is_abstract == false`) to gate the check to genuinely concrete classes -- an abstract subclass legitimately need not implement everything.

One nuance worth flagging for ticket 07's design discussion: `SymbolTable::lookup_member`'s existing override-shadowing logic (`symbol_table.rs:484-552`) only excludes an ancestor candidate once a more-derived *same-arity* candidate has `modifiers.is_override == true`. That flag is required (and set) when a class overrides a `virtual`/`abstract` method from an ancestor **class**, but Apex does **not** require (or usually write) `override` when a class implements an **interface** method -- confirmed empirically by this project's own `dynamic_dispatch_resolution.rs` fixtures, e.g. `Impl implements Greeter { public String greet() {...} }` with no `override` keyword (`crates/apex-binder/tests/dynamic_dispatch_resolution.rs:99-126`), and that same test shows a call through the interface-typed reference resolving to `Resolution::Candidates([greeter_greet, impl_greet])` -- i.e. today's machinery deliberately keeps both the interface declaration and the implementation as separate candidates for dynamic-dispatch-widening purposes, it never collapses "the abstract declaration is satisfied by this concrete member" into a single answer. A "required methods" pass therefore cannot reuse `lookup_member`'s `is_override`-based shadowing as-is for interface satisfaction; it needs its own "same name (case-insensitive) + same arity, declared on something at or below this ancestor level in the chain" test that doesn't require `is_override` for the interface case but should for the abstract-superclass case (matching real Apex's own asymmetry between `extends` overriding and `implements` satisfying).

### 2. Interface default/static methods and generic interfaces

**Default/static interface methods do not exist in Apex, and this is enforced structurally, not just by convention.** The grammar's own doc comment states it plainly: `interfaceMethodDeclaration: modifier* (typeRef|VOID) id formalParameters ';' -- interface methods never have a body` (`crates/apex-parser/src/grammar/declarations.rs:368-378`). `InterfaceBody::methods()` (`crates/apex-syntax/src/ast/decl.rs:216-220`) only ever yields `MethodDecl` children -- there is no field/property/constant path into an interface body at the AST level at all. So there is nothing to "handle" here: the sub-question's premise (Java-style default/static interface methods) doesn't apply to Apex, and no design effort is needed for it.

**Generic interfaces are also a non-issue, for a different reason: Apex has no user-defined generics at all.** `generics.rs`'s own module doc comment states this directly: "Apex has no user-defined generics at all (only these three built-in collection types [`List`/`Map`/`Set`] are generic)" (`crates/apex-binder/src/generics.rs:1-7`). A project-local `interface` can never itself declare a type parameter (`public interface Foo<T>` isn't legal Apex), so "multiple generic interface implementations" in the project-local sense the ticket worried about cannot occur.

What *can* occur is a project class implementing a **generic-shaped standard-library interface**, e.g. `implements Comparable` or `implements Iterator<Account>`. Checked directly against the raw stdlib data (`crates/apex-stdlib/data/apex_reference.json`) rather than inferring from Rust struct shape:
- `Comparable` (line 80100) is **not actually generic in real Apex** -- its one method's real signature is `public Integer compareTo(Object objectToCompareTo)` (line 80108), a plain `Object` parameter, no type substitution involved at all.
- `Iterator` (line 85828) genuinely is generic (`Iterator<T>`), with `hasNext()`/`next()` (lines 85836-85853) type-erased to `Object` in the reference doc; a real implementation narrows `next()`'s return type to `T`.

Either way, **this is moot for the current chain-resolution layer**, because `SymbolTable` only holds project-local declarations -- `Comparable`/`Iterator`/every other stdlib interface is never a member of `top_level`/`nested_type`, so `resolve_dotted_name_from` (`symbol_table.rs:654-673`) can never resolve `implements Comparable` or `implements Iterator<Account>` to a `SymbolId` at all. `Type::text()` (`crates/apex-syntax/src/ast/decl.rs:385-412`) does strip the `<Account>` generic argument before the name ever reaches `inherit.rs`, so even if `Iterator` *were* project-resolvable, the `<T>` substitution would already be lost by the time chain resolution sees it -- but that's academic here since stdlib interfaces never enter `inherited_chain` in the first place (see §4 below for why that matters more than it sounds).

### 3. What happens today when a concrete class fails to implement a required method: nothing detects it

No existing pass notices. Confirmed by:
- Reading `completion.rs` in full: its only inheritance-aware logic (`crates/apex-binder/src/completion.rs:320-345`) walks `inherited_chain` to build a `.`-access member-suggestion list -- purely a lookup helper, no "what's missing" computation, and no override-stub-generation code path exists anywhere in `apex-binder/src` (grepped for `override_stub`/`implement_interface`/`unimplemented`/`stub_method` -- zero matches).
- Reading `call_hierarchy.rs` in full: zero references to `abstract`/`interface`/`override`/`inherited_chain` at all -- it has nothing to do with type obligations.
- `dead_code.rs`'s analysis (`crates/apex-binder/src/dead_code.rs`) is reference-counting in the other direction entirely (flagging *unused* declarations, not *missing* ones) and its own module doc comment (`dead_code.rs:1-7`) states the project's "deliberately conservative... only ever flags a declaration when it can rule out every channel it knows about" bar -- this is the zero-false-positive precedent the ticket references, but it isn't itself a source of missing-implementation detection.
- `resolve.rs`'s `expand_dynamic_dispatch`/`widen_for_dynamic_dispatch` (`resolve.rs:400-451`) widens a resolved call to every subtype's same-name/same-arity override for dead-code reference-crediting purposes -- but it never checks that such an override actually exists as a *requirement*; it only widens when one happens to be present, and silently does nothing (returns just the base candidate) when it isn't. It's the closest existing code to "walking who overrides what," but it runs in the opposite direction (interface/abstract type -> its subtypes) from what a missing-implementation check needs (concrete class -> its required ancestor methods), and it never flags absence.
- No test anywhere in `crates/apex-binder/tests/` exercises a concrete class that fails to implement a required method -- every `implements`/`extends` fixture across `extends_chain_resolution.rs` and `dynamic_dispatch_resolution.rs` is well-formed Apex where the concrete type always provides what's required. Grepped the whole crate for `unresolved_direct_super`/"does not implement"/"missing...implement"/"abstract method" -- no hits outside the plumbing itself.

So today, a concrete class that omits a required abstract/interface method binds and resolves exactly as if it were compliant -- it silently passes through unnoticed, exactly as the ticket suspected.

### 4. Does resolution stop cleanly on an unresolved supertype/interface? Only partially -- this is the load-bearing gap

Two very different signal qualities exist depending on which clause is involved:

- **A class's own single direct `extends` name**: if it fails to resolve against the project, `inherit.rs:44-49` explicitly records that fact via `SymbolTable::set_unresolved_direct_super`/`unresolved_direct_super` (`symbol_table.rs:118-135`, `366-379`) -- a real, queryable "this name is real Apex but external" signal (the documented motivating case is `extends Exception`). A future check *can* safely use this to skip a class whose direct superclass is unresolvable.
- **Every `implements` name, and every non-direct ancestor further up an `extends` chain**: there is **no equivalent signal at all**. `inherit.rs:56-63`'s `direct` map building explicitly documents dropping an unresolvable name with zero record: "an unresolvable supertype contributes nothing to the chain, it doesn't abort collection" (`inherit.rs:51-55`). Once dropped, that name is gone for good -- `SymbolTable`'s only per-type inheritance state is `inherited_chain`/`direct_super`/`unresolved_direct_super`/`subtypes`, none of which retain *which* raw names were attempted and failed for anything but the single direct-`extends` case.
- The raw pre-resolution strings (`raw_extends: Vec<(SymbolId, Vec<SmolStr>)>`) that *would* let a caller reconstruct "this class named N things, M of which resolved" are collected in Pass 1 (`collect.rs:200-261`) and persisted only inside the incremental `BindCache` (`crates/apex-binder/src/incremental.rs:163-168`), purely so `resolve_inheritance` can be re-run cheaply on an incremental rebuild. **`BoundProgram` -- the type every diagnostic pass (including `dead_code.rs`) actually operates over -- does not expose `raw_extends`/`raw_super` at all** (confirmed by reading `BoundProgram`'s full field list, `crates/apex-binder/src/lib.rs:111-150`, and its `from_files_cached` pipeline, `lib.rs:186-260+`, which only ever writes those into the private `BindCache`, never into the returned snapshot). So even a diagnostic pass with full access to `BoundProgram` has no way today to distinguish "this class implements nothing else" from "this class implements something that failed to resolve" for anything other than a class's own direct extends target.

**Practical consequence, concretely**: a class written as `public class Foo implements Comparable { ... }` or `public class MyBatch implements Database.Batchable<SObject> { ... }` -- both extremely common real Apex shapes -- gets **zero** entries for `Comparable`/`Database.Batchable` in `inherited_chain`, indistinguishable today from a class that declared no `implements` clause at all. This is not a corner case; it's true of *every* standard-library interface a project class implements (`Comparable`, `Iterator`, `Iterable`, `Queueable`, `Schedulable`, `Database.Batchable`, `Messaging.InboundEmailHandler`, `StubProvider`, ...), since `SymbolTable` only ever contains project-local declarations. Building the future diagnostic directly on `inherited_chain` as-is would therefore not just miss these cases -- worse, if it tried to also flag "implements nothing, so nothing required" it would be unable to tell that apart from "implements an unresolvable/external interface, skip me," which is exactly the zero-false-positive trap `dead_code.rs`'s own doc comment (`dead_code.rs:1-7`) warns against.

### Recommendation for ticket 07

Before implementing, ticket 07 needs to settle:

1. **Scope decision: project-local-only vs. also standard-library interfaces.** As shown above, `inherited_chain` today silently drops every standard-library `implements` target, so a check limited to what's already resolved will only ever catch a class extending a project-local abstract class or implementing a project-local interface (fully achievable with existing data) -- it will never catch a class that botches `Comparable`/`Database.Batchable`/etc., which is likely the *more* common real-world case this diagnostic would otherwise be valuable for. Extending coverage to stdlib interfaces is plausible (`apex-stdlib`'s raw JSON already carries each interface's method list, e.g. `apex_reference.json:80104-80121` for `Comparable`), but requires a genuinely new cross-reference step (project class -> unresolved implements name -> stdlib interface lookup by name) that doesn't exist yet, and should be scoped as an explicit, separate decision rather than assumed in passing.
2. **A structural prerequisite regardless of scope**: `inherit.rs`/`SymbolTable` needs a real "did every `implements`/every chain-hop resolve" signal before any missing-method check can be zero-false-positive-safe -- today only a class's single direct `extends` name has one (`unresolved_direct_super`). At minimum this means extending `resolve_inheritance` to record, per type, whichever of its raw `implements`/`extends` names failed to resolve (not just silently drop them), so the new check can unconditionally skip any class touching an unresolved name anywhere in its chain, exactly the same conservative posture `dead_code.rs` already takes.
3. **The interface-vs-abstract-class satisfaction-test asymmetry** flagged in §1: an interface method is satisfied by any same-name/same-arity method regardless of `is_override`; an abstract-superclass method is only legitimately satisfied by one carrying `is_override` (or `virtual override` further down a multi-level chain, per `dynamic_dispatch_resolution.rs`'s own module doc comment, `crates/apex-binder/tests/dynamic_dispatch_resolution.rs:8-24`, on the `virtual override` re-override rule). The flattening pass needs two different satisfaction rules, not one.
4. **Multiple-interface signature collisions and diamond shapes** (two implemented interfaces requiring same-name/different-arity or same-signature methods) are structurally already handled at the *type-graph* level by `flatten`'s cycle/visited-set guard (`inherit.rs:95-116`, dedupes any type appearing twice in the chain), but the *method*-level dedup (two interfaces both requiring, say, `void run()`) still needs explicit design -- satisfying it once should satisfy both, which falls out naturally from a name+arity-keyed "still missing" set as long as the flattening pass is written that way from the start.
