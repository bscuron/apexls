Type: research
Status: resolved

## Question

Survey every call site and usage pattern of `crate::ty::Ty` (`crates/apex-binder/src/ty.rs`) across `resolve.rs`, `generics.rs`, and `conversions.rs` to establish, precisely:

- What per-expression type information is already computed during Pass 2 body walking but currently discarded once the walker moves past that expression (never stored on `BoundProgram`, never exposed outside the walker)?
- What are `Ty`'s current precision gaps for a stored/queryable use case -- e.g. does it distinguish a system type's own possible values precisely enough for real type-mismatch checking, or is `Ty::System { name, args }`'s "not project-local, but at least named" level of detail (per its own doc comment) too coarse?
- Survey a sample of real Apex code from the NPSP corpus for the specific patterns a type-mismatch/wrong-argument-type diagnostic would need to handle correctly to hit zero false positives: implicit numeric widening, `Object`-typed parameters/variables, `List`/`Set`/`Map` generic substitution (already handled by `generics.rs` for some cases), SObject dynamic typing, and any other real-world pattern that would trip up a naive nominal-type-equality check.
- What would the minimal viable promotion of `Ty` into a stored, queryable per-expression type layer look like, structurally (e.g. a new field on `BoundProgram`, keyed how) -- without committing to build it; just scope what "minimal" could mean as input to the architecture decision.

This ticket is fact-finding only -- it does not decide the architecture. Its findings feed [Decide the Ty-promotion / type-inference-layer architecture](09-ty-promotion-architecture-decision.md).

## Answer

### 1. What's computed but discarded today

`bind_expr` (`crates/apex-binder/src/resolve.rs:1887`) returns `Option<Ty>` for *every* expression kind, but the overwhelming majority of its call sites are statement-level and simply never bind the return value:

- **`Stmt::LocalVarDecl`** (`resolve.rs:1855-1871`) is the single most consequential discard site: `self.resolve_type_ref(&ty)` (line 1857) computes the *declared* `Ty` and `self.bind_expr(scope, &e)` (line 1861) computes the *initializer*'s inferred `Ty` for every declarator -- both are thrown away immediately (neither captured into a local, neither compared to the other). This is exactly the `Integer x = someMethodReturningString();` mismatch shape; today nothing downstream ever sees these two `Ty`s side by side.
- The `for`-loop init-declarator arm (`resolve.rs:1649-1671`) discards the same pair for a `for (Integer i = someExpr(); ...)` init.
- **`Stmt::Return`** (`resolve.rs:1799-1802`) binds the returned expression's `Ty` and drops it -- never compared against the enclosing method's own declared return type, even though `self.enclosing_member: Option<SymbolId>` (`resolve.rs:742`) is already in scope and `self.type_of_symbol(id)` (`resolve.rs:1424`) already knows how to turn a method symbol into its return `Ty`. A `return "oops";` from a method declared `Integer` computes a `Ty::system("String")` for the return expression and never checks it against anything.
- Every other purely-side-effecting statement arm (`Stmt::Expr` at 1872-1875, `Stmt::Throw`/`Insert`/`Update`/`Delete`/`Undelete`/`Upsert`/`Merge`/`RunAs`/`If`'s condition/`Switch`'s condition/`For`'s condition and update exprs/`ForEach`'s iterable, `resolve.rs:1609-1849` generally) discards its `bind_expr` result the same way. The single bare-expression body walk at `resolve.rs:852` (`binder.bind_expr(root_scope, expr)`, used for a field/property initializer with no enclosing statement at all) and the dynamic-SOQL-bind walk in `crates/apex-binder/src/soql.rs:114` do too.
- Argument `Ty`s (`arg_types: Vec<Option<Ty>>`, built at `resolve.rs:2848-2853` for method calls and `3095-3099`/`3226-3236` for calls/`new`) *are* consumed -- but only to disambiguate overloads via `narrow_by_overload`/`narrow_stdlib_overload`, and even there, **the check is skipped for the common non-overloaded case**: `narrow_by_overload` (`resolve.rs:122-163`) short-circuits at line 142-144 (`if pool.len() == 1 { return Resolution::Resolved(pool[0]); }`) the instant arity alone leaves one same-name candidate, *before* `is_argument_type_compatible`/`conversions::type_compatible` ever run. So today, a call to a non-overloaded method with a wrong-typed argument silently resolves fine -- the type-compatibility machinery that already exists (`conversions.rs`) is wired only into tie-breaking, not into validation.
- Nothing computed by `bind_expr`, `bind_stmt`, or their helpers is stored on `BoundProgram` (`crates/apex-binder/src/lib.rs:111-150`): the struct holds `symbols`, `schema`, `stdlib`, `labels`, `pages`, per-file `bodies: FxHashMap<FileId, Arc<FileBodies>>`, and `vf_referenced_classes` -- no field of any `Ty`-shaped type anywhere. `crate::reference_table::ReferenceTable` (`reference_table.rs:296-321`), the one place *some* per-expression information does survive (`resolutions: FxHashMap<SyntaxPtr, Resolution>`), stores `Resolution` (what a reference resolved *to*, a `SymbolId`/schema-object/stdlib-member/label/page), never the walker's own inferred `Ty` -- confirmed by `ty.rs`'s own module doc comment, which says this explicitly.

### 2. `Ty`'s precision gaps for a stored/queryable use case

- **`Ty::System { name, args }` conflates two genuinely different things** (per its own doc comment, `ty.rs:17-27`): an unmodeled system/library type (`String`, `Integer`) and a schema SObject type (`Account`) that `SchemaIndex` *does* know real facts about (fields, describe info). For chaining member lookups this conflation is harmless (`Resolution::SchemaObject` vs `Unresolved` already keeps the real distinction elsewhere), but for a stored, queryable "what type is this expression" layer, a consumer would have to re-derive "is this actually a real SObject" by calling back into `SchemaIndex` every time, rather than reading it off the `Ty` itself.
- **No `Object`/`void`/`null` distinction.** `Ty::for_literal` returns `None` for `null` "compatible with everything, so inventing one would be worse than `None`" (`ty.rs:98-99`, `159-161`) -- but that makes `None` overload two meanings a stored layer would need to keep apart: "not known" (a genuinely uninferred expression) and "known to be `null`/untyped-compatible-with-anything." A void method call's result is also just `None`, indistinguishable from an unresolved one.
- **No representation of "ambiguous but narrowed."** `result_type_of` (`resolve.rs:1556-1571`) already handles `Resolution::Candidates` by returning a `Ty` only when *every* surviving candidate shares the identical return type, and gives up (`None`) otherwise -- a real, silent precision loss for a would-be diagnostic (e.g., candidates could differ only by return type nullability/subtype and still be usably narrowed for compatibility checking, but `Ty` has no "one of several" variant to carry that).
- **No source location/span carried on `Ty` itself.** `Ty` is purely a value returned up through recursive `bind_expr` calls; nothing ties a specific `Ty` back to the `Expr`/`SyntaxPtr` it came from except being in a caller's local variable at the moment it's computed. Promoting it to a stored, queryable layer requires deciding that key structurally (see §4) -- `Ty` itself has no notion of "which expression."
- **`SmolStr`-named system types have no canonicalization guarantee beyond what already-written call sites happen to produce.** `Ty::system_owned` accepts any source-text spelling (`resolve.rs:1528`, `ty_from_scraped_type` at `resolve.rs:281-288`), and while today's call sites are careful to strip `Namespace.` prefixes and split generic args, nothing in `Ty`'s own type enforces that invariant -- a `Ty::System` built by a new call site could carry an un-normalized name, silently defeating any name-based comparison a stored layer would want to do (e.g. `"Account"` vs `"Schema.Account"`).
- **Numeric/date rank and curated-conversion knowledge live entirely in `conversions.rs`, not in `Ty` itself.** This is fine for the current one-shot "can this argument go here" use, but a queryable layer that wants "is expression A's type assignable to expression B's type" as a general query still has to reach for `conversions::type_compatible`/`widen` every time -- `Ty` alone doesn't encode widenability.

### 3. Concrete NPSP patterns a zero-false-positive checker must handle

- **Implicit numeric widening at a call boundary.** `TEST_OpportunityBuilder.cls:161` declares `public TEST_OpportunityBuilder withAmount(Decimal amount)`; real call sites pass bare integer literals with no cast, e.g. `ALLO_Allocations_TEST.cls:780` (`.withAmount(20)`) and `ACCT_CascadeDeleteLookups_TEST.cls:162` (`.withAmount(2)`). A naive nominal check (`Ty::system("Integer") != Ty::system("Decimal")` => flag) would false-positive on this extremely common shape. `conversions::numeric_rank`/`type_compatible` (`conversions.rs:121-127, 245-247`) already models this correctly.
- **Mixed-type arithmetic through SObject fields and literals.** `ALLO_Allocations_TDTM.cls:685`: `allo.Amount__c = (amount * allo.Percent__c * .01).setScale(2);` -- `allo.Percent__c`/`Amount__c` are `Decimal` custom fields, `.01` is a `NumberLiteral` (typed `Decimal` per `Ty::for_literal`, `ty.rs:110`), and `amount` is a parameter of unknown-here type -- `Ty::for_bin_op`'s `lhs.or(rhs)` fallback (`ty.rs:134`) means the expression's inferred type depends on evaluation order and doesn't actually verify every operand is arithmetic-compatible; a checker built directly on today's `for_bin_op` output could miss a real mismatch or invent a false one depending on which side is `None`.
- **`Object`-typed variables/returns receiving concrete values from dynamic SObject field access.** `HouseholdNamingService.cls:209`: `Object currentNumberOfHouseholdMembersValue = household.get('Number_of_Household_Members__c');` -- `SObject.get(String)`'s scraped return type is bare `Object` (real Salesforce API), so the RHS's `Ty` is `Ty::system("Object")` while the field's real runtime value is a `Decimal`. `conversions::type_compatible` already treats `Object` as universally compatible in both directions where it's the *parameter* (`conversions.rs:189-191`), but a checker also needs the *reverse* direction (concrete value assigned *into* a declared `Object`-typed local) to never flag -- which is the common case here, and which the same short-circuit already covers as long as it's consulted for assignments, not just call arguments.
- **Casts recovering a concrete type out of dynamic `.get(...)`.** `HouseholdNamingService.cls:516` (`(String) household.get('Name')`), `LegacyHouseholds.cls:263` (`Id objId = (Id) dmlObj.get('id');`) -- an explicit `Cast` expression's `Ty` (via `resolve_type_ref`, `resolve.rs:1919-1924`) must be trusted as the expression's real type going forward rather than the pre-cast `Object`, or every one of these extremely common defensive-unboxing idioms becomes a false positive.
- **Collection covariance (`List<Concrete>` into a `List<SObject>`/`List<Object>`-typed parameter), with no cast.** `AccountAdapter.cls:383` declares `public List<Account> householdAccounts()`; `AccountAdapter.cls:285` passes its result directly, uncast, to `HouseholdNamingService.cls:459`'s `setCustomNamingField(List<SObject> records, Map<Id, SObject> oldMap)`. This is real, uncast, uncontrived code relying on exactly the collection-covariance rule `conversions.rs`'s own doc comment (`conversions.rs:23-25`) had to verify against a live org because it's *not* Java's invariant-generics behavior. A checker ignoring this (treating `List<Account>` and `List<SObject>` as simply "different, therefore mismatched") would false-positive constantly across real Apex. (NPSP elsewhere also explicitly casts the identical shape, e.g. `HouseholdService.cls:178`: `unitOfWorkInst.registerNew((List<SObject>) households);` where `households: List<npo02__Household__c>` -- showing both the cast and uncast spellings of the same legal widening coexist in one real codebase, so a checker can't assume "uncast implies same-type" either.)
- **`Id`/`String` bidirectional compatibility with no principled specificity winner.** Already called out and empirically verified in `conversions.rs:36-51` (a real org resolves `describe(String)` over `describe(Id)` for *every* call including one whose argument is `Id`-typed) -- any mismatch checker reusing `Ty` must not invent a preference between these two where `conversions.rs` deliberately stays silent, or it risks a wrong, confident answer instead of an honest "can't tell." `CON_ContactMerge_TEST.cls:52` (`row.selectedValue = String.valueOf(masterId);`, `masterId` being `Id`-typed) shows the defensive-conversion style real code often uses instead of relying on the implicit rule, but the implicit assignment (`String s = someId;`) is separately confirmed legal and must not be flagged.
- **SObject-to-`SObject` widening, never the reverse, never sibling-to-sibling.** Already modeled in `system_type_compatible` (`conversions.rs:261-277`) via `schema.object(...)`, not a name guess -- any new consumer of `Ty` for a diagnostic must route through this existing logic (or reuse it) rather than re-deriving object-ness from `Ty::System`'s name alone, since `Ty` itself doesn't carry "is this a real SObject" as a boolean.

### 4. Scoped options for "minimal viable promotion" (not a decision)

All of these are structural sketches only -- picking one, and how far to take it, is `09-ty-promotion-architecture-decision.md`'s job, not this ticket's.

- **Option A -- a parallel `SyntaxPtr`-keyed map, mirroring `ReferenceTable`'s existing shape.** `ReferenceTable` already proves the pattern (`reference_table.rs:296-297`: `resolutions: FxHashMap<SyntaxPtr, Resolution>`, populated by `set`/`set_with_highlight` as the walker goes). A `types: FxHashMap<SyntaxPtr, Ty>` populated at the same call sites `bind_expr` already returns a `Ty` from (one `.insert` per non-`None` return, keyed by `SyntaxPtr::new(self.file, expr.syntax())`) would need no new traversal -- just an extra write at the existing return points. It would live on `BodyBinder`/`ReferenceTable`'s sibling (or inside `ReferenceTable` itself as a second field) and surface on `FileBodies`/`BoundProgram` the same way `refs` does today. Cost: one hashmap entry per typed expression per body; `Ty` would need to become `pub(crate)`-visible outside `apex-binder`'s internals only if a diagnostic pass lives in a different module/crate.
- **Option B -- narrower: only at statement-relevant checkpoints, not every expression.** Instead of keying by every `SyntaxPtr` `bind_expr` ever touches, only capture `Ty` at the handful of sites in §1 that actually matter for a mismatch diagnostic: `Stmt::LocalVarDecl`'s (declared `Ty`, initializer `Ty`) pair, `Stmt::Return`'s (declared return `Ty`, returned-expression `Ty`) pair, and method-call argument `Ty`s already collected in `arg_types` (already computed, just needs `is_argument_type_compatible`/`type_compatible` invoked unconditionally instead of only when `pool.len() > 1`). This avoids a whole-body storage cost and can run the compatibility check *inline*, during Pass 2, emitting a diagnostic (or recording a `(SyntaxPtr, mismatch info)`) directly rather than persisting `Ty` at all -- effectively "promote the check, not the type."
- **Option C -- a dedicated small diagnostics-only pass, reusing `Ty` transiently.** Add a new, focused walk (or extend the existing one) that calls `bind_expr`-equivalent logic *again* only at the checkpoints from Option B, purely to compare two `Ty`s via `conversions::type_compatible`/`widen` and emit findings -- without ever storing `Ty` anywhere long-lived. Cheapest to build, but duplicates part of the walk (or requires `bind_expr` to optionally take a callback/collector) and forecloses any other future consumer (e.g. hover-shows-inferred-type) that would want the same data.
- **Common considerations regardless of option:** (1) `Ty`'s `SymbolId`/`SmolStr` payloads are already cheap to clone (that's the whole point of `ty.rs`'s own doc comment on `SmolStr` vs `String`), so storage cost is dominated by entry *count*, not per-entry size -- Option A's "every expression" scope is affordable if it's ever wanted for something beyond diagnostics (e.g. hover). (2) Any option needs to fix the `pool.len() == 1` short-circuit in `narrow_by_overload` (`resolve.rs:142-144`) to still run `type_compatible` when it wants a diagnostic (today it's a valid optimization for resolution but silently skips validation). (3) Whatever layer emits diagnostics from this must reuse `conversions::type_compatible`/`is_curated`'s "only eliminate on positively-known incompatibility, `None` never eliminates" discipline (`conversions.rs:169-176`) -- that discipline is exactly what today's zero-false-positive overload resolution already depends on, and a type-mismatch diagnostic has the same correctness bar.
