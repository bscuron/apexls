Type: research
Status: resolved

## Question

Investigate what a cross-method (transitive) extension of the DML/SOQL-in-loop diagnostic would actually need, to feed [the architecture-decision ticket](12-cross-method-bulkification-decision.md). `apex-binder` has no call-graph or control/data-flow analysis of any kind today (confirmed while resolving ticket 04 -- grepped the whole crate, only doc-comment caveats explicitly disclaiming a real CFG/data-flow analysis exist), so this is a genuinely new capability, not an extension of an existing one. Establish, concretely:

- **How common is the real shape in practice?** Sample the real NPSP corpus: how often does a loop body call a project-local method (directly, one hop) whose own body contains a DML statement or SOQL query? How deep do these chains typically run in practice (one hop, or several) before hitting a DML/SOQL statement? This bears directly on whether one-hop coverage alone would already catch the overwhelming majority of real cases, or whether skipping full transitive tracing would miss most of them.
- **Cycle handling.** Does real Apex code (or could it, syntactically) have mutually-recursive or self-recursive call chains that would need cycle detection to avoid an infinite walk? Survey what `apex-binder`'s existing `inherited_chain` (`inherit.rs`) does for its own analogous cycle-guarding on type hierarchies, as a possible existing pattern to reuse for a call-graph walk instead of building cycle detection from scratch.
- **Virtual/interface dispatch ambiguity.** When a call in the chain resolves to `Resolution::Candidates` (multiple possible concrete methods -- the binder already can't narrow interface/virtual dispatch to one target), what should happen: treat the call as tainted if *any* candidate contains DML/SOQL (higher recall, more false-positive risk), only if *every* candidate does (lower recall, safer), or leave dispatch-ambiguous calls out of this analysis entirely (matching how BACKLOG.md already treats `Resolution::Candidates`-as-error as "too risky against this project's own no-guessing discipline" for an unrelated diagnostic)?
- **Cost.** Would a whole-project "does method X's body contain DML/SOQL, directly or transitively" fact need to be computed as a new pass (and cached/invalidated on incremental rebuild, matching `apex-binder`'s existing three-pass incremental structure), or could it be computed lazily per query? Rough-estimate the cost against the real NPSP corpus's method count.

This ticket is fact-finding only -- it does not decide the architecture. Its findings feed [the architecture-decision ticket](12-cross-method-bulkification-decision.md).

## Answer

Investigated with a throwaway integration test in `apex-binder` (`BoundProgram::from_files` against the real NPSP checkout at `tests/corpus/npsp`, submodule pin `3dc817c94e3f2d41d461f6a79dd9e83c279ded9c`, 1,035 `.cls` files / ~316k lines), deleted before this commit -- not grep heuristics, real parsed/bound AST + the binder's actual `Resolution` data. Every number below is from that run.

### How common is the shape, and how deep do chains run?

Corpus-wide: 12,351 `Method`/`Constructor` symbols, of which 2,499 (20.2%) directly contain a keyword DML statement, `SoqlExpr`, or a textual `Database.insert/update/delete/upsert/undelete/merge/query/countQuery/getQueryLocator(` call (the same trigger set [ticket 04](04-dml-soql-in-loop-diagnostic.md)/[ticket 10](10-dml-soql-in-loop-implement.md) settled for the direct rule). 3,083 loop nodes (`ForStmt`/`ForEachStmt`/`WhileStmt`/`DoWhileStmt`) exist project-wide; 162 already contain DML/SOQL directly (ticket 10's rule already catches these). Of the 1,328 loops that call at least one project-local `Method`/`Constructor` (`Resolution::Resolved` or `Candidates`):

- **87 loops (one-hop)**: a directly-called local method's own body directly contains DML/SOQL. E.g. `CDL_CascadeDeleteLookups.cls:247` (`undeleteRecords` calling `load`), `BDI_AdditionalObjectService.cls:269/294` (`importObjectWrappers` calling `updateRecords`/`insertRecords`).
- **232 loops (any-hop, cycle-guarded BFS capped at depth 9)**: some call chain from the loop eventually reaches DML/SOQL. 226 of these 232 are *not* already caught by the direct rule -- i.e. cross-method tracing would add roughly **226 net-new flaggable loops** against this corpus (about 7.3% of all loops, 17% of loops that call any local method).
- **Depth histogram of the 232 any-hop hits**: depth 1 (one-hop) = 87, depth 2 = 50, depth 3 = 28, depth 4 = 27, depth 5 = 12, depth 6 = 19, depth 8 = 4, depth 9 = 5 (no depth-7 hits; none exceeded 9 in this corpus).

**This directly answers the "is one-hop enough" question: no.** One-hop coverage (87) is only 37.5% of what full transitive tracing eventually finds (232) -- the majority (62.5%, 145 of 232) of real cross-method bulkification shapes in NPSP require walking *two or more* hops, and real chains run as deep as 8-9 methods before hitting a DML/SOQL statement (e.g. deep service/gateway layering in classes like `RLLP_OppPartialSoftCreditRollup_TEST.cls`, `BDI_AdditionalObjectService.cls`, `LD_LeadConvertOverride_TEST.cls`, all of which appear at multiple hop depths in the raw run). Restricting to one hop only, as a scope-limiting compromise, would leave the majority of the real problem this ticket exists to catch on the table.

### Cycle handling

Real cyclic/self-referential call structure exists in NPSP, confirmed both syntactically and via the binder's own resolution data -- a call-graph walk cannot skip cycle detection:

- **Genuine recursion, syntactically confirmed:** `fflib_Criteria.cls`'s inner `FormulaEvaluator` class is a real composite/tree pattern: its constructor (`fflib_Criteria.cls:206`) recursively instantiates itself for each sub-formula (`fflib_Criteria.cls:222`: `formulaParts.add(new FormulaEvaluator(subFormula));`), and its `toSOQL(Map<Integer,String>)` (`fflib_Criteria.cls:285`) loops over `IFormulaEvaluator`-typed children (`fflib_Criteria.cls:288`) calling `evaluator.toSOQL(queryByNumber)` (`fflib_Criteria.cls:292`) -- an interface-typed dispatch that can loop back into another `FormulaEvaluator`. A naive unguarded walk starting from that `for` loop would recurse forever on this real file.
- **Project-wide cycle census:** a 3-state (unvisited/on-stack/done) DFS over the whole call graph -- built entirely from `apex_binder::outgoing_calls`, no new traversal primitive needed -- found **67 callables participating in at least one call cycle** project-wide (out of 12,351), the great majority self-loops (a method whose own `Resolution` set names itself), a minority genuine mutual cycles (e.g. `fflib_Criteria.cls`'s `evaluate`/`toSOQL` family).
- **A cautionary finding**: not every apparent "self-recursion" is real recursion -- some are `Resolution::Candidates` artifacts. `fflib_SObjectUnitOfWork.cls:230-236`'s bulk overload (`registerEmptyRecycleBin(List<SObject> records)`) loops calling the singular overload (`registerEmptyRecycleBin(record)`, line 234) -- textbook bulk-delegates-to-singular, not recursion -- yet the binder resolves that call site as `Resolution::Candidates` naming *five* same-named declarations project-wide (confirmed via direct debug dump of `call_sites_in_range`, including the List-arg method itself), because `registerEmptyRecycleBin` is declared six times across `fflib_ISObjectUnitOfWork.cls:131,137` (interface), `fflib_SObjectUnitOfWork.cls:217,230` (the `virtual class`, line 54), and an unrelated `fflib_SObjectMocks.cls:158,163` mock. This means a self-loop found by a naive "did any candidate include myself" cycle check can be a resolution-ambiguity artifact, not true recursion -- worth keeping in mind when interpreting cycle output, though it doesn't change the *need* for cycle guarding (an artifact self-edge still has to terminate the walk, not be treated as "impossible so no guard needed").
- **Existing pattern to reuse, and why it needs strengthening**: `inherit.rs`'s `flatten` (`crates/apex-binder/src/inherit.rs:101-116`) already guards exactly this shape for the *type*-hierarchy graph -- a `FxHashSet` visited-set plus an explicit stack (not a recursion). Its comment explicitly calls out that this handles "a malformed `class A extends B` / `class B extends A` (or any longer cycle, or a diamond shape)". That "visited once, never revisit" shape is directly reusable *as-is* for one thing a call-graph walk also needs: deduplicating repeated reachability (the same helper called from ten different loops shouldn't be re-walked ten times -- confirmed cheap via memoization in the survey, see Cost below). It is **not**, by itself, sufficient for *cycle detection* during a single walk the way `inherit.rs` needs, because supertype graphs in practice are DAGs-with-accidental-cycles (a cycle is always a user error to guard against, never intended), whereas call graphs have *legitimate* cycles (the `fflib_Criteria` example above is correct, working code). The distinction that matters: `flatten`'s single visited-set answers "have I ever seen this node," which is enough to terminate a walk safely, but a call-graph walk that wants to also report *chain depth* (as this ticket's one-hop-vs-transitive question needs) benefits from the stronger 3-state on-stack/done DFS shape used in the survey script, so a real back-edge (a true cycle) can be told apart from ordinary re-convergence (a diamond, or two loops calling the same shared helper).

### Virtual/interface dispatch ambiguity

Ambiguous, dispatch-widened resolution is not a rare edge case inside loop bodies specifically: of 2,973 call-site resolutions inside loops that name at least one project-local `Method`/`Constructor`, 237 (8.0%) are `Resolution::Candidates` rather than a single `Resolution::Resolved` (2,736 resolved cleanly). `call_hierarchy.rs`'s own outgoing-calls already picked a policy for this exact ambiguity in a closely analogous feature (`crates/apex-binder/src/call_hierarchy.rs:11-20,80-84`): fan out to *every* candidate rather than guessing one, matching how `references`/`documentHighlight` already treat `Resolution::Candidates` project-wide. Given:

- This precedent already exists and is exercised safely (the `outgoing_calls`/`incoming_calls` NPSP corpus sweep test, `crates/apex-binder/src/call_hierarchy.rs:172-196`, runs it across the whole real corpus without incident),
- and the `registerEmptyRecycleBin` example above shows a `Candidates` set can include a container/mock class's or interface's *unrelated* same-named declaration alongside the real target, so "every candidate contains DML/SOQL" (the safest option) would likely under-fire, while "resolved-only, skip Candidates entirely" would silently drop 8% of otherwise-tainted call sites inside loops --

the fact-finding here does not settle which policy ticket 12 should pick (that's explicitly ticket 12's job, per this ticket's scope), but it does establish that *whichever* policy is chosen, it will materially matter: 8% of in-loop local calls hit this case, not a negligible corner.

### Cost

Timed against the full real NPSP corpus (release build, this dev machine -- absolute numbers are illustrative, not portable, but the *relative* costs are the useful signal):

- Cold parse + bind of the whole corpus (`BoundProgram::from_files`, the existing Pass 1 / Pass 1.5 / Pass 2 pipeline): **311 ms**.
- Computing "does this callable's body directly contain DML/SOQL" for all 12,351 callables (the leaf fact any transitive computation bottoms out on): **142 ms**.
- Scanning all 3,083 loops and running the cycle-guarded, memoized BFS (up to depth 9) from every loop's locally-called targets: **128 ms**.
- A full project-wide cycle census (3-state DFS over all 12,351 callables' `outgoing_calls`): **34 ms**.

So the whole survey -- direct-DML fact for every callable, plus full transitive BFS for every loop, plus a whole-project cycle census -- adds roughly **300 ms on top of a 311 ms cold bind**, i.e. it's the same order of magnitude as binding itself, not negligible but not prohibitive either, for a *from-scratch whole-project* computation with no caching at all beyond per-run memoization.

That points toward this needing to be a **real new pass, not a naive per-query lazy computation**, for two reasons found here, not assumed:

1. **Dependency ordering**: unlike Pass 1.5's `inherited_chain` (which only needs Pass 1's raw `extends`/`implements` names, collected file-by-file before any cross-file resolution), a transitive "contains DML/SOQL" fact needs `Resolution` data (`Resolution::Resolved`/`Candidates` on every call site) -- which only exists after Pass 2 has already run project-wide (`crates/apex-binder/src/lib.rs:3`, `:228` doc comments on the three-pass structure). So this is necessarily a **Pass 3**, sequenced strictly after Pass 2 completes, not foldable into an earlier pass the way Pass 1.5 is.
2. **Incremental invalidation is the real cost driver, not the cold-compute numbers above.** Pass 2 already reruns for *every* file whenever *any* file's declarations change, conservatively (`crates/apex-binder/src/lib.rs:228-233`'s own documented tradeoff) -- but a method *body* edit alone (the single most common edit in an editor session: typing inside a method) never triggers that rerun today, only Pass 2 for the dirty file itself. A transitive DML/SOQL fact is different in kind: it is defined by *body content* (whether a DML/SOQL statement is present, directly or via a callee), so an edit inside *any* single leaf utility method's body can flip its "contains DML/SOQL" bit and therefore must invalidate that fact for every transitive caller project-wide (not just the edited file) -- a reverse-reachability propagation this project's existing per-file dirty-tracking (`crates/apex-binder/src/incremental.rs`) has no analog for today. Computing this fact lazily, per diagnostics pass, without a cached/invalidated whole-project index would mean redoing (at minimum) the 142 ms leaf-fact pass every time *any* method body changes anywhere in the project -- workable for a manual/on-demand check, but the wrong shape for `publish_diagnostics`' existing on-every-keystroke-in-an-open-file model (`crates/apexls-server/src/lib.rs:556-577`).

**Reusable machinery, confirmed rather than assumed needed from scratch**: `apex_binder::outgoing_calls` (`crates/apex-binder/src/call_hierarchy.rs:76-96`, already `pub use`d from the crate root) is sufficient, unmodified, to build the entire call-graph traversal this ticket investigated -- the survey script called it directly with no new low-level primitive. What's missing today is only the higher-level per-callable "contains DML/SOQL, transitively" fact and its cycle-guarded computation/caching, not a call-graph primitive itself.
