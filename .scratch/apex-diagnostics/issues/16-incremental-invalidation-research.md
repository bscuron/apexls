Status: resolved

## Question

Investigate how `apex-binder` could incrementally invalidate a whole-project fact that's defined by a method's *body content* rather than its declaration -- the specific gap [ticket 12](12-cross-method-bulkification-decision.md) found blocking cross-method bulkification detection, but stated generally since the same shape of fact would block any future transitive/interprocedural analysis this binder ever wants to add (not just this one diagnostic).

Context: `apex-binder`'s existing three-pass structure (Collect/Inherit/Resolve) and its incremental rebuild (`crates/apex-binder/src/incremental.rs`) both key invalidation on *declarations* -- Pass 2 conservatively reruns for every file whenever any file's declarations change (`crates/apex-binder/src/lib.rs:228-233`'s own documented tradeoff), and a body-only edit inside one file today only reruns Pass 2 for that one file. A transitive "does this callable's body, directly or via any callee, contain DML/SOQL" fact breaks that model: editing a single leaf utility method's body can flip its own bit, which must then propagate to invalidate every transitive caller project-wide -- a reverse-reachability problem with no existing analog in this codebase.

Establish, concretely:
- Is there a real, standard technique for this (e.g. a memoized/incremental call-graph library or algorithm from another language-server implementation, a well-known "salsa"-style incremental-computation pattern, or a simpler bespoke approach specific to this binder's own shape) that keeps the common case (editing one method body) cheap, rather than reverting to a full-project recompute on every keystroke?
- Does `apex_binder::outgoing_calls`/`incoming_calls` (`call_hierarchy.rs`) already carry (or could cheaply carry) enough reverse-edge information to make "who transitively calls this method" a fast, incremental query rather than a fresh whole-project walk each time?
- What's the actual real-world edit-locality pattern worth optimizing for -- do most real edits in a session touch leaf methods with shallow caller fan-in (cheap to invalidate), or is there a realistic worst case (a widely-called low-level utility method) where even a "smart" incremental approach degrades to something close to a full recompute? Sample the real NPSP corpus's own call graph (already surveyed once in ticket 11, branch since merged) for caller fan-in distribution to ground this rather than guessing.
- Would solving this generally (a reusable "transitive fact with incremental invalidation" primitive) versus solving it narrowly (just for the DML/SOQL-taint bit this one diagnostic needs) change the shape of the answer -- is the general version meaningfully harder, or does the narrow version already require solving the same core problem anyway?

This ticket is fact-finding only -- it does not decide the architecture. Its findings would feed a future architecture-decision ticket, should cross-method bulkification (or any other transitive analysis) be reopened.

## Answer

### 1. Is there a real, standard technique for this?

Yes, two, and they're really the same idea at different levels of commitment.

**`salsa` (rust-analyzer's incremental-computation framework)** is the directly relevant, real prior art the ticket asked to check. Its "red-green" algorithm ([salsa-rs.github.io/salsa/reference/algorithm.html](https://salsa-rs.github.io/salsa/reference/algorithm.html)) is **demand-driven and pull-based, not push-based**: nothing eagerly walks reverse edges when an input changes. Instead every memoized query stores (a) its cached value, (b) the set of other queries it read, and (c) the revision each of those was last *observed to actually change* in. On the next request for a query's value, salsa walks that query's own recorded dependencies forward and asks each "did you change since my last read?" -- recursively, lazily, only for queries someone actually asks about again. Two optimizations make this cheap in practice: **early cutoff/backdating** (if a query re-executes because an input changed but its own output is bit-for-bit identical to before, it reports "unchanged" upward, so the query that depends on it never even has to re-execute), and **durability** (queries can be tagged by how often their inputs actually change, letting a whole durability class be skipped without per-query checking). rust-analyzer's own write-up ([rust-analyzer.github.io/blog/2023/07/24/durable-incrementality.html](https://rust-analyzer.github.io/blog/2023/07/24/durable-incrementality.html)) frames the whole discipline as designing queries so a stable intermediate layer (e.g. a signature) "shields" everything above it from a change to something below (e.g. a body) that didn't actually affect the shielding layer's output.

Mapped onto this exact problem: a per-callable memoized query `transitively_has_dml(method_id) -> bool`, defined as `has_dml_directly(method) || outgoing_calls(method).any(|callee| transitively_has_dml(callee))`, is *precisely* a salsa-shaped incremental query with early cutoff for free -- editing one leaf method's body only forces recomputation of queries that actually read that method's now-stale memo, and if the boolean doesn't flip, nothing above it ever reruns. This is not a hypothetical fit; it is the textbook shape salsa exists for (rust-analyzer's own type-inference-per-function queries are structured exactly this way for the same "body edit shouldn't invalidate unrelated bodies" reason).

**The bespoke alternative** (no salsa, no query database) is the worklist/fixpoint propagation algorithm from incremental interprocedural dataflow analysis: maintain a persistent reverse call-edge map and a persistent per-callable fact cache; on an edit, recompute the fact for the directly-changed callable(s), and only if a fact's value actually flips, push its *callers* (via the reverse edges) onto a worklist and repeat, stopping the moment a propagation step produces no change (the same early-cutoff idea, applied by hand). This is the standard "incremental dependency analysis" pattern in the literature (worklist-driven solvers record fine-grained dependency relations so only the transitive closure of *actually* affected facts gets redirtied and recomputed, per the general incremental-dataflow/Datalog-semi-naive-evaluation family of techniques) -- not something this ticket had to invent from scratch, just something this codebase would have to build by hand rather than getting from a framework.

Given this binder's actual architecture (rowan CST, no query database, a bespoke three-pass pipeline that already does its own manual per-file cache-patching in `BindCache`), adopting real `salsa` wholesale would be a large structural rewrite; the bespoke worklist variant is the smaller, architecture-consistent version of the *same* underlying algorithm, and is what section 4 below assumes as the concrete shape.

### 2. Does `outgoing_calls`/`incoming_calls` already carry enough reverse-edge info?

Partially, and in a way worth being precise about. `incoming_calls` (`crates/apex-binder/src/call_hierarchy.rs:55`) is already efficient *per query*: it calls `BoundProgram::references_to(target)` (`crates/apex-binder/src/lib.rs:1047`), which is backed by `ReferenceTable::by_symbol: FxHashMap<SymbolId, Vec<SyntaxPtr>>` (`crates/apex-binder/src/reference_table.rs:309`) -- already indexed by target symbol, so asking "who calls this one method" is O(references to that method), never O(all references in the project). There is no need to build a new low-level index to make a *single* incoming-calls lookup cheap; that part was already true before this ticket.

What does **not** exist yet is a *persisted, project-wide reverse call-edge map* that a worklist could walk without re-deriving it. Today, `incoming_calls`/`outgoing_calls` are computed fresh from whatever `BoundProgram` snapshot is handed in (the module doc comment says as much: "Computed entirely on demand per request... no need for a precomputed whole-project call graph"), and a `BoundProgram`'s reference data (`bodies: FxHashMap<FileId, Arc<FileBodies>>`) is itself only ever fully assembled by walking every file's Pass 2 output -- exactly as expensive to do project-wide as Pass 2's own body walk already is. Building a full reverse-edge map once would cost one linear pass over that same data (cheap relative to producing it in the first place), and -- this is the part that answers "could it cheaply carry this incrementally" -- it could be persisted and patched file-by-file in `BindCache` using the *exact same discipline* already used for `bodies`/`raw_extends`/`raw_super`/`supertype_ptrs` (`crates/apex-binder/src/incremental.rs:163-172`): each file's Pass 2 rerun already knows every call site's resolved target inside that file, so it could just as cheaply record `(caller_id, callee_id)` edges local to that file, merged into one project-wide reverse map, and only recomputed for the dirty files Pass 2 already reruns for. No new low-level machinery is needed -- it is the same per-file-patch pattern this crate already leans on everywhere else, applied to one more derived structure.

### 3. Real-world edit-locality: NPSP corpus caller fan-in distribution

Sampled directly against the real, checked-out NPSP corpus (`tests/corpus/npsp/`, matching ticket 11's own `BoundProgram::from_files` method, via a throwaway test iterating `incoming_calls` over every callable and deleted before this commit):

- **12,351** total callables (methods + constructors) project-wide.
- **39.0%** (4,818) have **zero** callers project-wide (dead/unreached by this binder's reference resolution, external entry points like `@AuraEnabled`/trigger handlers/test methods, or genuinely unreachable code).
- Fan-in percentiles: **p50 = 1, p75 = 2, p90 = 5, p95 = 10, p99 = 44**.
- **90.3%** of all callables have **5 or fewer** distinct project-wide callers; **95.4%** have 10 or fewer.
- **Max fan-in = 500**, for a test-data-factory-style method named `build`. The rest of the top of the tail is the same shape: `setRecurringDonations2Enabled` (448), `useAdv` (314), `getClosedWonStage` (219), `getContactsSettingsForTests` (193), `mock`/`mockId` (190/172, `fflib_ApexMocks`-style test mocking helpers), several overloaded `add`/`withContact`-style builder methods (~130 each) -- i.e. exactly the shared test-fixture-builder and settings-accessor methods a large enterprise Apex codebase would be expected to concentrate high fan-in in, not typical business-logic methods.

This grounds a real, two-part answer rather than a guess: **the common case is cheap** -- the median edited method has exactly one caller, and 9 in 10 have five or fewer, so a worklist propagation from a body edit touches a handful of nodes in the overwhelming majority of real edits. But **a real, non-hypothetical worst case exists**: a small number of widely-shared low-level utility/test-factory methods (the top ~15 all sit at 130-500 callers) where a body edit's initial fact recomputation must at least *visit* (not necessarily fully recompute, thanks to early cutoff -- see section 1) every direct caller, and potentially their callers transitively if the fact actually flips. A "smart" incremental approach does not degrade to a *full-project* recompute even in this worst case (500 direct callers is ~4% of all callables, not 100%, and each visit is a cheap boolean re-check with early cutoff, not a re-derivation of the callable's Pass-2-scale semantic body walk) -- but it is honestly the one case where the win over "just recompute all callers of the edited method" narrows.

### 4. General primitive vs. narrow (DML/SOQL-only) solution

Solving this narrowly already requires solving the same core problem in full -- there is no meaningfully smaller version of "just the DML/SOQL bit." Whichever technique from section 1 is chosen, the diagnostic-specific instantiation still needs all of:

- A **persistent per-callable fact cache**, keyed the same way `bodies`/`raw_extends` already are (by `FileId`/`SymbolId`), not recomputed from nothing every call.
- **Reverse call edges** (section 2) to know who to re-examine when a fact changes -- this is not DML/SOQL-specific in any way; it's pure call-graph structure.
- **Worklist/fixpoint propagation with early cutoff** -- stopping propagation the moment a step produces no change is what keeps the common case (section 3's median-fan-in-1 method) cheap; this logic has nothing DML/SOQL-specific in it either.
- **Cycle handling.** Apex permits recursive and mutually recursive calls, so "does this method's body, directly or via any callee, contain DML/SOQL" is not well-defined by a simple topological walk over the call graph -- it requires either an SCC decomposition (Tarjan) with a fixpoint iteration within each strongly-connected component, or an equivalent cycle-safe formulation. This is exactly the kind of wrinkle real incremental-query frameworks build in explicitly (salsa has first-class support for cyclic queries for this reason) and a bespoke implementation cannot skip.

None of that machinery reads or cares what the fact *is*. The only DML/SOQL-specific code in the whole system would be the one-line base case ("does this callable's own body directly contain a DML statement or inline SOQL/SOSL query") and the boolean combine (`own || any(callee)`). Generalizing further -- to a reusable "transitive fact with incremental invalidation" primitive usable by some future, not-yet-designed transitive analysis -- costs only slightly more: the fact's value type would need to move from a hardcoded `bool` to something with a defined equality (for early cutoff to detect "did this actually change") and a defined per-callable combine function over its callees' values (monotone booleans are the easiest case; a richer fact, e.g. a *set* of DML object types touched, still fits the same shape as long as it has an equality check and a combine). That generalization is a modest type-level abstraction over the same reverse-edge-plus-worklist-plus-cycle-handling core, not a harder problem -- so if this is ever built, building the general version first and instantiating it once for DML/SOQL costs little over building the narrow version directly, and avoids having to redo the reverse-edge/worklist/cycle-handling machinery from scratch for the next transitive analysis this binder eventually wants.
