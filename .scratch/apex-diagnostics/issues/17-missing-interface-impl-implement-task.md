## Question

Implement the project-local-only missing-interface/abstract-method-implementation diagnostic exactly as settled in [ticket 07's Answer](07-missing-interface-impl-implement.md):

- For every concrete (non-abstract) project-local class, walk `inherited_chain(class_id)` and, for each ancestor, collect every method that's "required" (`is_abstract || container.kind == SymbolKind::Interface`, per [ticket 06](06-missing-interface-impl-research.md)'s own finding that interface methods are implicitly abstract without the modifier bit ever being set).
- For each required method, check whether it's satisfied:
  - Declared on an ancestor `Interface`: satisfied by any project-local method at or below that point in the chain with the same name (case-insensitive) and arity, regardless of `override`.
  - Declared on an ancestor abstract `Class`: satisfied only by one carrying `modifiers.is_override == true`.
- A required method with no satisfying override anywhere in the chain -> flag the concrete class itself (not the ancestor) with a diagnostic naming the missing method and which ancestor requires it.
- Method-level dedup across multiple interfaces requiring the same name+arity signature (e.g. two interfaces both requiring `void run()`) should fall out naturally from keying "still missing" by name+arity, not per-ancestor -- satisfying it once satisfies both.

Severity: this is a certain, provable defect once flagged (a concrete class genuinely fails to satisfy its declared contract) -- `ERROR`, matching `unknown_schema_diagnostics`/`modifier_diagnostics`/`unreachable_code_diagnostics`'s confidence level, not `WARNING`.

Definition of done: wired into the merged `publish_diagnostics`; tests covering a class missing a project-local interface method, a class missing a project-local abstract-class method (both with and without an intervening abstract subclass that legitimately doesn't implement it), the interface-vs-abstract-class `override`-requirement asymmetry (a same-name/same-arity method with no `override` correctly satisfies an interface requirement but does *not* satisfy an abstract-class requirement), the multi-interface same-signature dedup case, a class implementing a stdlib interface (`Comparable`, etc. -- must NOT be flagged at all, since it's silently invisible to `inherited_chain` today and flagging it would be a false positive against a case this scope explicitly excludes), and a real-NPSP-corpus zero-false-positive sanity pass (matching every other diagnostic on this map).

## Answer

Implemented as `apexls_server::capabilities::missing_implementation_diagnostics`, wired into the merged `publish_diagnostics` alongside the seven existing sources, `ERROR` severity. Bridges from the syntax tree to the symbol table via `BoundProgram::symbol_at` (a `ClassDecl`'s name-token offset -> its `SymbolId`) -- the first diagnostic on this map to need real symbol-table data (`inherited_chain`/`members_of`/`params`) rather than just the raw syntax tree, since `symbols_of_file` itself is `pub(crate)`-only inside `apex-binder`.

**A real false positive found and fixed by the mandatory NPSP corpus check, not foreseen at design time:** the initial implementation (requiring `is_override` for every abstract-superclass requirement, per ticket 07's own settled rule) flagged 16 diagnostics across the corpus, all against `fflib_SObjectSelector`'s `getSObjectType`/`getSObjectFieldList`. Investigation showed real, shipped `fflib_AppBindingsSelector` and three other real classes override both methods correctly with no `override` keyword at all. Verified directly against a real connected org (two minimal deploys, matching this project's established `sf` CLI oracle practice): an abstract method declared with an **explicit** visibility modifier (`public abstract String run();`) does require `override` on its satisfying method (confirmed: omitting it produces *both* "must implement the abstract method" and "must use the override keyword" errors simultaneously) -- but the **identical shape with no visibility modifier at all** (`abstract String run();`, `fflib_SObjectSelector`'s own real shape) deploys cleanly with no `override` keyword whatsoever. Fixed by keying `needs_override` on the abstract declaration's own visibility being explicit (`!= Visibility::Private`) rather than unconditionally on "declared on a class, not an interface" -- `ModifierSet`'s own `Visibility::default()` is already `Private`, exactly the value an unmodified declaration collapses to, so this reuses an existing signal rather than adding a new one. Ticket 06's own research (which only cited `dynamic_dispatch_resolution.rs`'s existing fixtures, all using explicit modifiers) didn't surface this distinction -- a real gap in that earlier research, closed here empirically rather than assumed.

Tests: `crates/apexls-server/tests/missing_implementation_diagnostics.rs` -- 10 cases covering a missing interface method, a missing abstract method (explicit-modifier shape), the override-vs-no-override asymmetry for both directions, the no-explicit-visibility exception (the real NPSP shape that triggered the fix above), partial implementation via an intermediate abstract subclass, multi-interface same-signature dedup, a stdlib interface (never flagged, out of scope), and an abstract class itself never being flagged. All pass. Zero-false-positive sanity check against the **entire** real NPSP corpus (1,035 files) via a throwaway example harness (built, run, deleted): zero diagnostics, down from the initial 16 before the fix above. Full `apexls-server` suite passes.
