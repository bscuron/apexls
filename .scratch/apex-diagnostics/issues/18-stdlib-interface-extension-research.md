Type: research
Status: resolved

## Question

Investigate what extending the missing-implementation diagnostic (ticket 17, `apexls_server::capabilities`'s not-yet-built project-local-only "does this concrete class implement every abstract/interface method its supertype chain requires" check) to cover standard-library interfaces (`Comparable`, `Iterator`, `Database.Batchable`, `Queueable`, `Schedulable`, `Messaging.InboundEmailHandler`, `StubProvider`, ...) would actually require, per ticket 06's own recommendation that this needs genuinely new `apex-binder`-core capability, not just new diagnostic code. Establish, concretely:

- **The `SymbolTable`/`resolve_inheritance` change.** Today only a class's single direct `extends` name has a "did this resolve" signal (`unresolved_direct_super`); every `implements` name, and every non-direct ancestor further up an `extends` chain, is silently dropped with zero record (`inherit.rs:51-55`'s own documented behavior). What's the minimal, real change to `resolve_inheritance`/`SymbolTable` needed to record *which* raw `implements`/`extends` names failed to resolve, per type, without regressing `inherit.rs`'s existing incremental-rebuild story (`crates/apex-binder/src/incremental.rs`'s `BindCache`, which already holds `raw_extends` privately for cheap re-runs -- can this newly-needed signal reuse that existing plumbing, or does it need its own?).
- **The stdlib cross-reference lookup.** `apex-stdlib`'s raw scraped JSON (`crates/apex-stdlib/data/apex_reference.json`) does carry each interface's method list (confirmed for `Comparable`/`Iterator` in ticket 06's own research). What's the concrete lookup path from "this class's `implements` clause names X, which didn't resolve as a project-local type" to "X is a known stdlib interface with these required methods" -- does `apex_binder::stdlib_index::StdlibIndex` already expose enough to do this cheaply, or does it need a new accessor?
- **Real-world frequency.** Sample the real NPSP corpus: how many project-local classes implement a standard-library interface at all, and of those, how many would this check actually have real signal on (i.e., how often would a genuine missing-method bug be catchable, versus every real implementation already being complete -- confirming whether this is worth building at all, similar to how ticket 11's real-data sampling informed the bulkification cross-method decision).
- **Multiple-interface signature collisions specific to stdlib interfaces.** Does any real stdlib interface share a method name/arity with another in a way that could create an ambiguous "which interface's requirement does this satisfy" situation, or does Apex's own interface design avoid this in practice (worth checking a handful of the most commonly-implemented stdlib interfaces directly against the raw JSON rather than assuming).

This ticket is fact-finding only -- it does not decide the architecture. Its findings would feed a future architecture-decision ticket, mirroring ticket 11 -> ticket 12's shape.

## Answer

### 1. The `SymbolTable`/`resolve_inheritance` change

`inherit.rs:56-63` already computes exactly the residue we need and throws it away. The `direct` map is built with:

```rust
let resolved = names.iter().filter_map(|n| table.resolve_dotted_name_from(n, from)).collect();
```

`filter_map` silently drops every name whose `resolve_dotted_name_from` call returned `None` -- there is no side channel today. The minimal change is to widen that closure to also push the rejected name into a per-type `Vec<SmolStr>` alongside the resolved-id vec (a `partition`/manual-loop instead of `filter_map`), then, after the loop, call a new `SymbolTable::set_unresolved_supertypes(type_id, Vec<SmolStr>)` mirroring the existing `set_unresolved_direct_super` (`symbol_table.rs:366-370`) and its own accessor pattern (`symbol_table.rs:377-379`). The new field lives in `Indices` right next to `unresolved_direct_super` (`symbol_table.rs:118-135`).

Two real wrinkles this ticket's own framing undersells:

- **`raw_extends` conflates `extends` and `implements` into one untagged `Vec<SmolStr>`.** `collect.rs:200-213` pushes a class's own `extends` name (if any) *first*, then every `implements` name, into the *same* `supertypes` vec that becomes one `raw_extends` entry -- there is no per-name tag saying which clause a given string came from. For an `InterfaceDecl` (`collect.rs:224-236`), by contrast, every name in `raw_extends` came from `extends` (interfaces don't have `implements`). So "which raw names are implements names" is only recoverable today by *position* for a class (index 0 is `extends` when `class.extends().is_some()`, everything after is `implements`) -- fragile, undocumented, and easy to get wrong. A real implementation should not lean on that; either (a) tag each name at collection time (`collect.rs`) with its clause origin, e.g. `Vec<(SmolStr, SupertypeKind)>` instead of `Vec<SmolStr>`, or (b) simply subtract the class's own already-known `extends` name (available separately via `raw_super`/`direct_super`/`unresolved_direct_super`) from the unresolved set before recording it as "unresolved implements." Option (a) is the more honest fix and costs one new enum plus a one-line collect.rs change per call site (3 call sites: `collect_class`, `collect_interface`, and wherever `enum`/`trigger` might someday grow supertypes -- currently none do).
- **A class implementing its own nested interface doesn't resolve *today*, in production, not just in a hypothetical survey.** `resolve_inheritance` calls `resolve_dotted_name_from(name, table.get(type_id).container)` -- for a *top-level* class, `container` is `None`, so nothing about the class's *own* nested members is ever consulted. Real NPSP hits this: `fflib_Inheritor implements IA, IB, IC` where `IA`/`IB`/`IC` are declared as members of `fflib_Inheritor` itself (`tests/corpus/npsp/force-app/infrastructure/apex-mocks/main/classes/fflib_Inheritor.cls:5-9`), and `fflib_Criteria implements Evaluator` / `fflib_MyList implements IList` are the same self-referencing-own-nested-interface shape. These are today indistinguishable, via `unresolved_direct_super`'s existing single-slot mechanism or the new multi-slot one, from a genuine unresolvable name -- a false positive the new diagnostic would inherit unless `resolve_dotted_name_from` (or a caller-side check) is taught to also try the type's own nested types, not just its container's. Small in volume (3 distinct names / 3 sites across all of NPSP) but real, and worth fixing in the same pass as this ticket's own change since it shares the exact code path.

**`BindCache` reuse**: no new cache field is needed on the *input* side. `raw_extends`/`raw_super` are already persisted per-file (`incremental.rs:156-164`) and *already* get fed to `resolve_inheritance` in full whenever any file's declarations change (`incremental.rs:159-162`'s own doc comment: "every entry across every file is still fed to `resolve_inheritance` together whenever *any* file's declarations changed"). The new *output* (the unresolved-implements map) lives inside `SymbolTable`'s `Indices`, exactly like `unresolved_direct_super` does today -- and `SymbolTable` itself (`BindCache.table`, `incremental.rs:152-155`) is already the unit that gets wholesale-replaced by a fresh `resolve_inheritance` pass on any change, not something patched field-by-field the way `parses`/`bodies` are. So this needs zero new `BindCache` plumbing: it rides the exact same "whole-project, cheap enough to always redo" story `inherited_chain`/`direct_super`/`unresolved_direct_super` already ride.

### 2. The stdlib cross-reference lookup

`StdlibIndex::class(name: &str)` (`stdlib_index.rs:40-47`) takes a *bare* name and looks it up case-insensitively -- it does not exist for a dotted/namespaced string. Confirmed directly: of the 25 distinct unresolved `implements` names found in the NPSP survey (below), the namespace-qualified spellings (`Database.Batchable`, `Database.Stateful`, `System.StubProvider`, `System.Queueable`, `Metadata.DeployCallback`, even the differently-cased `database.batchable` and `Metadata.DeployCallBack`) all return `class(name) == None` when passed the *whole* dotted string, even though the bare tail (`Batchable`, `StubProvider`, `Queueable`, `DeployCallback`) resolves fine. So a real caller needs to split the trailing segment off first (the same "last segment is the simple name" logic `Type::base_name_tokens()` already isolates for a live AST node, or a plain `name.rsplit('.').next()`) and call `class_in_namespace(namespace, tail)` (`stdlib_index.rs:59-65`) when a namespace prefix is present, falling back to `class(tail)` otherwise. `StdlibIndex` already has both accessors needed; **no new accessor is required for name lookup**.

What *is* missing: **`StdlibClass` drops `kind` entirely.** `RawClass` (the private deserialization struct, `apex-stdlib/src/lib.rs:137-145`) has `kind: String` (`"Class"` / `"Interface"` / `"Enum"`), but `to_stdlib_class` (`apex-stdlib/src/lib.rs:230-234` on) never copies it into the public `StdlibClass` struct (`apex-stdlib/src/lib.rs:87-96`, no `kind` field at all). So today there is **no way**, via the public `apex_stdlib`/`apex_binder::stdlib_index` API, to ask "is `X` a stdlib *interface*" as opposed to a stdlib *class* or *enum*. That distinction matters for this diagnostic specifically: implementing an abstract *class* (which can have concrete/default method bodies) is a different, non-"every method required" contract than implementing an *interface*. Building this diagnostic correctly requires adding a `pub kind: StdlibClassKind` (or similar) field to `StdlibClass`, threaded through from `RawClass::kind` in `to_stdlib_class` -- a small, mechanical change, but a real one, not free.

### 3. Real-world frequency (NPSP corpus survey)

Surveyed via a throwaway test (`BoundProgram::from_files` over `tests/corpus/npsp`, walking every `SymbolKind::Class` symbol's `ClassDecl.implements()` clause and resolving each named type with the *exact* call `resolve_inheritance` itself makes -- `table.resolve_dotted_name_from(name, symbol.container)` -- not a naive global lookup, which would falsely flag every sibling/nested project-local interface as "unresolved"; deleted before this commit, per the ticket's instructions). Results:

- **324** project classes have an `implements` clause at all, naming **372** interface references in total (some classes implement more than one).
- **207** of those 372 references fail to resolve as a project-local type.
- Of the 25 *distinct* unresolved names, only 5 sites (`IA`, `IB`, `IC`, `Evaluator`, `IList` -- 1 implementer each) are the self-referencing-own-nested-interface false positive described above, not real stdlib candidates.
- The remaining **202 sites**, across **121 of the 324 classes with any implements clause (37%)**, name a real standard-library interface. By implementer count, the most common are: `StubProvider`/`System.StubProvider` combined (**76** implementers -- ApexMocks-style test stubs), `Database.Batchable`/`database.batchable` (**38**), `Schedulable` (**27**), `Database.Stateful` (**20**), `Queueable`/`System.Queueable` (**14**), `Database.AllowsCallouts` (**5**), `HttpCalloutMock` (**5**), `Comparable` (**4**), `Metadata.DeployCallback`/`DeployCallBack` (**4**), `System.Callable` (**3**), plus single implementers of `Database.BatchableContext`, `System.FinalizerContext`, `Cache.CacheBuilder`, `InstallHandler`, `UninstallHandler`, and `Finalizer`.
- **Two of the ticket's own named example interfaces have real, concrete data gaps.** `Messaging.InboundEmailHandler` (named directly in this ticket's own Question) does not appear *anywhere* in `apex_reference.json` -- confirmed by a direct case-insensitive text search for both `InboundEmailHandler` and `handleInboundEmail`, zero hits. And two of the *most-implemented* interfaces in the real NPSP data, `Database.Stateful` (20 implementers) and `Database.AllowsCallouts` (5 implementers), are also entirely absent from the raw JSON -- not merely filtered out by `standard_classes()`'s empty-methods filter (`apex-stdlib/src/lib.rs:221-224`), but never scraped as their own entries at all (these are real, zero-method Apex marker interfaces, likely without their own doc page for the scraper to find). Any version of this diagnostic built today would have **zero signal** on `Messaging.InboundEmailHandler`, `Database.Stateful`, or `Database.AllowsCallouts` -- three of the interfaces this ticket itself expected to cover, accounting for 25 real implementer sites (20 + 5, plus the ticket's own named example) that a naive "check against bundled stdlib JSON" implementation would silently skip or misreport as "not a known interface."
- **Whether a genuine missing-method bug is actually catchable this way is structurally limited, independent of any implementation quality.** All 121 implementer classes sampled are real, already-deployed NPSP production code (confirmed by spot-check: `STG_InstallScript implements InstallHandler` genuinely defines `global void onInstall(InstallContext context)` at `STG_InstallScript.cls:66`, matching the interface exactly). The Apex compiler *already* rejects a class at deploy time if it doesn't implement every method a *real* interface -- stdlib or project-local -- requires; a corpus of successfully-deployed code can therefore never contain a genuine "missing stdlib interface method" bug, by construction. This is unlike ticket 11's bulkification survey, where the platform doesn't reject the anti-pattern at compile time, so a real corpus genuinely can (and did) surface live instances. Here, the diagnostic's entire value is catching a *transient, mid-edit* state -- e.g., a developer types `implements Queueable` and hasn't yet written `execute(...)` -- which by definition cannot appear in any git-committed, already-compiling corpus. So "sample NPSP for a real gap" cannot itself validate or invalidate this diagnostic's usefulness the way it did for ticket 11/12; the only honest evidence this survey can offer is the *frequency* number above (121/324 classes, so real signal *opportunity* is common), not a "found N real bugs" count.

### 4. Multiple-interface signature collisions

Checked the method sets of the most commonly-implemented interfaces above directly against the raw JSON (not inferred):

| Interface | Method | Params | Return |
|---|---|---|---|
| `Schedulable` | `execute` | `(System.SchedulableContext)` | `Void` |
| `Queueable` | `execute` | `(QueueableContext)` | `void` |
| `Finalizer` | `execute` | `(FinalizerContext)` | `void` |

**A real, same-name/same-arity collision exists**: three different, commonly-implemented stdlib interfaces each require a one-argument method literally named `execute`, differing only in parameter *type*. Apex allows this legitimately (overloading by parameter type is normal), but it means a correct diagnostic **cannot** use arity alone (this project's own established "arity alone is authoritative" rule for *user-defined* overload resolution, per `resolution_consistency.rs`'s module doc comment) to decide which interface's requirement a given concrete `execute` method satisfies -- it must compare the declared parameter *type* against each candidate interface's required parameter type. `StubProvider`/`Comparable`/`Iterator`/`Batchable`/`Callable`/`CacheBuilder`/`DeployCallback`/`HttpCalloutMock`/`InstallHandler`/`UninstallHandler` were also checked and have no cross-interface name collisions among themselves. Separately (not a cross-interface collision, but a same-interface wrinkle worth flagging): `Database.Batchable` itself has *two* scraped `start` overloads with the same name/arity but different return types (`System.Iterable` vs `Database.QueryLocator`) -- documentation of "either return type is acceptable," not two independent requirements, so the diagnostic must treat that pair as satisfied-by-either rather than requiring both.

No class in the current NPSP corpus actually implements two of `{Queueable, Schedulable, Finalizer}` together (checked via a direct grep for `implements` clauses naming two of the three) -- the collision is real and present in the *data*, but not yet observed as a live co-implementation in this corpus. A future implementation should still handle it correctly rather than assume it away, since Apex's own design doesn't prevent it.

### Summary

Building this out is a real, multi-part `apex-binder`-core change, not just new diagnostic code, confirming ticket 06's own framing: (1) `resolve_inheritance`/`SymbolTable` need a new per-type "which raw names failed to resolve" signal, ideally with clause-origin tagging fixed at collection time rather than inferred positionally, plus a fix for the self-referencing-nested-interface false positive it would otherwise inherit; (2) `apex_stdlib::StdlibClass` needs a `kind` field restored from the raw data it already has but currently discards, to distinguish "interface" (every method required) from "class" (default bodies allowed); (3) the bundled `apex_reference.json` snapshot itself has real, concrete holes -- `Messaging.InboundEmailHandler`, `Database.Stateful`, and `Database.AllowsCallouts` are entirely unscraped, together accounting for a large fraction (25 of 202) of the real candidate implementer sites in NPSP, so shipping this diagnostic without first patching the stdlib snapshot would misfire on some of the most commonly-implemented real interfaces; and (4) overload matching for the diagnostic must compare parameter types, not arity alone, because `Schedulable`/`Queueable`/`Finalizer` genuinely collide on `execute`'s name and arity. On frequency: 121 of 324 (37%) NPSP classes with any `implements` clause name a real stdlib interface, so the *opportunity* for this check to fire is common -- but because Apex's compiler already rejects incomplete real-interface implementations at deploy time, no already-deployed corpus (NPSP included) can ever demonstrate a genuine caught bug; this diagnostic's value is inherently about catching a mid-edit, not-yet-compiling state, which sampling a committed corpus cannot validate one way or the other.
