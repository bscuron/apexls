## Question

Investigate the concrete mechanics of adopting the real `salsa` crate as `apex-binder`'s incremental-computation engine, per [ticket 19](19-incremental-invalidation-decision.md)'s decision. Ticket 16 already established *why* salsa's algorithmic shape fits this problem (demand-driven memoization with early cutoff); this ticket is about *how it would actually integrate with this specific codebase*, which hasn't been investigated at all yet. Establish, concretely:

- **The `Send`/`Sync` question.** `crates/apex-binder/src/lib.rs:599-601` documents that `SyntaxNode` (rowan-based) is deliberately neither `Send` nor `Sync`, and the existing three-pass pipeline uses real multi-threading (`rayon`) for Pass 1/Pass 2 parallel work. What does salsa actually require of its tracked inputs/query return values regarding thread-safety, and does that conflict with storing (or referencing) rowan `SyntaxNode`/`SyntaxPtr` values inside salsa-tracked structures? If there's a real conflict, what's the resolution -- keep only owned, thread-safe data (symbol ids, text ranges, cached strings) in salsa-tracked queries and re-resolve back to the live tree only at the edges, the way `crate::ptr::SyntaxPtr` already works today?
- **Mapping the existing three-pass structure onto salsa's own vocabulary.** Salsa distinguishes inputs (external, settable data) from tracked functions (derived, memoized, invalidation-tracked computations). How would `apex-binder`'s Collect/Inherit/Resolve passes, and its existing `BindCache`/incremental-rebuild machinery (`crates/apex-binder/src/incremental.rs`), map onto that vocabulary -- is this a wholesale replacement of `BindCache`, or could salsa be adopted incrementally for a subset of the binder (e.g. only the new transitive-fact layer this whole effort was originally about) while the existing three-pass pipeline stays as-is underneath?
- **Migration path and blast radius.** Given every existing diagnostic/capability (`BoundProgram`'s full public API -- `resolution_at`, `symbol_at`, `inherited_chain`, `references_to`, all eight shipped diagnostics, hover, completion, rename, ...) currently depends on `BoundProgram`'s current shape, what would actually need to change in each consumer, versus what could stay behind a stable-looking API while the implementation swaps underneath? Is an incremental, feature-flagged, or parallel-implementation migration path realistic, or does salsa's own model force an all-at-once cutover?
- **Real-world precedent beyond rust-analyzer.** rust-analyzer is the obvious salsa consumer, but it was designed around salsa from very early on. Is there a real precedent for retrofitting salsa onto an *existing*, already-shipped incremental compiler/language-server architecture (not built with salsa from day one) that this project could learn from, including what broke or took longest during that retrofit?

This ticket is fact-finding only -- it does not decide the migration plan. Its findings would feed a future migration-plan ticket.
