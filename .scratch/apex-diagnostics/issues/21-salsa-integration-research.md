Type: research
Status: resolved

## Question

Investigate the concrete mechanics of adopting the real `salsa` crate as `apex-binder`'s incremental-computation engine, per ticket 19's decision (apexls should adopt real salsa, not a lighter bespoke worklist pattern, as its incremental-computation engine for transitive facts -- a decision made for reasons broader than just this specific technical question). Ticket 16 (a prior research ticket, already resolved) already established *why* salsa's algorithmic shape fits this problem (demand-driven memoization with early cutoff); this ticket is about *how it would actually integrate with this specific codebase*, which hasn't been investigated at all yet. Establish, concretely:

- **The `Send`/`Sync` question.** `crates/apex-binder/src/lib.rs:599-601` documents that `SyntaxNode` (rowan-based) is deliberately neither `Send` nor `Sync`, and the existing three-pass pipeline uses real multi-threading (`rayon`) for Pass 1/Pass 2 parallel work. What does salsa actually require of its tracked inputs/query return values regarding thread-safety, and does that conflict with storing (or referencing) rowan `SyntaxNode`/`SyntaxPtr` values inside salsa-tracked structures? If there's a real conflict, what's the resolution -- keep only owned, thread-safe data (symbol ids, text ranges, cached strings) in salsa-tracked queries and re-resolve back to the live tree only at the edges, the way `crate::ptr::SyntaxPtr` already works today?
- **Mapping the existing three-pass structure onto salsa's own vocabulary.** Salsa distinguishes inputs (external, settable data) from tracked functions (derived, memoized, invalidation-tracked computations). How would `apex-binder`'s Collect/Inherit/Resolve passes, and its existing `BindCache`/incremental-rebuild machinery (`crates/apex-binder/src/incremental.rs`), map onto that vocabulary -- is this a wholesale replacement of `BindCache`, or could salsa be adopted incrementally for a subset of the binder (e.g. only the new transitive-fact layer this whole effort was originally about) while the existing three-pass pipeline stays as-is underneath?
- **Migration path and blast radius.** Given every existing diagnostic/capability (`BoundProgram`'s full public API -- `resolution_at`, `symbol_at`, `inherited_chain`, `references_to`, all eight shipped diagnostics, hover, completion, rename, ...) currently depends on `BoundProgram`'s current shape, what would actually need to change in each consumer, versus what could stay behind a stable-looking API while the implementation swaps underneath? Is an incremental, feature-flagged, or parallel-implementation migration path realistic, or does salsa's own model force an all-at-once cutover?
- **Real-world precedent beyond rust-analyzer.** rust-analyzer is the obvious salsa consumer, but it was designed around salsa from very early on. Is there a real precedent for retrofitting salsa onto an *existing*, already-shipped incremental compiler/language-server architecture (not built with salsa from day one) that this project could learn from, including what broke or took longest during that retrofit?

This ticket is fact-finding only -- it does not decide the migration plan. Its findings would feed a future migration-plan ticket.

## Answer

### 1. The `Send`/`Sync` question

Salsa's real requirement, confirmed against its own docs, is stricter than a vague "thread-safety" note -- it's an enforced macro-level bound:

- `salsa::Database` itself is `pub trait Database: Send + ZalsaDatabase + AsDynDatabase` (https://docs.rs/salsa/latest/salsa/trait.Database.html) -- note `Send`, not `Sync`; salsa's parallel-query model is "each thread holds/clones its own database handle over shared, `Arc`-backed storage," not "one database instance shared by reference across threads."
- `#[salsa::tracked]` functions require: the database parameter aside, every key parameter and the output must implement `Send + Sync`; a single key parameter must be a Salsa struct; multiple key parameters additionally need `Clone + Eq + Hash`; any parameter/output type that isn't unconditionally `'static` must implement salsa's `SalsaValue` (https://docs.rs/salsa/latest/salsa/attr.tracked.html).
- `#[salsa::tracked]` **struct** fields: unconditionally-`'static` fields are accepted directly, everything else must implement `SalsaValue`.
- Tracked-struct plumbing itself requires `Send + Sync`: the internal `Configuration::Fields<'db>` associated type and its `Revisions` type both must implement `Send + Sync` (https://salsa-rs.github.io/salsa/plumbing/tracked_structs.html).

So yes -- there is a real, hard constraint, and it does conflict with ever putting a live `SyntaxNode`/`SyntaxToken` (rowan's red tree, `Rc`-based, confirmed `!Send`/`!Sync` by `crates/apex-binder/src/lib.rs:599-601`'s own comment) into any salsa input, tracked-fn parameter, tracked-fn return, or tracked-struct field. That would fail to compile, not just "be a bad idea."

The good news: this codebase already never does that, for exactly the same reason (surviving `rayon` multi-threading), and the fix is already the codebase's own established pattern, not something to invent:

- `crates/apex-binder/src/ptr.rs:1-26`'s own module doc comment states the rationale nearly verbatim: "rowan's green tree is `Rc`-based, so `SyntaxNode`/`SyntaxToken` are neither `Send` nor `Sync`... `SyntaxPtr`/`AstPtr<N>` mirror rust-analyzer's `SyntaxNodePtr`/`AstPtr<N>` split: cheap, `Copy`, `Send + Sync` data that can be re-resolved into a real node." `SyntaxPtr` is `{file: FileId, kind: SyntaxKind, range: TextRange}` -- trivially `Send + Sync + Copy + Eq + Hash`, i.e. already satisfies every bound salsa's macros enforce.
- `crates/apex-binder/src/symbol.rs:175-206`'s `Symbol` struct already stores only a `SyntaxPtr` (`pub ptr: SyntaxPtr`) and `Option<AstPtr<Type>>`, never a live node.
- `crates/apex-binder/src/incremental.rs`'s whole `BindCache`/`FileBodies` shape (`ReferenceTable`, `FxHashMap<SyntaxPtr, ScopeTree>`, `Vec<(SymbolId, SmolStr)>`, etc.) is already built entirely from owned, `Send`/`Sync`-safe data -- there is nothing in it today that would need to change shape to become a `SalsaValue`.
- Separately, `crates/apex-parser/src/errors.rs:8-38`'s `Parse` struct (`{green: GreenNode, errors: Vec<ParseError>}`) wraps rowan's *green* tree, which is `Arc`-based and `Send + Sync` -- only `Parse::syntax()` builds the (non-`Send`/`Sync`) red `SyntaxNode` on demand, never stored. `crates/apex-binder/src/lib.rs`'s Pass 2 comment (around line 599) already exploits exactly this: closures are keyed "by `&Parse` (`Sync`, safe to share across threads), not by an already-built `SyntaxNode`... each parallel closure below calls `.syntax()` itself to build its own thread-local node." This is precisely rust-analyzer's own `SourceFile`/`GreenNode`-as-salsa-input pattern (see item 4 below) -- apexls already has the identical seam ready to use as a salsa input if a whole-tree salsa input were ever wanted, without inventing anything new.

**Resolution**: no design change is needed to satisfy salsa's `Send`/`Sync` requirement -- it's already satisfied by the discipline this codebase adopted independently (rowan red trees never persisted past the closure that built them; `SyntaxPtr`/`AstPtr<N>`/`SymbolId`/`SmolStr`/`FxHashMap` used everywhere `apex-binder` needs to remember something long-lived). A salsa migration would keep using exactly these owned shapes as tracked-fn inputs/outputs/struct fields, and re-resolve to a live `SyntaxNode` only at the LSP-facing edge (`BoundProgram`'s own accessor methods, e.g. `syntax()`, `resolution_at()`), exactly as today.

### 2. Mapping Collect/Inherit/Resolve onto salsa's input/tracked-fn vocabulary

- **Pass 1 (Collect)** maps onto: one `#[salsa::input]` per file (source text/`Parse`, keyed by `FileId`) feeding a `#[salsa::tracked] fn collect_file(db, file) -> FileSymbols` that does today's per-file `collect::` work, returning the same shape `BindCache::table`/`raw_extends`/`raw_super`/`supertype_ptrs` already store per file (`crates/apex-binder/src/incremental.rs:152-171`). Salsa's own per-input revision tracking *is* what `Freshness::Stat`/`Freshness::ContentHash` (`crates/apex-binder/src/incremental.rs:46-73`) hand-implements today (`std::fs::metadata` stat-match / content-hash-match to decide "can this cached `Parse` be reused") -- a salsa input's built-in "did this exact input change" check would replace that machinery outright for whichever layer adopts it.
- **Pass 1.5 (Inherit)** is salsa's classic "aggregating tracked fn": `resolve_inheritance(db) -> InheritanceTable` reading every file's `collect_file(file)` raw-extends/raw-super and doing what `crate::inherit::resolve_inheritance` does today. `BindCache`'s own doc comment already states the reason this is whole-project ("inheritance is inherently whole-project, not something one file's edit can resolve in isolation," `crates/apex-binder/src/incremental.rs:156-162`) -- salsa's early-cutoff (a downstream tracked fn only re-runs if the *value* it read changed, not merely the input's revision counter) is specifically what would let this, and everything downstream of it, skip recomputation more often than today's blunt `declarations_changed` boolean does: `lib.rs`'s Pass 1.5 comment (around the `if declarations_changed { ... }` block) documents that *any* declaration change anywhere today forces a full-project `rebuild_indices()` + `resolve_inheritance()` + a full Pass 2 rebind of every current file (the "conservative fallback, identical cost to a full rebuild" mentioned right before `files_to_rebind`) -- salsa would only re-run inheritance-dependent work for symbols whose actual supertype set changed, not merely "some file somewhere changed."
- **Pass 2 (Resolve)** maps most naturally onto *per-body*, not per-file, tracked fns: `bind_body(db, body_ptr: SyntaxPtr) -> (ReferenceTable-slice, ScopeTree)`, depending on `resolve_inheritance(db)` and whichever other files' `collect_file` a qualified reference crosses into. This is the biggest granularity win available: today's `FileBodies` (`crates/apex-binder/src/incremental.rs:75-87`) is replaced wholesale per dirty *file* ("Replaced wholesale whenever that file gets rebound"), so editing one method currently forces rebinding every symbol in that file; a per-body salsa tracked fn would only recompute the edited method's own body.
- `BindCache`'s directory-walk-derived data (`discovery`/`schema`/`labels`/`pages`/`vf_referenced_classes`, all gated by the same hand-rolled `need_fresh_discovery` trigger and `invalidate_discovery()` hook, `crates/apex-binder/src/incremental.rs:90-186`) is an even lower-risk salsa candidate than the three passes themselves: no rowan tree involved at all, already `Arc`-wrapped, already invalidated by one boolean trigger -- a natural first `#[salsa::input]` to convert.
- **Is this a wholesale replacement of `BindCache`, or can it be adopted incrementally?** Salsa's own model doesn't force all-or-nothing -- nothing stops the new transitive-fact layer (ticket 19's original scope) from being implemented as salsa tracked fns that consume *pre-computed, already-owned* data (`SymbolId` graphs, `Resolution` tables) produced by the existing three-pass pipeline as its salsa inputs, while Collect/Inherit/Resolve and `BindCache` itself stay untouched underneath. The real cost of that staged shape: the boundary between "salsa-owned" and "`BindCache`-owned" data needs its own invalidation glue -- every time `BindCache` decides a file is dirty and rebinds it, whatever feeds that file's data into salsa's inputs must be told to invalidate too, so two independent "what changed" trackers exist side by side until (unless) the rest is migrated as well. That's real but bounded complexity, not a blocker.

### 3. Migration path and blast radius

`BoundProgram`'s public accessor API (`crates/apex-binder/src/lib.rs:777-1135`: `files`, `file_path`, `file_id`, `syntax`, `syntax_errors`, `file_count`, `resolution`, `highlight_range`, `resolution_at`, `symbol_at`, `all_resolutions`, `resolutions_in_file`, `references_to`/`references_to_in_file`/`references_to_external`/`references_to_external_in_file`, `scope_tree`, `call_sites_in_range`, `enclosing_callable`) is already shaped as read-only queries over owned, `SyntaxPtr`-keyed/`SymbolId`-keyed data (`Resolution`, `ScopeTree`, etc.) -- exactly the "re-resolve to the live tree only at the edges" shape a salsa migration wants at its boundary. None of these signatures need to change to be backed by salsa internally: every consumer (hover, completion, rename, the eight shipped diagnostics, call hierarchy) calls through this same surface today and could keep doing so unchanged if `BoundProgram::from_files_cached`'s *implementation* were swapped from "diff against `BindCache` by hand" to "read a salsa database's tracked-fn results and snapshot them into the same owned maps `BoundProgram` already exposes." That makes the migration adapter-shaped at the outward edge, not signature-breaking.

What *would* have to change is everything inside `from_files_cached`'s current imperative orchestration and all of `incremental.rs`'s `BindCache` -- that's exactly the code salsa's own memoization/invalidation is meant to replace (the `Freshness` checks, the per-file dirty diffing, the `declarations_changed` all-or-nothing fallback). That's a real, large internal rewrite, but confined to `apex-binder`'s own guts, not its consumers in `apexls-server`/`apexls`.

Is an incremental/parallel-implementation path realistic, or does salsa force an all-at-once cutover? Salsa itself imposes no such requirement -- a `#[salsa::db]` can be introduced alongside `BindCache` and grown one query at a time (starting with the lowest-risk, rowan-free candidates named in item 2 -- `SchemaIndex`/`LabelIndex`/`PageIndex` -- before ever touching Pass 1/1.5/2). The real cost of staging it, as noted above, is that the still-unmigrated remainder either needs hand-written invalidation glue at the seam, or gets modeled as one coarse salsa input that's fully invalidated on any change inside it (correct, but non-incremental for that remainder until it's migrated too). Neither option is free, but neither is a hard blocker -- a staged migration is realistic, just not "come for free" the way switching a single self-contained query would be.

### 4. Real-world precedent beyond rust-analyzer

rust-analyzer's own architecture is a *closer* partial precedent than the ticket's framing assumes, and it's directly on point for this codebase's shape: rust-analyzer's official architecture doc states plainly that its `syntax` crate (rowan-based, exactly analogous to `apex-syntax`/`apex-parser`) "is completely independent from the rest of rust-analyzer. It knows nothing about salsa or LSP," with a dedicated `base-db` crate as the sole seam that turns that salsa-agnostic syntax-layer data into salsa inputs (https://rust-analyzer.github.io/book/contributing/architecture.html). Public history backs this up: rust-analyzer began as "libsyntax2," a standalone rowan-based, error-resilient parser with no salsa and no LSP; salsa was layered on afterward, once the project grew from "a syntax tree library" into an actual IDE backend. That is the same shape this ticket is asking about -- a pre-existing, salsa-ignorant rowan tree layer, with salsa introduced later purely at a translation seam -- and it maps onto `apex-binder` directly: `apex-syntax`/`apex-parser` would stay untouched and salsa-ignorant exactly as `syntax` does in rust-analyzer, and a narrow seam (plausibly a new module inside `apex-binder`, playing `base-db`'s role) would be the only place that ever touches both a live `SyntaxNode` and a salsa database in the same function.

Beyond that specific rust-analyzer-lineage precedent, I could not find a citable, documented case study of a mature, already-shipped, non-rust-analyzer-lineage compiler or language server converting its *own pre-existing* incremental engine over to salsa, despite checking: salsa-rs/salsa's own README and GitHub topic listings (no adopters list found), and targeted web searches for "migrating to salsa" / "adopted salsa" / "retrofit salsa" (no case-study blog posts turned up). The closest analog outside rust-analyzer's own lineage is Astral's Ruff project: its `ty` type checker (formerly "red-knot") is salsa-based and was added as a new, separate sub-project (`red_knot_python_semantic`/`ty_python_semantic` crates) inside the pre-existing, already-shipped, non-salsa Ruff linter monorepo. One secondary source (a WebSearch AI-generated summary, not independently confirmed against a primary changelog/PR in this pass) characterized this as salsa being "migrated to... in mid-2024" after some earlier non-salsa implementation, but I was unable to verify that specific claim against a primary source (GitHub commit search against `astral-sh/ruff` returned no matches for "salsa" in commit messages, and `astral.sh/blog/red-knot` 404s) -- flagging it here as unverified rather than asserting it. Even taken at face value, that precedent is still "add a new salsa-based component beside an existing shipped tool," not "convert an existing shipped component's own engine to salsa," which is a meaningfully lower-risk shape of adoption than what this ticket asked about. No evidence was found that Rome/Biome uses salsa at all. **Honest conclusion**: no strong outside precedent exists for the specific scenario asked about; the rust-analyzer `syntax`/`base-db` seam design is the best available architectural template to imitate, not a "what broke / what took longest" retrospective, since no such retrospective was located.
