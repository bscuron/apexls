## Question

Implement the three type-mismatch checkpoints settled in [ticket 09's Answer](09-ty-promotion-architecture-decision.md), `ERROR` severity, Option B (inline, no general stored `Ty` layer):

- **`Stmt::LocalVarDecl`**: for each declarator with both a declared type and an initializer expression, capture the declared `Ty` (`self.resolve_type_ref(&ty)`) and the initializer's inferred `Ty` (`self.bind_expr(scope, &e)`) and check `conversions::type_compatible`. Also fix the identical discard in the `for`-loop init-declarator arm (`resolve.rs:1649-1671`), the same shape.
- **`Stmt::Return`**: capture the returned expression's `Ty` and compare it against the enclosing method's own declared return type (`self.enclosing_member`/`self.type_of_symbol`).
- **Non-overloaded call arguments**: fix `narrow_by_overload`'s `pool.len() == 1` fast path (`resolve.rs:142-144`) to still run `is_argument_type_compatible`/`type_compatible` against the single candidate for diagnostic purposes (recording a mismatch, not changing the `Resolution` itself -- the fast path's existing resolution behavior must stay unchanged, only a new side-channel finding gets added).

Route every comparison through the existing `conversions::type_compatible`/`is_argument_type_compatible`, never a new nominal-equality check -- this is what inherits the zero-false-positive correctness ticket 08's own NPSP survey confirmed those functions already have. Record each finding as a `(SyntaxPtr, message)` (or emit the `Diagnostic` directly from within `apex-binder`'s own walk, whichever shape fits the existing `Resolution`-recording plumbing better) rather than persisting `Ty` anywhere -- per Option B, "promote the check, not the type."

Definition of done: wired into the merged `publish_diagnostics` alongside the eight existing sources; tests covering each of ticket 08's six real NPSP patterns explicitly as **negative** tests (implicit numeric widening, `Object`-typed dynamic-SObject-access idioms, casts recovering a concrete type, `List<Concrete>`-into-`List<SObject>` covariance with no cast, `Id`/`String` bidirectional compatibility, SObject-to-SObject widening) -- none of these six may ever be flagged; plus positive tests for a genuine mismatch at each of the three checkpoints; a real-NPSP-corpus zero-false-positive sanity pass (matching every other diagnostic on this map, and especially load-bearing here given how many real-world exceptions to naive type equality ticket 08 catalogued).

## Answer

Shipped as `type_mismatch_diagnostics`, all three checkpoints (`LocalVarDecl`/`for`-init declared-vs-initializer, `Return` vs. the enclosing method's declared type, and non-overloaded call arguments via a new side-channel `check_call_argument_types` that runs after `narrow_by_overload` without changing its `Resolution`), all routed through `conversions::type_compatible`, `ERROR` severity, per ticket 09's Option B.

**The real work was the false-positive hunt.** A first full-NPSP-corpus pass came back with **422** findings -- an order of magnitude past every other diagnostic on this map -- because these checkpoints are the first consumers to run `type_compatible` unconditionally on every declaration/argument/return, not just as a tie-breaker among multiple same-arity overload candidates (which `narrow_by_overload` only ever does when there's real ambiguity to break). That exercised real gaps `conversions.rs`/the stdlib snapshot/the binder had never been forced to confront before. Root-caused and fixed each one in its actual shared layer rather than special-cased per checkpoint, driven back down to **0** by iterating the corpus scan after every fix:

- **`List<SObject>` into `List<ConcreteObject>` is legal in *every* context** (assignment, argument, return) -- confirmed against a real org (`List<Account> accs = aListOfSObject;` compiles); initially modeled as argument/return-only after misreading a two-statement oracle probe, corrected once a clean single-statement test showed assignment gets it too. `Set`/`Map` get no such leniency (`Set<SObject>` to `Set<Account>` is a real `Illegal conversion` error) -- confirmed `List`-only.
- **`List<SObject>` into a *scalar* object-typed variable** (`SObject`/a concrete type) is legal via specific dynamic-SOQL call expressions (`Database.query(...)` used directly as an initializer) but not via a stored `List<SObject>` variable -- narrower than this module can recognize syntactically, so kept conservative (`None`) for the whole shape rather than guessing which call expressions qualify.
- **`Decimal` narrows to `Double`** for a plain assignment/`return`, but not as a call argument (confirmed via `takesDouble(aDecimalValue)` being a real "incorrect signature" error) -- the one numeric pair that isn't uniform across contexts, contradicting `numeric_rank`'s prior "never the reverse" assumption (never actually oracle-tested for this specific pair before).
- **A reference field's own literal API name (`OwnerId`, `Contact1Imported__c`) yields `Id`, never the related object** -- only the separate relationship-name accessor (`Owner`, `Contact1Imported__r`) does. `bind_field_expr` conflated the two (both normalize to the same field lookup); fixed by comparing the originally-accessed segment against the found field's own API name. Also fixed a stale doc comment claiming `Account.OwnerId.Username` chains (a real "non foreign key field in path expression" compile error) -- the test asserting it was itself wrong, corrected to `Owner.Username`.
- **`array_size`/array-initializer `new` expressions** (`new Opportunity[0]`, `new Opportunity[]{...}`) resolved as the bare element type, not `List<Element>` -- the grammar never attaches `[]` to the `new`'s own `Type` node (a sibling, not part of it), unlike a declared type's `Type::is_array()`. New `NewExpr::is_array_new()` AST accessor.
- **`SObject.clone(...)` on a concrete receiver returns that concrete type**, not the scraped generic `SObject` its signature declares -- confirmed against a real org, mirroring `generics.rs`'s existing "same type as receiver" treatment for `List`/`Map`/`Set`'s `clone`/`deepClone`.
- **A bare `Object`-named argument is at least as often this crate's own "couldn't infer more" fallback as a genuinely-declared `Object`** -- made symmetric with the existing `param_name == "Object"` leniency (`None`, not a guessed elimination).
- **Namespace-qualified type names** (`ApexPages.Message`) never matched a resolved `Ty`'s always-bare name, and source-text case drift (`Apexpages.Message`) compounded it -- new shared `strip_namespace_prefix` helper (case-insensitive `stdlib.class_in_namespace` lookup), applied to both the declared and the resolved-argument side.
- **`Ty::for_bin_op`'s `+` propagated the *left* operand's type unconditionally** -- wrong for Apex's overloaded string concatenation whenever the non-`String` operand came first (`aLongValue + 'suffix'`); fixed to check either side for `String` first.
- **`declare_local` (body-local declarations) had its own, second copy of `type_ptr_and_name`'s array-sugar logic, missing both the top-level and the nested-generic-argument fix** `type_ptr_and_name` itself already had -- replaced with a direct delegation instead of two copies drifting apart.
- **`apex_stdlib`'s scraped `return_type`/param `type_name` fields lose a generic argument entirely for ~168+132 real stdlib methods** (`Database.query` scrapes as bare `"List"`, not `"List<SObject>"`, though the method's own `signature` text still has it) -- new `parse_signature` recovers the missing argument from `signature` whenever the existing field is a bare `List`/`Set`/`Map`, never overriding an already-correct field.
- **`Search.query`'s single-arg overload's scraped `return_type`/`signature` were both outright garbled** (`"sObject"` / `"sObject[sObject[]]"` for a method that really returns `List<List<SObject>>`) -- a scraper artifact distinct from the above, hand-corrected directly in `data/apex_reference.json` (this crate's own established practice for confirmed scraper mistakes).
- **`conversions::project_arg_compatible` resolves a declared name via the *unscoped* `resolve_dotted_name`**, unlike a real type reference's own scope-aware resolution -- misfires when a project has two same-named types, one lexically nested and one an unrelated top-level (`PSC_ManageSoftCredits_CTRL`'s own nested `SoftCredit` vs. the unrelated top-level `SoftCredit.cls`, the exact scenario ticket 22 fixed for type *references*, never mirrored here for value *comparison*). Two-part fix: a scope-aware short-circuit added at each of the three checkpoints (using `self.enclosing_type`/the callee's own enclosing type), plus a same-name fallback inside `project_arg_compatible` itself (two different-but-same-named resolved ids stay `None`, not a guessed `Some(false)`) for the cases the short-circuit can't reach (a name collision nested one level inside a generic argument).
- **`System.Iterator` is a real, modeled stdlib interface with unenumerable implementors** (a `Database.QueryLocatorIterator` genuinely implements it) -- this module has no "which stdlib class implements which stdlib interface" registry, so the final "two different real stdlib classes never convert" elimination wrongly fired; excluded `Iterator` specifically from that rule, mirroring the same accepted gap already documented for a project class implementing an unmodeled interface.
- Also folded in two field-type-mapping gaps found early: `apex_type_for_schema_field_type` had no case for `"name"` (a custom object's implicit compound Name field) or `"autonumber"`, both really `String`.

Tests: `crates/apexls-server/tests/type_mismatch_diagnostics.rs`, 11 tests -- one positive test per checkpoint (plus a constructor-argument variant) and all six of ticket 08's negative patterns, none flagged. `crates/apex-stdlib/src/lib.rs` gained two new unit tests for the signature-enrichment recovery (`Database.query`'s return type, `StandardController.addFields`'s param type). `crates/apex-binder/tests/standard_schema_resolution.rs`'s pre-existing lookup-chain test was corrected (it asserted `acct.OwnerId.Username` resolves, which is itself a real compile error; fixed to use the real relationship-name chain `acct.Owner.Username`). Full `apex-binder` suite passes (93 unit tests, all integration tests, `resolution_regression_baseline.rs` unaffected). Full `apexls-server` suite passes except the one pre-existing, unrelated flaky test already known from earlier tickets this session (`syntax_error_diagnostics`'s clears-the-diagnostic-on-next-publish race, reproduced failing even run alone, confirmed unrelated to any change here). Final real-NPSP-corpus sweep: **0** type-mismatch diagnostics across all 1,035 files.
