## Answer

Ticket 24 had already landed by the time this was worked (`salsa = "0.28.2"` pinned in `crates/apex-binder/Cargo.toml`, `crates/apex-binder/src/salsa_smoke.rs` in place) -- no surprises versus ticket 21's documented API, confirmed while resolving this ticket.

**Staging order**: locked as ticket 21 recommended, unrevised -- Stage 1 (the rowan-free indices: `SchemaIndex`/`LabelIndex`/`PageIndex`/`vf_referenced_classes`/`discovery`) -> Stage 2 (Pass 1/Collect) -> Stage 3 (Pass 1.5/Inherit) -> Stage 4 (Pass 2/Resolve). Already risk-ascending (no rowan involvement at all -> file-scoped rowan use -> whole-project aggregation -> per-body, highest-blast-radius granularity), and each stage's salsa inputs are exactly the prior stage's outputs, so reordering would break the dependency chain for no benefit.

**Seam/module structure**: a new module inside `apex-binder` -- `crates/apex-binder/src/db.rs` -- playing rust-analyzer's `base-db` role *conceptually*, but as a module, not a separate crate. This matches every existing internal-concern split in this codebase (`schema_index`, `label_index`, `page_index`, `reference_table`, `symbol_table`, `ptr`, `scope`, ... -- 23 modules, one crate, zero precedent for spinning an internal concern into its own crate) even though rust-analyzer's own `base-db` is a separate crate; the codebase's own established convention wins over the precedent's literal shape. Routing: a **hard branch per stage** inside `BoundProgram::from_files_cached` (`crates/apex-binder/src/lib.rs`) -- once a stage's data is salsa-backed, `from_files_cached` reads it from the salsa database unconditionally, with no permanent feature flag or trait-object indirection. `from_files_cached` is a single, linearly-staged function today (Stage -1 discovery -> Stage 0 FileIds -> Stage 1a parse -> ...) with no existing plugin seam, so a stage's own migration replaces its block in place rather than routing through new abstraction.

**Coexistence / invalidation-glue strategy**: `BindCache` (`crates/apex-binder/src/incremental.rs`) stays the single "what changed" authority for the entire staged period, even for already-migrated stages -- it keeps deciding staleness exactly as it does today (`need_fresh_discovery`, `declarations_changed`, per-file `Freshness` diffing). Every point where `BindCache` currently writes a freshly-computed value into its own fields *also* pushes that value into the matching salsa input via a small adapter function living in `db.rs` (e.g. a `sync_discovery_into_db(&mut db, &discovery)`-shaped call at Stage 1's `need_fresh_discovery` write-site). Salsa never gets its own independent staleness signal during the migration -- it's pure memoization sitting downstream of `BindCache`'s existing dirty-detection, until a stage's own migration is complete, at which point `BindCache`'s hand-rolled diffing for that specific data is deleted outright (not kept as a permanent shadow copy). Glue code lives entirely in `db.rs`, called from the exact `from_files_cached` sites that already write into `BindCache` today -- `BindCache` itself stays salsa-agnostic.

**Validation technique**: dual-run-and-diff against the real NPSP corpus (1,035 files) before any stage's cutover -- the first time two implementations of the same fact coexist in this codebase (every prior corpus-validated ticket, e.g. 17/22/23, only ever had one implementation to validate). Concretely: a temporary corpus test/example, same shape as `resolution_regression_baseline.rs`, running both the `BindCache` path and the salsa path over the whole corpus and asserting byte-identical output for that stage's data. Deleted once that stage cuts over and its `BindCache` half is removed -- not kept as a permanent parallel-implementation tax. This is in addition to, not instead of, the chain's already-locked done-bar (full existing test-suite parity, `cargo bench -p apex-binder` non-regression).

Stages 2-4 stay unspecified (map fog) until each one's own turn comes, per this ticket's own scope.
