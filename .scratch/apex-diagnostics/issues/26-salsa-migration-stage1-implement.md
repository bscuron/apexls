## Question

Implement Stage 1 of [ticket 25](25-salsa-migration-architecture-decision.md)'s locked salsa migration plan: convert `BindCache`'s rowan-free directory-walk-derived data (`discovery`/`schema`/`labels`/`pages`/`vf_referenced_classes` in `crates/apex-binder/src/incremental.rs`) into real `salsa` inputs, per the seam, coexistence, and validation strategy ticket 25 already decided. This is the lowest-risk stage (no rowan `SyntaxNode`/`SyntaxPtr` involvement at all) and the first real cutover, not just the smoke-test ticket 24 already did.

Concretely, per ticket 25's own answer:

- Add `crates/apex-binder/src/db.rs`, a new module (not a new crate) holding the salsa database type and its `#[salsa::input]`s for `discovery`/`schema`/`labels`/`pages`/`vf_referenced_classes`, plus the `#[salsa::tracked]` query functions that reproduce today's `SchemaIndex::from_discovery`/`LabelIndex::from_discovery`/`PageIndex::from_discovery`/`apex_metadata::visualforce::referenced_controller_classes` computations.
- Wire adapter glue (living in `db.rs`, called from `BoundProgram::from_files_cached` in `crates/apex-binder/src/lib.rs`) at the existing `need_fresh_discovery` write-site (`lib.rs` Stage -1, around line 269) so every time `BindCache` decides a fresh walk is needed and writes `cache.discovery`/`cache.schema`/`cache.labels`/`cache.pages`/`cache.vf_referenced_classes`, the same fresh values are pushed into the matching salsa inputs. `BindCache`'s own `need_fresh_discovery` check stays the sole staleness authority for this stage -- salsa is purely a memoization layer downstream of it.
- Replace `from_files_cached`'s reads of `cache.schema`/`cache.labels`/`cache.pages`/`cache.vf_referenced_classes` with reads from the salsa database's tracked queries -- a hard branch/replacement in place, not a runtime feature flag or trait-object toggle.
- Add a temporary dual-run-and-diff corpus test (same shape as `resolution_regression_baseline.rs`), running both the old `BindCache`-computed values and the new salsa-computed values over the full real NPSP corpus (1,035 files) and asserting byte-identical output, before ever trusting the salsa path alone. Delete this test once cutover is confirmed and `BindCache`'s own hand-rolled computation for this data is removed.
- Once the dual-run test confirms parity, delete `BindCache`'s own `schema`/`labels`/`pages`/`vf_referenced_classes` fields and their computation in `from_files_cached` -- Stage 1 data is salsa-owned only after cutover, not kept as a permanent shadow copy. `BindCache::discovery`'s own field/`invalidate_discovery` hook stays (it's still the staleness trigger salsa's input is synced from), but the four derived indices move to salsa-only storage.

**Done bar** (per ticket 25's chain-wide lock, not optional for this stage): full existing test-suite parity (no behavior change) and a `cargo bench -p apex-binder` non-regression check, in addition to the dual-run-and-diff corpus parity above.

Out of scope: Stage 1 touches only the rowan-free indices. Pass 1/Collect (Stage 2), Pass 1.5/Inherit (Stage 3), and Pass 2/Resolve (Stage 4) stay unspecified until their own turn comes, per ticket 25.

## Answer

Shipped exactly per ticket 25's own plan. `crates/apex-binder/src/db.rs` (new module): a `BindDatabase` (`#[salsa::db]`, `salsa::Storage<Self>`), one `#[salsa::input] DiscoveryInput` wrapping `apex_discover::Discovery`, and four `#[salsa::tracked(no_eq, returns(clone))]` queries (`schema_index`/`label_index`/`page_index`/`vf_referenced_classes`) that call the exact same `SchemaIndex::from_discovery`/`LabelIndex::from_discovery`/`PageIndex::from_discovery`/`apex_metadata::visualforce::referenced_controller_classes` functions the pre-salsa code called directly. `no_eq` on all four: none of `SchemaIndex`/`LabelIndex`/`PageIndex`/`HashSet<String>` need content-equality for salsa's early-cutoff, since they only ever recompute when `DiscoveryInput` itself changed. `sync_discovery_into_db` (the one adapter function) is called from `BoundProgram::from_files_cached`'s existing `need_fresh_discovery` write-site (`crates/apex-binder/src/lib.rs`), pushing the freshly-walked `Discovery` into the salsa input; `BindCache::discovery`/`need_fresh_discovery` stay the unchanged staleness authority. Once the dual-run test confirmed parity (see below), `BindCache`'s own `schema`/`labels`/`pages`/`vf_referenced_classes` fields and their direct computation were deleted outright -- `from_files_cached` now reads all four through `db::*` on every call, not just a fresh-walk one.

**Dual-run validation**: `crate::salsa_stage1_dual_run` (`crates/apex-binder/src/salsa_stage1_dual_run.rs`, `#[cfg(test)]`-gated in place, mirroring ticket 24's `salsa_smoke.rs` rather than a `tests/*.rs` integration test -- it needs `pub(crate)` access to `db`'s internals to feed one shared `Discovery` down both paths). `SchemaIndex`/`LabelIndex`/`PageIndex`/`VisualforcePage` gained `PartialEq`/`Debug` derives (previously had neither) solely so this test can `assert_eq!` them. A first version of this test called `apex_discover::discover` twice independently (once for the "old" direct path, once inside `BoundProgram::from_files` for the "new" salsa path) and found a real, pre-existing, unrelated bug: `ignore`'s parallel walker returns `Discovery::object_meta_files`/`field_meta_files` in a run-to-run-nondeterministic order, and `SchemaIndex::from_discovery` given two differently-ordered-but-equal `Discovery`s produces `SchemaIndex`es whose per-object `Vec<FieldSchema>` differ in order -- a false divergence unrelated to salsa. Confirmed directly (a throwaway probe: two `discover()` calls over the same tree, `apex_files`/`object_meta_files`/`field_meta_files` unequal both times; `SchemaIndex::from_discovery` given the same `Discovery` twice is deterministic, given two different-order `Discovery`s is not). Worked around by feeding one shared `Discovery` down both dual-run paths instead of walking twice -- this ticket's own scope is the salsa seam, not `apex-discover`'s walk-order guarantees, so the underlying nondeterminism itself is left as a real, documented, unfixed gap for whichever future ticket needs stable field order. With that fix, the dual-run test passes: byte-identical `SchemaIndex`/`LabelIndex`/`PageIndex`/`vf_referenced_classes` between the pre-salsa and salsa-routed paths over the full real NPSP corpus (1,035 files).

**A second, more consequential finding**: salsa 0.28's thread-local "attached database" model (`salsa::attach`, panics if a *different* database tries to attach on a thread that already has one attached) is incompatible with handing tracked-fn calls to `rayon`'s *shared, process-global* thread pool once more than one independent `BindDatabase` can be in play at the same time. Not theoretical -- a first version of this ticket's implementation wrapped the four `db::*` calls in the same `rayon::join` nesting the pre-salsa code used (to overlap `SchemaIndex`/`LabelIndex`'s bundled-JSON one-time parse with `global_stdlib_index`'s own), and hit a real, reproducible "Cannot change database mid-query" panic under `cargo test`'s parallel test threads (each test's own `BoundProgram::from_files` call gets its own `BindCache`/`BindDatabase`, and `rayon`'s work-stealing let one test's worker thread pick up another's salsa-attached job mid-scope). Fixed by making every `db::*` read in `from_files_cached` strictly sequential, never inside a `rayon::join`/`par_iter` closure. Verified via `cargo bench -p apex-binder`, per this chain's own locked done-bar: a same-machine, freshly-captured master baseline (this repo's default `target/criterion`-stored baseline turned out stale, giving a misleading ~20-60% "regression" until re-baselined) showed no statistically significant change on any of the five existing benchmarks (`corpus/bind_npsp_full`, `corpus/warm_rebind_after_one_file_edit`, `constructs/deep_field_chain_resolution`, `constructs/wide_overload_set_lookup`, `constructs/deep_extends_chain`) after dropping the parallelism. Any future stage that also wants to call into salsa from inside `rayon` (Stage 2-4 all do real per-file/per-body parallel work today) needs to solve this properly rather than just avoid it -- e.g. one `BindDatabase`/`Storage::clone()` handle per `rayon` scope with no cross-scope sharing, or `salsa::attach_allow_change` if genuinely switching databases on one thread is intended.

Full `apex-binder` test suite passes (95 unit tests including the new dual-run test, all integration tests, `resolution_regression_baseline.rs` unaffected -- confirmed clean across 5 repeated runs post-fix, where before the sequential fix it failed with the attach panic on 4 of 5 runs). Full workspace test suite passes. `cargo clippy` clean on every file this ticket touched. `apexls-server`'s one pre-existing flaky test (`syntax_error_diagnostics`'s clears-the-diagnostic race, already known from ticket 23's own resolution) reproduces identically on unmodified `master`, confirmed unrelated to this ticket.
