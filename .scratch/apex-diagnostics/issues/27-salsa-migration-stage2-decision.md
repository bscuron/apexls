## Question

Decide Stage 2 (Pass 1/Collect)'s own concrete salsa design, building on [ticket 21](21-salsa-integration-research.md)'s original four-stage research, [ticket 25](25-salsa-migration-architecture-decision.md)'s locked cross-stage answers (seam is the `crates/apex-binder/src/db.rs` module; `BindCache` stays the sole staleness authority via adapter glue that syncs fresh values into salsa inputs; dual-run-and-diff against the real NPSP corpus before any cutover; `from_files_cached` routes to a landed stage via a hard branch, never a flag or trait-object toggle), and [ticket 26](26-salsa-migration-stage1-implement.md)'s hands-on Stage 1 experience -- specifically its discovery that salsa 0.28's thread-local database-attach model (`salsa::attach`) panics ("Cannot change database mid-query") the moment more than one independent `BindDatabase` is handed to `rayon`'s shared, process-global thread pool, worked around there only by making Stage 1's four whole-project queries fully sequential.

Stage 2 can't take that same shortcut. Pass 1/Collect (`crates/apex-binder/src/collect.rs`) is, by its own module doc comment, "embarrassingly parallel across files" -- and today's `BoundProgram::from_files_cached` already exploits that in Stage 1b (`crates/apex-binder/src/lib.rs`, ~line 538): `parsed.par_iter().filter(|p| p.dirty).map(...)` runs `collect::collect_trigger_unit`/`collect::collect_compilation_unit` across every *dirty* file in parallel via `rayon`, then merges the results sequentially into `cache.table`/`cache.raw_extends`/`cache.raw_super`/`cache.supertype_ptrs`. Unlike Stage 1's four small, whole-project-rebuilt indices, Pass 1/Collect is already fine-grained per-file incremental (only dirty files get recollected) -- exactly the shape salsa's own memoization is built for -- but that same fine granularity means a real migration wants *many* small per-file tracked queries running in parallel, not four sequential ones the way Stage 1 settled for. Making them sequential the way Stage 1 did would give up real wall-clock parallelism on a pass that runs across 1,000+ files (the full NPSP corpus), a regression this chain's own locked done-bar (`cargo bench -p apex-binder` non-regression) would almost certainly catch.

Resolve, with the user:

- **What's the actual salsa input for this stage?** Three real options, each a different blast radius:
  1. Parsing stays entirely `BindCache`-owned (today's `Freshness`-gated reparse-skip in `incremental.rs` untouched), and only each file's already-built `Parse` (cheap to clone -- `apex_parser::Parse` wraps an `Arc`-based `GreenNode` plus `Vec<ParseError>`, confirmed `Send`+`Sync`-safe by ticket 21) gets synced into a per-file salsa input, mirroring Stage 1's `sync_discovery_into_db` shape exactly.
  2. File *text* becomes the salsa input (rust-analyzer's own `base-db` shape, ticket 21's closest precedent), and parsing itself becomes a new salsa-tracked query sitting between the input and `collect_file` -- meaning this stage would actually also subsume today's `BindCache::parses`/`Freshness` reparse-skip logic, not just Pass 1's own collection.
  3. Something narrower still -- e.g. `collect_file` stays a plain function called from inside the existing `rayon::par_iter()` (not salsa-tracked at all this stage), and only its *aggregate, whole-project* output becomes a salsa input for Pass 1.5/Stage 3 to consume, deferring per-file collection's own incrementality to a later stage.
- **Per-file query keying.** Does each file get its own `#[salsa::input]` (a `FileText`/`FileParse`-shaped struct keyed by `FileId`, matching rust-analyzer's per-file input granularity), or one project-wide input holding every file (closer to Stage 1's single `DiscoveryInput` shape, but working against per-file incrementality)?
- **The rayon/salsa-attach problem, concretely.** Given the answer above, what's the actual mechanism that lets many files' tracked queries run in parallel without hitting the same "Cannot change database mid-query" panic ticket 26 found? Candidates worth weighing: a fresh `BindDatabase` (via `Storage::clone()` -- `#[derive(Clone)]` was on `BindDatabase` at one point during ticket 26's own work and was removed only because it turned out unneeded there; trivially restorable) handed to each `rayon` task with zero cross-task database sharing (a task's own query results copied back out, never the database itself); `salsa::attach_allow_change` (deliberately switching databases on one thread -- `salsa`'s own `attach.rs` flags this as bug-prone, "switching databases can cause bugs"); or some other structuring (e.g. one shared `BindDatabase` touched only from the single calling thread, with `rayon` used only for this pass's non-salsa parts, the same shape Stage 1 ended up in but scoped per-file instead of per-index).
- **Coexistence/invalidation-glue, this stage's own shape.** Ticket 25's general answer (`BindCache` stays sole staleness authority, adapter glue syncs fresh values in) was written before Stage 1's own experience; confirm it still holds unchanged for Stage 2's *per-file* dirty-tracking specifically (`cache.table`/`raw_extends`/`raw_super`/`supertype_ptrs`, all currently patched file-by-file in the Stage 1b sequential-merge loop at `lib.rs`, ~line 558) -- i.e. does every place that loop writes into those four `cache.*` maps today also need a matching salsa-input sync call, the same shape `sync_discovery_into_db` used for the single `Discovery`/`DiscoveryInput` pair?

## Answer

**Salsa input: Option 2 (file text), not Option 1 (`Parse`) or Option 3 (aggregate-only).** File text becomes a per-file `#[salsa::input]`, and parsing itself becomes a new salsa-tracked query sitting between that input and `collect_file` (also newly salsa-tracked) -- this retires `parse_one`'s hand-rolled `Freshness`-keyed `Parse` cache (`cache.parses`/`cache.file_parses`) once dual-run confirms parity, the same way Stage 1 deleted `BindCache`'s `schema`/`labels`/`pages`/`vf_referenced_classes` fields. Chosen over Option 1 (safer but leaves parsing permanently duplicated between a hand-rolled cache and a salsa mirror of it) and Option 3 (doesn't actually migrate Collect onto salsa this stage at all). The real cost this accepts: `parse_one`'s `rayon::fold()`-scoped `NodeCache` sharing (which fixed a measured 47% warm-rebind regression) has no direct salsa equivalent and needs a replacement -- see the blocking prototype ticket below.

**Per-file keying: `FileText` keyed by `FileId`**, one salsa input per file -- not a single project-wide input (Stage 1's shape). Real per-file incrementality is the entire reason Stage 2 differs from Stage 1, so project-wide keying would work directly against the goal.

**The rayon/salsa-attach mechanism (verified against salsa 0.28.2's actual source, not inferred): restore `Clone` on `BindDatabase`.** `Storage<Db>`/the database struct is meant to derive `Clone` -- cloning is cheap (`Arc::clone`s the shared engine, gives each clone a fresh independent per-thread state) -- and salsa's own canonical parallel pattern (`tests/parallel/*.rs`, the `calc` tutorial example) is: clone the whole db once per thread/task, move each clone in, call tracked queries directly on it. No `Snapshot`/`ParallelDatabase` type exists in 0.28 (that salsa-2022-era concept is fully subsumed by plain `Clone`). `salsa::attach_allow_change` is not the mechanism -- it swaps *which* database is attached on the *same* thread, not cross-thread parallelism, and salsa's own doc comment calls it bug-prone. Load-bearing gotcha this surfaces: setting any `#[salsa::input]` field requires `&mut`, which cancels every other in-flight query on every other clone and blocks until they drop -- so per-file `FileText` inputs must all be set *sequentially* on one db handle first, and only *then* should the db be cloned per `rayon` task for a read-only parallel phase (`parse`/`collect_file` tracked-query calls). Inputs can never be mutated inside the same parallel section that's reading others.

**Coexistence/invalidation glue: confirms, does not amend, ticket 25's locked answer.** `BindCache`'s existing `Freshness` stat/hash check keeps deciding which files are dirty (still needed regardless of salsa -- no reason to read+push 1000+ unchanged files' text every call); only for dirty files does fresh text get pushed into that file's salsa input. Sync flows one way only: `BindCache` detects dirty -> pushes fresh text into salsa's per-file input -> salsa computes `Parse` then `FileCollection` -> the existing sequential merge loop (`lib.rs` ~558-577) reads salsa's computed `FileCollection` and patches `cache.table`/`raw_extends`/`raw_super`/`supertype_ptrs` exactly as it does today. Those four fields stay `BindCache`-owned and never need a matching salsa-input sync themselves -- they're downstream consumers of salsa's output, not salsa inputs. This is the identical shape Stage 1 already established (`need_fresh_discovery` as trigger, `sync_discovery_into_db` as the one-way push, salsa owning the computed value), just applied one layer deeper -- so no amendment to ticket 25 is needed, despite that being this session's first instinct.

**Follow-on tickets split off:** [a prototype ticket](28-salsa-parse-nodecache-prototype.md) for the one real unvalidated risk (does a thread-local `NodeCache`, reused across every parse a given `rayon` worker thread handles over a run, actually preserve the warm-rebind win `parse_one`'s current fold-segment sharing provides) blocks [Stage 2's own implement ticket](29-salsa-migration-stage2-implement.md), matching ticket 09->23 and ticket 25->26's design-ticket -> implement-ticket pattern -- deliberately *not* blocking this decision itself, since Option 2's overall shape is confirmed consistent with the already-locked architecture and confirmed against salsa's real source, the same confidence bar ticket 25 met before ticket 26 surfaced its own real mechanical problems only during implementation.
