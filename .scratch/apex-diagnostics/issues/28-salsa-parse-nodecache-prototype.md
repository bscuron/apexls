## Question

[Ticket 27](27-salsa-migration-stage2-decision.md) chose Option 2 for Stage 2 (Pass 1/Collect): file text becomes a per-file `#[salsa::input]` keyed by `FileId`, and parsing itself becomes a new salsa-tracked query. This retires `parse_one`'s hand-rolled `Freshness`-keyed `Parse` cache (`crates/apex-binder/src/lib.rs` ~L367-461) -- but that function's `rayon::into_par_iter().with_min_len(64).fold(...)` deliberately shares one `apex_parser::NodeCache` per fold segment across many files, specifically because a naive per-file `NodeCache` regressed warm single-file-edit rebind by ~47% (measured via `cargo bench -p apex-binder`). Under salsa's clone-per-thread parallel model (confirmed in ticket 27: each `rayon` task gets its own cloned `BindDatabase`, tracked queries are logically independent per call), that fold-segment grouping doesn't exist anymore -- nothing obviously replaces the sharing.

Build the smallest real prototype needed to answer, not reason abstractly about: does a `thread_local!` `NodeCache` -- created once per `rayon` worker thread (not per query call), reused across every parse a given worker thread happens to handle over a run, persisting across distinct salsa-tracked query invocations dispatched to that same underlying OS thread -- actually preserve the current fold-segment sharing's benefit? Concretely:

- Wire a minimal salsa-tracked `parse` query (per-file `FileText` input -> `Parse` output) alongside a `thread_local!` `NodeCache`, run it over the real NPSP corpus via `rayon`, and benchmark against the current `parse_one` baseline for both the cold-project case (the interning-amortization win the fold-segment sharing targets) and the warm single-file-edit rebind case (the 47%-regression case specifically).
- If thread-local sharing doesn't hold up, this ticket's job is to find what does (a bounded pool of `NodeCache`s handed out per `rayon` task rather than truly one-per-thread; batching multiple files into one salsa input/query the way Stage 1 batched into `DiscoveryInput` rather than true per-file granularity; or some other structuring) -- report back with real numbers either way, not a guess.

Blocks [Stage 2's own implement ticket](29-salsa-migration-stage2-implement.md): per ticket 27's own resolution, this doesn't block the architecture decision itself (already locked), only the implementation that depends on this specific mechanism actually working.

## Answer

Built the smallest real thing: `crates/apex-binder/examples/salsa_nodecache_prototype.rs`, a throwaway (not wired into `from_files_cached`) runnable harness (`cargo run -p apex-binder --release --example salsa_nodecache_prototype`) with a minimal real salsa db, a per-file `FileText`-shaped `#[salsa::input]`, and a `#[salsa::tracked(no_eq, returns(clone))]` `parse_query` backed by a `thread_local! RefCell<NodeCache>`, run over the real NPSP corpus (1070 files) via `rayon`, compared against today's real `parse_one` shape (fold-scoped `NodeCache`, `.with_min_len(64)`).

**Case 1 -- cold full-corpus parse:** salsa + thread-local `NodeCache` is consistently *faster*, not just non-regressing -- 7-33% across six separate runs (e.g. 38.6ms vs 49.8ms; 37.6ms vs 47.0ms; 41.0ms vs 50.6ms). Root cause, not just a benchmark artifact: a `thread_local!` cache is reused across *every* file a `rayon` worker thread ever parses over the whole run, while today's `rayon::fold()` resets to a brand-new `NodeCache` at the start of every fold segment -- many segments run per call, so today's sharing is narrower in scope than a true thread-local, not equivalent to it.

**Case 2 -- warm single-file-edit rebind:** a single sample per run was pure noise (410µs vs 927µs one run, 62µs vs 98µs the next, sign flipping) -- fixed by sampling 300 unique-edit iterations per run (mirroring `binder_bench.rs::bench_warm_single_edit`'s own unique-suffix rationale) and taking the median. Across three such runs: +9.0%, +73.8%, +5.3% -- salsa modestly *slower*, but on a tiny absolute baseline (18-374µs, itself swinging over 20x run-to-run from system noise alone) -- nowhere near the previously-measured 47% regression, which was 47% of a much larger (milliseconds-scale) *full-pipeline* number from a statistically-treated criterion benchmark, not a parse-only microbenchmark. The mechanism this ticket existed to de-risk (thread-local sharing failing to help, the way a naive fresh-per-file `NodeCache` did before) doesn't materialize as a real problem -- if anything, thread-local's structural advantage (it survives *across* separate edit-response calls; today's fold-scoped `NodeCache` is rebuilt from scratch every single call, never persisted in `BindCache` at all) appears to roughly offset whatever dispatch overhead salsa's own query machinery adds.

**Real mechanical finding along the way** (not anticipated by ticket 27): `Storage<Db>` (hence any `#[salsa::db]` struct built on it) is not `Sync` -- a `rayon` closure cannot hold a *shared reference* to one outer db and clone it per call (`Fn` closures used by `rayon::for_each`/`map_init`/etc. must themselves be `Sync`, and a closure capturing `&db` requires `db: Sync`). The working pattern is to pre-clone the db once per item *before* entering the parallel section (`items.iter().map(|x| (x, db.clone())).collect()`, then `.into_par_iter()` over the owned pairs) -- matching salsa's own test precedent (`db_t1`/`db_t2`, cloned and moved into separate threads, never borrowed) exactly, just spelled out concretely for a `rayon`-shaped fan-out rather than a fixed pair of `std::thread::spawn` calls. [Stage 2's implement ticket](29-salsa-migration-stage2-implement.md) needs this exact shape, not the naive "clone inside the closure" version this prototype first tried and hit `Storage<Db>: !Sync` on.

**Verdict: proceeds Stage 2 as designed.** Thread-local `NodeCache` sharing is validated as sound -- it preserves (and appears to improve) the cold-parse benefit, and the warm-edit case shows no sign of a repeat of the 47% regression at the mechanism level, though [ticket 29](29-salsa-migration-stage2-implement.md) still owes its own real `cargo bench -p apex-binder` full-pipeline measurement per this map's Notes and ticket 29's own definition of done -- this prototype's numbers are a parse-only, single-median signal sufficient to unblock implementation, not a substitute for that rigorous, whole-pipeline gate.

**Prototype disposition:** left in place, uncommitted, at `crates/apex-binder/examples/salsa_nodecache_prototype.rs` on the working branch (not captured to a separate throwaway branch) -- available for [ticket 29](29-salsa-migration-stage2-implement.md) to re-run or reference directly while implementing.
