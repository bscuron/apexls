## Question

Implement Stage 2 (Pass 1/Collect) of the salsa migration per [ticket 27](27-salsa-migration-stage2-decision.md)'s locked design:

- A per-file `#[salsa::input]` `FileText` keyed by `FileId` (new to `crates/apex-binder/src/db.rs`, alongside Stage 1's existing `DiscoveryInput`/`BindDatabase`), plus two new `#[salsa::tracked]` queries: `parse` (`FileText` -> `Parse`) and `collect_file` (`Parse` -> `collect::FileCollection`), replacing today's plain-function `parse_one` parse step and the `parsed.par_iter().filter(|p| p.dirty).map(...)` Pass-1b collection step in `crates/apex-binder/src/lib.rs`.
- `BindCache`'s existing `Freshness` stat/hash check keeps deciding which files are dirty; only dirty files get their text pushed into `FileText` via a new adapter function mirroring `sync_discovery_into_db`'s shape. All per-file input writes happen sequentially on one `BindDatabase` handle before any parallel read phase -- per ticket 27's confirmed load-bearing gotcha (writing a salsa input cancels every other in-flight query on every other clone of the database).
- Parallel reads: restore `Clone` on `BindDatabase` (dropped after Stage 1 as unneeded), clone it per `rayon` task, call `parse`/`collect_file` read-only inside the parallel section -- the clone-per-thread pattern ticket 27 confirmed against salsa 0.28's own source and tests.
- Use whatever `NodeCache`-sharing mechanism [ticket 28](28-salsa-parse-nodecache-prototype.md)'s prototype validated (thread-local or otherwise) to avoid regressing the warm single-file-edit rebind case.
- The existing sequential merge loop (`lib.rs` ~L558-577) stays as-is in shape: it reads each dirty file's `FileCollection` (now via `collect_file(&db, file_input)` instead of a plain function call) and patches `cache.table`/`raw_extends`/`raw_super`/`supertype_ptrs` exactly as today. Those four fields are not salsa inputs and need no sync glue of their own, per ticket 27's resolution.
- Delete `BindCache`'s `parses`/`file_parses` fields (and `parse_one`'s hand-rolled `Freshness` comparison for the read/reparse skip specifically -- `Freshness`-based *dirty detection* itself stays) once dual-run-and-diff against the real NPSP corpus confirms byte-identical output between the pre-salsa path and the salsa path, per ticket 25's locked validation strategy and matching ticket 26's own precedent (`crate::salsa_stage1_dual_run`, `#[cfg(test)]`-gated in place, not a `tests/*.rs` integration test).
- Benchmark against the real NPSP corpus (`cargo bench -p apex-binder`, non-regression on both cold-project and warm-rebind cases) before landing, per this map's Notes.

## Answer

Shipped exactly per ticket 27's design, with one deliberate deviation from this ticket's own literal text (below). `crates/apex-binder/src/db.rs` gained: a per-file `#[salsa::input] FileTextInput { file: FileId, trigger: bool, text: String }`; `sync_file_text_into_db` (mirrors `sync_discovery_into_db`'s create-or-set shape); `#[salsa::tracked(no_eq, returns(clone))] parse_query` (routes through a `thread_local!` `NodeCache`, per ticket 28's validated mechanism, replacing `parse_one`'s old `rayon::fold()`-scoped one); `#[salsa::tracked(no_eq, returns(clone))] collect_query` (calls `parse_query` internally, then `crate::collect::collect_compilation_unit`/`collect_trigger_unit` on the result -- salsa memoizes the inner call same as any other caller). `Clone` restored on `BindDatabase` (dropped after Stage 1 as unneeded); every parallel `rayon` section clones it once per item *before* entering `.into_par_iter()`, never from inside the closure -- `Storage<Db>` isn't `Sync` (ticket 28's real finding), so a closure can never hold a shared reference to one outer `db` and clone it per call.

`crates/apex-binder/src/lib.rs`'s Stage 1a lost its `NodeCache`/`rayon::fold()` machinery entirely (parsing moved to salsa) and now only checks freshness (stat or content-hash, unchanged logic) to decide which files are dirty; a dirty file's freshly-read text feeds a new sequential phase (`db::sync_file_text_into_db`, one call per dirty file, strictly before any parallel salsa read -- ticket 27's confirmed load-bearing gotcha) before Stage 1b's parallel phase calls `db::parse_query`/`db::collect_query` on owned, pre-cloned `(FileTextInput, BindDatabase)` pairs.

**Deliberate deviation:** this ticket's own text calls for deleting both `BindCache::parses` *and* `file_parses`. Only `parses` was deleted (replaced by a lighter `freshness: FxHashMap<PathBuf, Freshness>` -- freshness-only, no redundant `Parse` copy, since salsa now owns that caching job). `file_parses` (`FxHashMap<FileId, Parse>`, patched only for dirty files) was **kept**, populated from `parse_query`'s salsa-memoized output instead of `parse_one`'s direct computation. Reasoning: Pass 2's conservative "declarations changed somewhere, rebind every current file" path needs *every* current file's `Parse` on hand, not just the dirty ones -- restructuring that to query salsa per-file for all ~1,070 corpus files every single call (most of them a memoized-value fetch) was measurably worse for the warm single-edit case than this persisted map's near-free `.clone()`, and routing Pass 2 itself through salsa would be real Stage 4 (Resolve) work, explicitly out of scope for this ticket (ticket 27's own scope note). `BoundProgram.parses`' assembly (`cache.file_parses.clone()`) is unchanged.

**Correctness validated two ways:**
- `crates/apex-binder/src/salsa_stage2_dual_run.rs` (new, mirrors `salsa_stage1_dual_run.rs`'s ticket-26 precedent): dual-runs `parse_query`/`collect_query` against direct `parse_compilation_unit_with_cache`/`collect_compilation_unit` calls over all 1,070 real NPSP files, `assert_eq!`ing `Parse` (via `.syntax().to_string()` + `.errors`) and `FileCollection` (gained `PartialEq`/`Debug`, and `Symbol` gained `PartialEq`, solely for this comparison -- same reasoning as `SchemaIndex`/`LabelIndex`/`PageIndex`'s ticket-26 precedent). **Passes**, byte-identical.
- Full `cargo test -p apex-binder` (96 lib unit tests + every integration test, including `incremental_rebind.rs`'s four tests that directly exercise the incremental-vs-cold-rebuild paths this ticket rewired, and `resolution_regression_baseline.rs`) -- **all pass**, and the whole workspace (`apexls-server`, `apexls` CLI) builds clean against the unchanged `BoundProgram`/`BindCache` public shape.

**Benchmark (`cargo bench -p apex-binder`), re-baselined from a clean `git stash`-isolated master build per ticket 26's own diligence (a stale stored baseline gave misleading numbers there):**
- `corpus/bind_npsp_full` (cold, real NPSP): no significant change (p=0.08).
- `corpus/warm_rebind_after_one_file_edit` (the case this whole ticket chain exists to protect): **-5.4%**, a real improvement (p<0.05) -- matches ticket 28's prototype finding, confirmed at full-pipeline scale.
- `constructs/*` (tiny 2-3-file synthetic fixtures, a *different* benchmark group than the corpus/real-project one this ticket's own done-bar names): `deep_field_chain_resolution` +7.7% and `wide_overload_set_lookup` +13.6% regressed; `deep_extends_chain` -8.8% improved. Root cause: salsa's per-query dispatch (attach, memo lookup, revision tracking) is a small but real fixed cost per file, invisible against real per-file parse/collect work at corpus scale but proportionally large against these deliberately tiny fixtures -- the same *kind* of tradeoff this bench file's own doc comment already documents for `rayon`'s thread-pool scheduling overhead ("expected to run measurably slower... a roughly fixed per-call cost that only pays for itself past a real project's file/symbol count, which these deliberately tiny fixtures never reach"). Not a corpus-scale regression, and not this ticket's stated gate -- documented here for anyone re-baselining `constructs/*` later, not treated as a blocker.

Stage 2 is complete. Frontier: Stage 3 (Pass 1.5/Inherit)'s own design decision, not yet specifiable per the map's "Not yet specified" section until this ticket's own experience is in hand.
