## Answer

**This ticket went through three narrowings during the session, in order: (1) a project-wide input mirroring Stage 1, (2) true per-symbol tracked queries at the user's explicit direction to lean on salsa maximally, (3) back to a project-wide query -- not the original (1), but its salsa-integrated, real-early-cutoff successor -- once building (2) out concretely surfaced a genuine correctness gap, not just an aesthetic preference. All three are recorded below rather than only the final answer, since the middle step's now-abandoned costs (documented, then found unsound) are exactly the kind of thing a future reader benefits from seeing, matching this whole map's practice of keeping false starts visible (e.g. ticket 09's `narrow_by_overload` precondition, ticket 23's 422-false-positive first pass).**

**Why (2) -- real per-symbol tracked queries -- doesn't work.** Verified against salsa 0.28.2's own source first (`salsa-0.28.2/src/function.rs`, `src/cycle.rs`, `examples/calc/type_check.rs`): a tracked function's key must be a salsa struct, so per-symbol queries need `SymbolId` reachable as one (resolved: a project-wide `#[salsa::interned]` promotion, realized practically as call sites reconstructing the handle on demand rather than a wholesale lifetime rewrite -- interning is cheap to redo, not something to store long-term); salsa's default cycle handling is `panic`, needing explicit `cycle_fn`/`cycle_initial` per query. Both are real but tractable costs. What isn't tractable: decomposing `resolve_inheritance` into genuinely independent per-symbol queries requires `resolve_supertype_name`'s container-chain fallback (`resolve_dotted_name_from` -> `nested_type_visible_from`) to read *another* type's `inherited_chain` -- meaning a true per-symbol `inherited_chain_query` would need to mutually recurse with `resolve_supertype_name_query` in both directions, not just handle simple self-cycles. Today's imperative code gets away with this via a sequencing accident, not a designed contract: it reads a container's `inherited_chain` *before* this same pass's own writes land, so it transparently reads last-run's stale value, and that "read the previous revision" shape has no clean salsa equivalent (salsa's model is pure memoization of the *current* revision, not "peek at what this query returned last time"). Replicating today's exact behavior through mutually-recursive per-symbol queries either risks a silent behavior change -- which the mandated dual-run test (ticket 25's own locked validation technique, byte-identical output required) is specifically built to catch and reject -- or needs a materially harder bidirectional-cycle design than anything else in this map, not something to ship without being able to actually guarantee its correctness. Checking real call sites also found a second problem with (2)'s original framing: `inherited_chain`/`direct_super`/`subtypes` are read from 20 sites across `resolve.rs`/`conversions.rs` (Pass 2's own hottest path -- per-argument, per-overload-candidate comparison loops) and `capabilities.rs`'s diagnostic walkers, all today a zero-cost `FxHashMap` lookup; making every one of those a live salsa-tracked-query call risks a real Pass-2 regression against this chain's own locked `cargo bench -p apex-binder` non-regression bar and this codebase's standing performance priority.

**Locked design: one project-wide tracked query, `pass_1_5_query`, running `inherit::resolve_inheritance`'s existing algorithm verbatim** -- same sequencing (`raw_super` resolved before `direct`/`inherited_chain` are built, `direct_subtypes` built last, the exact order that makes today's "reads previous revision's `inherited_chain`" sequencing accident behave the way it does), same manual visited-set cycle guard in `flatten` (no `cycle_fn`/`cycle_initial` needed -- there's no recursive salsa-query graph for cycles to occur *in*; it's one query invocation running the same plain-Rust loop as today), same output shape (`direct_super`/`unresolved_direct_super`/`inherited_chain`/`subtypes` per `SymbolId`, bundled into one returned value). Trivially guaranteed behavior-identical to today because it *is* today's code, just called from inside a tracked query instead of directly from `lib.rs`. No `SymbolId` interning, no `cycle_fn` -- neither is needed once nothing is keyed per-symbol.

**Inputs: a new project-wide `symbol_name_index` plus every file's `collect_query`, both already-shipped-shaped.** `symbol_name_index` (alongside Stage 1's `schema_index`/`label_index`/`page_index` in `db.rs`) aggregates every current file's declared top-level and nested type names -- needed because `resolve_inheritance`'s own name resolution can cross files, so the dependency has to be real, not assumed. `pass_1_5_query` depends on `symbol_name_index` plus every file's `collect_query` output (for `raw_extends`/`raw_super`) -- salsa's own dependency tracking records exactly which files it read, giving real early cutoff without hand-rolled diffing. This reopens **Stage 2's `no_eq` choice on `collect_query`** (`db.rs:224`, shipped in ticket 29): for `symbol_name_index`/`pass_1_5_query` to get real early-cutoff savings (skip recompute when an edit touches only a method body, never a declared name), salsa needs to see `collect_query`'s output as unchanged, which needs real equality comparison, not `no_eq`. `FileCollection` already derives `PartialEq` (ticket 29, for its own dual-run test) -- only the `no_eq` attribute on `collect_query` itself needs to come off. Re-validated with a fresh corpus dual-run for that change alone, on top of Stage 3's own, folded into Stage 3's implement ticket rather than split off -- the user's own call, made after this cost was surfaced.

**`SymbolTable`'s own shape: keeps `inherited_chain`/`direct_super`/`unresolved_direct_super`/`subtypes` as plain fields, populated by a merge loop.** (This piece was locked before the (2)->(3) walk-back and doesn't change: `lookup_member` and every other reader keep a zero-cost `FxHashMap` lookup; a post-`pass_1_5_query` merge loop copies its bundled result into `SymbolTable`'s existing fields, the identical "coexistence" shape Stage 1/2 already established, applied one layer deeper.)

**Recomputation trigger: `declarations_changed`'s bool goes away as Pass 1.5's gate; salsa's dependency graph replaces it.** Today's `lib.rs` ~line 555 `if declarations_changed { rebuild_indices(); resolve_inheritance(...) }` block is replaced by an unconditional call into `pass_1_5_query` every `from_files_cached` call -- unconditional at the call-site level, but salsa's own early cutoff (via `symbol_name_index`/`collect_query`'s real equality comparison) means the query's *body* only actually re-executes when something inheritance-relevant changed, which is strictly more precise than `declarations_changed`'s current over-broad trigger (a method/field addition with no `extends`/`implements` clause anywhere no longer forces a full project-wide re-flatten).

**Internal parallelism: unchanged from today.** `resolve_inheritance`'s own `rayon::par_iter()` calls stay exactly as they are, wrapped inside `pass_1_5_query`'s body -- a plain-Rust parallel step inside one salsa-tracked query, salsa never seeing the parallelism inside it. No per-task `BindDatabase` cloning needed here (unlike Stage 2): there's no per-item salsa input to look up mid-loop, since `pass_1_5_query`'s own arguments (`symbol_name_index`'s result, every file's `collect_query` result) are all fetched once, up front, before the parallel section runs.

**Follow-on:** split off Stage 3's own implement ticket (not yet created as a numbered ticket -- next in this map's sequence) covering: `collect_query`'s `no_eq` removal plus its own fresh corpus dual-run; the new `symbol_name_index` tracked query; `pass_1_5_query` wrapping `resolve_inheritance`'s existing algorithm; the merge loop replacing `lib.rs`'s `declarations_changed`-gated block; a full corpus dual-run (Stage 3's own, on top of the reopened Stage 2 one) before cutover, per this map's Notes and ticket 25's locked validation technique.
