## Question

Decide Stage 3 (Pass 1.5/Inherit)'s own concrete salsa design, building on [ticket 21](21-salsa-integration-research.md)'s original four-stage research, [ticket 25](25-salsa-migration-architecture-decision.md)'s locked cross-stage answers (seam is the `crates/apex-binder/src/db.rs` module; `BindCache` stays the sole staleness authority via adapter glue that syncs fresh values into salsa inputs; dual-run-and-diff against the real NPSP corpus before any cutover; `from_files_cached` routes to a landed stage via a hard branch, never a flag or trait-object toggle), and [ticket 27](27-salsa-migration-stage2-decision.md)/[ticket 29](29-salsa-migration-stage2-implement.md)'s Stage 2 experience -- specifically the confirmed rayon/salsa-attach mechanism (clone `BindDatabase` once per `rayon` task, never share one by reference; every `#[salsa::input]` write happens sequentially, strictly before any parallel read phase) and the confirmed shape of "coexistence glue" (`BindCache`'s existing dirty-detection stays the one trigger; a small adapter in `db.rs` pushes fresh values into a salsa input; a sequential merge loop reads salsa's computed output back into `BindCache`'s own fields).

Stage 3 does not look like Stage 1 or Stage 2. Both landed stages had a clean input shape: Stage 1's four indices are keyed by one whole-project `DiscoveryInput`; Stage 2's parse/collect are keyed per-file by `FileTextInput`, and both stages' actual invalidation trigger already lived in `BindCache` as a simple boolean/dirty-set check. Pass 1.5/Inherit (`crates/apex-binder/src/inherit.rs`, called from `crates/apex-binder/src/lib.rs` ~line 550-564) is neither:

- Its real inputs, `raw_extends`/`raw_super`, are already project-wide-aggregated `Vec`s built by flattening *every* file's slice of `cache.raw_extends`/`cache.raw_super` (`FxHashMap<FileId, Vec<...>>`, populated file-by-file in Stage 1b/2's own merge loop) -- there is no existing per-file salsa value for Stage 3 to key off directly the way Stage 2 read Stage 1's discovery.
- Its trigger is `declarations_changed`, a single project-wide `bool` computed during Stage 1b/2's merge loop (true if *any* dirty file's declared-symbol set differs from before, or a file was added/removed) -- coarser than Stage 2's per-file `Freshness` diffing, and today it gates *whether Pass 1.5 runs at all*, not what it recomputes.
- Its output does not get returned and stored the way `SchemaIndex`/`Parse`/`FileCollection` do. `resolve_inheritance` takes `&mut SymbolTable` and calls `table.set_direct_super`/`set_unresolved_direct_super`/`set_inherited_chain`/`set_subtypes` directly, in place, on the one persistent, non-salsa `SymbolTable` every other pass (including Pass 2) also reads and writes. `SymbolTable` itself holds no salsa-tracked data anywhere today -- Stage 1/2 never needed to touch it.
- It already does its own internal `rayon::par_iter()` (over `raw_extends`/`raw_super` entries and over `resolve_supertype_name`/`flatten` calls), all closures capturing `table: &SymbolTable` by shared reference with **no salsa database in the picture at all** -- a different parallel shape than Stage 2's per-task `BindDatabase` clones, since there's no per-item salsa input to look up.

Resolve, with the user:

- **What's the actual salsa input for this stage?** Candidates worth weighing, each a different blast radius:
  1. A single project-wide `#[salsa::input]` wrapping the already-aggregated `raw_extends`/`raw_super` `Vec`s (mirroring Stage 1's `DiscoveryInput` shape exactly: one input, synced wholesale by an adapter at the same site `declarations_changed` is computed today, recomputed only when that trigger fires).   2. Per-file `#[salsa::input]`s (or a query reading Stage 2's per-file `FileTextInput`/`collect_query` outputs directly) feeding a tracked query that does the aggregation salsa currently does *outside* salsa (the `cache.raw_extends.values().flatten()...` step in `lib.rs`) -- lets salsa's own dependency tracking discover which files' raw-extends actually changed, rather than trusting `declarations_changed`'s existing bool, but is a materially bigger change to how the aggregation itself is expressed.

If this stage's input/output does become salsa-tracked, does that internal parallelism need to change shape at all (e.g. per-task `BindDatabase` clones the way Stage 2 settled on), or does it stay exactly as it is -- a plain-Rust parallel step wrapped by one salsa-tracked query at the boundary, salsa never seeing the parallelism inside it?

## Answer

**Salsa input: true per-type incrementality** -- option 2 (per-file inputs feeding an in-salsa aggregation) narrowed further, during this session, into real per-`SymbolId` tracked queries: `resolve_supertype_name`/`flatten` become salsa-tracked functions keyed per symbol, not one project-wide function gated by `declarations_changed`. Chosen deliberately over the cheaper options this ticket originally framed (a project-wide input mirroring Stage 1's `DiscoveryInput` shape, or an adapter-side content-diff before `.set()`) at the user's explicit direction to lean on salsa as fully as the codebase can support, even after this session surfaced real, concrete costs at each step -- documented below, not glossed over, since a future implement-ticket author needs to see the actual shape of what was accepted, not just the destination.

**Costs verified against salsa 0.28.2's own source before locking this in** (`salsa-0.28.2/src/function.rs`, `src/cycle.rs`, plus its `examples/calc/type_check.rs` and `tests/` precedents -- not inferred, matching this whole chain's own practice):

1. **A tracked function's key must be a salsa struct** (`Configuration::SalsaStruct<'db>`), so per-symbol queries need `SymbolId` reachable as one. This ticket originally proposed containing that lifetime to a private twin inside `db.rs` (Stage 1/2's established pattern: salsa specifics never leak past that module). The user explicitly rejected that containment and chose to make `SymbolId` itself the salsa-interned type project-wide -- a deliberate, acknowledged departure from every prior stage's own seam discipline, and from this ticket's own original "out of scope: re-litigating ticket 25" line (ticket 25 didn't literally forbid this, but its whole staged design assumed `db.rs` stayed the only salsa-aware module). Realized *practically*, not as a literal wholesale rewrite: salsa's own interned-struct idiom is "cheap to reconstruct from plain fields, not something to store long-term" (interning is deduplicating -- the same `(file, local)` pair always interns to the same `Id` within a session), so `ReferenceTable`/`Ty`/`apexls-server`'s diagnostics and every other long-lived holder of `SymbolId` keep storing the existing plain `{file: FileId, local: u32}` value exactly as today; only call sites that actually invoke a per-symbol tracked query construct the interned handle on demand from that plain data. A literal `'db`-lifetime rewrite of every `SymbolId`-holding structure across the binder was considered and rejected as not buildable as one coherent change and not what salsa's own idiom calls for -- "lean on salsa maximally" is honored at the query boundary, not by breaking unrelated long-lived storage.
2. **Salsa's default cycle handling is `panic`** (`cycle.rs`'s own doc comment). A malformed cyclic `extends` chain (`class A extends B` / `class B extends A` -- real, if rare, parseable Apex; today's plain `flatten()` visited-set guard already tolerates it for free) needs explicit `cycle_fn`/`cycle_initial` opt-in per query or it panics instead of degrading gracefully. Locked: `cycle_initial` returns an empty chain, `cycle_fn` fixpoint-iterates to convergence, reproducing `flatten()`'s exact current truncation semantics (a cyclic type's own `inherited_chain` ends up with whatever ancestors were reachable before the cycle closed) -- same observable behavior as today, reached via salsa's fixpoint machinery instead of a manual visited set.
3. **A project-wide name index is required for correctness, not just performance.** `resolve_supertype_name`'s dotted-name fallback (`resolve_dotted_name_from`) can resolve to a type declared in a *different* file than the one being resolved -- so a per-symbol query can't depend only on its own file's `raw_extends`/`raw_super`; it needs the whole project's declared-type namespace as a real salsa dependency, or a rename in file Y could silently leave a stale resolution for a reference in file X (a correctness bug, not a missed optimization). Locked: a new project-wide tracked query (working name `symbol_name_index`, alongside Stage 1's `schema_index`/`label_index`/`page_index` in `db.rs`) aggregates every file's declared top-level and nested type names into one lookup structure, built from each file's `collect_query` output.
4. **This reopens Stage 2's `no_eq` choice on `collect_query`, already shipped in ticket 29.** For `symbol_name_index` to actually deliver early-cutoff savings (skip re-verifying every per-symbol query when an edit touches only a method body, never a declared name), salsa needs to see the index's *computed value* as unchanged, which requires real equality comparison propagating from its inputs -- but `collect_query` is currently `no_eq` (`db.rs:224`, deliberate at Stage 2's own time, since Stage 1/2's triggers were already coarse enough that comparing never helped there). Locked: `collect_query` switches from `no_eq` to real `PartialEq`-based comparison as part of Stage 3's implement ticket, requiring `FileCollection` to implement `PartialEq` (expected cheap -- it's `Vec<Symbol>` plus a couple `Vec<(SymbolId, ...)>`s), re-validated with a fresh corpus dual-run before Stage 3 cuts over, on top of Stage 3's own dual-run. This is explicitly in scope for Stage 3's implement ticket, not deferred to a separate prerequisite -- the user's own call, made after this cost was surfaced.

**`SymbolTable`'s own shape: stops owning `inherited_chain`/`direct_super`/`subtypes` as plain fields.** `lookup_member` and every other reader calls the per-symbol salsa-tracked query directly (constructing the interned `SymbolId` handle inline) rather than reading a value a merge loop pre-populated -- the user's explicit direction to lean on salsa as the source of truth rather than mirror its output back into plain storage, even on Pass 2's hot path. `set_inherited_chain`/`set_direct_super`/`set_unresolved_direct_super`/`set_subtypes` and their backing fields are retired from `SymbolTable` once Stage 3 cuts over, the same "delete the old field outright, don't keep a permanent shadow copy" pattern Stage 1 used for `BindCache`'s four index fields.

**Recomputation trigger and grain: real per-symbol, not `declarations_changed`-gated.** `BindCache`'s existing `declarations_changed` bool stops gating whether Pass 1.5 runs at all (today's `lib.rs` ~line 555 `if declarations_changed { ... }` block goes away for this stage); instead, every current file's dirty-or-not status still decides which files' `FileTextInput`s get a fresh `.set()` (unchanged from Stage 2), and salsa's own dependency graph -- `symbol_name_index` depending on every file's now-real-equality `collect_query`, each per-symbol query depending on its own file's `collect_query` plus `symbol_name_index` -- decides which individual symbols' chains actually need recomputing, via early cutoff at each layer.

**The internal-rayon-vs-salsa mechanism: the same clone-per-task pattern ticket 27/29 confirmed for Stage 2, applied per-symbol.** Every current project-wide symbol gets its own `resolve_supertype_name`/chain-flatten call, fanned out via `rayon` with each task holding its own pre-cloned `BindDatabase` (never a shared reference cloned from inside the closure) -- identical mechanism to Stage 2's per-file fan-out, just keyed by `SymbolId` instead of `FileId`. `symbol_name_index` itself is computed once, sequentially, before that parallel phase begins (mirroring the load-bearing "set every input before any parallel read phase" gotcha ticket 27 confirmed), since every per-symbol task depends on it.

**Follow-on:** split off Stage 3's own implement ticket (not yet created as a numbered ticket -- next in this map's sequence) covering: `SymbolId` promoted to `#[salsa::interned]`; `collect_query`'s `no_eq` removal plus `FileCollection: PartialEq` plus a fresh corpus dual-run for that change alone; the new `symbol_name_index` tracked query; per-symbol `resolve_supertype_name`/`flatten` tracked queries with `cycle_fn`/`cycle_initial` configured to match today's truncation semantics; `SymbolTable`'s four inheritance-related fields and their setters deleted outright; every `lookup_member`-style reader migrated to call the tracked query directly; a full corpus dual-run (Stage 3's own, on top of the reopened Stage 2 one) before cutover, per this map's Notes and ticket 25's locked validation technique.
