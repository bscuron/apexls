## Answer

Shipped per ticket 30's final (simplified) design, with one significant real bug found and fixed along the way, plus a second, narrower gap found and fixed during implementation before it ever shipped.

**What landed:**
- `collect_query` (`crates/apex-binder/src/db.rs`) lost `no_eq` -- `FileCollection` already derived `PartialEq` (ticket 29).
- A new project-wide `#[salsa::input] FileSetInput { entries: Vec<(FileId, FileTextInput)> }`, synced (`db::sync_file_set_into_db`) only when the file set itself changes (a file added/removed), sorted by `FileId` for determinism.
- A new project-wide `#[salsa::tracked(returns(clone))] raw_inheritance_inputs(db, file_set) -> Arc<RawInheritanceInputs>`, aggregating every current file's `raw_extends`/`raw_super` *and* every declared type-kind symbol's own `(id, name, container)` from `collect_query`'s output. `RawInheritanceInputs` derives real `PartialEq`.
- `crates/apex-binder/src/lib.rs`'s Pass 1.5 block: `rebuild_indices()` still runs on every `declarations_changed` exactly as before, but `inherit::resolve_inheritance(...)` now only runs when `raw_inheritance_inputs`'s freshly-fetched value differs *by content* (not `Arc` pointer -- salsa's own early cutoff means a query body can rerun and still return content-equal output) from the previous call's. `inherit.rs`/`resolve_inheritance`/`SymbolTable`'s public API are unmodified.

**Real bug #1, caught by the existing test suite immediately:** `SymbolTable::rebuild_indices()` unconditionally wipes `inherited_chain`/`direct_super`/`unresolved_direct_super`/`subtypes` back to empty, relying on the implicit (undocumented-as-a-hazard) invariant that `resolve_inheritance` always runs immediately after to repopulate them -- true in every call before this ticket, since both were gated by the same `declarations_changed` check. Giving `resolve_inheritance` a narrower trigger broke that invariant: `declaration_changing_edit_via_incremental_cache_matches_a_cold_rebuild` (`tests/incremental_rebind.rs`) failed immediately (`x` unresolved in a class that should still have inherited it from `Base`), the exact shape predicted. Fixed at the root, not patched around: `rebuild_indices()` now carries the four inheritance-related fields forward from the previous `Indices` bundle instead of defaulting them, making it safe to call independently of `resolve_inheritance` -- a more robust invariant regardless of this ticket, not just a Stage-3-specific workaround.

**Real bug #2, found by re-reasoning through the trigger's own soundness before shipping, not caught by any existing test:** comparing only `raw_extends`/`raw_super` content (the design as first written) is unsound on its own -- an *unchanged* `extends Foo` clause can resolve to a *different* target when a same-named type is added, removed, or renamed elsewhere (name resolution shifts even though the clause's own text didn't); and even after bundling every type-kind symbol's `(name, container)` alongside it, a *nested* type's own `SymbolId` shifting because an unrelated declaration (a method, say) was added earlier in the same file would go undetected by `(name, container)` alone, since neither field changes -- leaving `SymbolTable`'s carried-forward `inherited_chain` keyed by a now-stale id. Fixed by including each type-kind symbol's own `id` in the comparison too, not just `name`/`container` -- see `RawInheritanceInputs::type_names`'s own doc comment for the full reasoning. Verified with a new real-corpus test (`a_real_npsp_classs_inherited_chain_survives_an_unrelated_declaration_change_in_another_file`, `tests/incremental_rebind.rs`) mirroring the synthetic fixture's exact shape at real NPSP scale, since a single-shot whole-corpus bind (this stage's own would-be dual-run counterpart) can't exercise an *incremental*, multi-call bug like either of these -- both fixes needed a warm-vs-cold comparison across a real edit, not a static comparison.

**Validation:** full `cargo test -p apex-binder` (226 tests across the lib and every integration suite, including the two new/fixed `incremental_rebind.rs` cases) passes. `cargo bench -p apex-binder -- corpus`, freshly re-baselined against a clean pre-Stage-3 build (ticket 26/29's own re-baselining precedent, not a possibly-stale stored one): `bind_npsp_full` and `warm_rebind_after_one_file_edit` both show "No change in performance detected" (p > 0.05 on both). No separate `salsa_stageN_dual_run.rs` module was added: unlike Stages 1/2, `inherit.rs`/`resolve_inheritance` itself was never rewritten (per ticket 30's own final simplification), so there's no "old algorithm vs new algorithm" pair to dual-run -- the real risk here was always incremental-trigger correctness, which the `incremental_rebind.rs` tests (one fixed, one new) target directly.
