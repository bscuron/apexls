## Question

Given [the research ticket](32-visibility-narrowing-research.md)'s findings, decide `visibility_narrowing_diagnostics`'s concrete architecture: how a candidate's **required visibility** actually gets computed and how the diagnostic wires into `apexls-server`'s merged `publish_diagnostics`, alongside the existing four sources (`syntax_error_diagnostics`, `unresolved_reference_diagnostics`, `dead_code_diagnostics`, `type_mismatch_diagnostics`).

Already settled (do not re-litigate): in-scope transitions (`Public` -> narrower, `Protected` -> `Private`; `Global` out of scope), member kinds (fields/properties/methods/constructors; nested classes deferred), the `dead_code_diagnostics`-verbatim annotation/Visualforce exemption list, the override/interface-implementation exclusion, and `WARNING` severity with no tag.

Resolve, with the user:

- **The reference-bucketing algorithm**, using ticket 32's findings on how to map a reference back to its enclosing declaration and on same-file nested-type private access: for a given candidate, how exactly do references get sorted to arrive at "narrowest safe target" -- e.g. is it a simple three-way classification (same declaring scope / reachable via `subtypes` / anything else), or does it need to be more precise than that?
- **Where the zero-reference / `dead_code_diagnostics` overlap gets resolved** -- lock the actual rule ticket 32 investigated (skip zero-reference candidates, or some other resolution if the research surfaced a real double-flagging scenario).
- **Module/function placement** -- new function in `crates/apexls-server/src/capabilities.rs` alongside its siblings, or does the required-visibility computation itself belong in `apex-binder` (as a `BoundProgram` method, the way `dead_symbols_in_file` lives in `apex_binder` and `capabilities.rs` just formats its output as LSP diagnostics)? The existing pattern splits "prove it" (binder) from "format it" (server) -- confirm this follows the same split.
- **Message wording and the narrower-target's phrasing** -- e.g. `"Method 'foo' is declared 'public' but could be 'private'"` vs. some other phrasing; check against how `dead_code_diagnostics`'s own message (`"{kind} '{name}' is never used"`) and `modifier_diagnostics`'s messages are worded, for consistency.
- **Split off this diagnostic's own implement ticket** once the above is resolved, per this map's established design-ticket -> implement-ticket pattern (e.g. ticket 09 -> 23, ticket 27 -> 29).

Out of scope: re-litigating anything already settled above; nested/inner-class visibility narrowing (a real, separate follow-on); any general per-diagnostic configuration/opt-out mechanism (already out of scope for this whole map).

## Answer

**Module/function placement**: new `crates/apex-binder/src/visibility_narrowing.rs`, module-shaped identically to `dead_code.rs` -- it proves the fact, `apexls-server/src/capabilities.rs` only formats/positions it as an LSP diagnostic. Public entry point: `narrowing_candidates_in_file(program: &BoundProgram, file: FileId) -> Vec<NarrowingCandidate>`, mirroring `dead_symbols_in_file`'s exact per-file signature -- matches every other diagnostic on this map's "prove it in the binder, format it in the server" split, and keeps `capabilities.rs` from needing binder-internal access to `SymbolTable::subtypes`/`references_to`.

`NarrowingCandidate { ptr: SyntaxPtr, name_range: TextRange, kind: SymbolKind, name: SmolStr, current: Visibility, required: Visibility }` -- `required` is always strictly narrower than `current`; nothing is ever constructed otherwise, so the server-side formatter never needs to re-check that invariant itself.

**Candidacy**: `Method | Field | Property | Constructor` with `Visibility::Public | Visibility::Protected` only (matches the map's already-settled scope). Reuses `dead_code.rs`'s full three-part exemption check verbatim -- `has_platform_invocation_annotation`, `is_visualforce_referenced`, and `is_platform_invoked_test_method` (ticket 32's own real-corpus scan caught that the ticket 32/33 chain's originally-settled two-item exemption list, annotation + Visualforce only, was itself incomplete -- a `public`/`protected` `@isTest`/`testMethod` method has no textual call site and would otherwise be misjudged as narrowable) -- plus a new override/interface-satisfaction exclusion (locally reimplemented against `inherited_chain`, same shape as `missing_implementation_diagnostics`'s own interface-satisfaction check, ticket 07/17), plus a locally-reimplemented `top_level_container` walk (following `dead_code.rs:208-211`'s own precedent directly -- no new `SymbolTable` surface exposed for this).

**Zero-reference candidates are skipped entirely**, for both `Public` and `Protected` -- deferring to `dead_code_diagnostics`. Ticket 32 confirmed this makes `Public` disjoint-by-construction from dead-code (zero double-flags across the real NPSP corpus). For `Protected`, this knowingly leaves a gap: a totally-unused `protected` member is caught by neither diagnostic today, since `dead_code_diagnostics` never considers `Protected` candidacy at all (its own doc comment already calls this "a reasonable, cheap future extension... not built yet," `dead_code.rs:36-40`). **Decision: accept the gap as pre-existing and out of scope for this diagnostic.** `visibility_narrowing_diagnostics`'s own identity is "used, but too broadly" -- stretching it to also cover "not used at all" for one visibility level blurs that boundary and patches around a gap that belongs to `dead_code_diagnostics`'s own future-extension scope, not this one's.

**Reference-bucketing algorithm**, computed lazily per candidate at diagnostic-run time (not threaded eagerly into `ReferenceTable::set` at bind time -- ticket 32 found a direct, on-point precedent, `reference_table.rs:374-385`'s `stored_highlight_range` doc comment, where eagerly storing a similar per-reference field "measurably regressed bind time when tried"; this diagnostic runs on-demand, not on the bind hot path, and ticket 32's real corpus numbers -- 5,752 candidates, most with a handful of references each -- bound the lazy cost comfortably):

- New `declaring_type_of_reference(program: &BoundProgram, reference: SyntaxPtr) -> Option<SymbolId>` in `visibility_narrowing.rs`, generalizing `BoundProgram::enclosing_callable`'s ancestor-walk-then-range-match pattern (`lib.rs:1157-1194`) to `ClassDecl`/`InterfaceDecl`/`EnumDecl` instead of `MethodDecl`/`ConstructorDecl` -- exact code already sketched in ticket 32's Answer §1.
- `Protected -> Private`: candidate narrows to `Private` iff *every* reference's `top_level_container(declaring_type_of_reference(ref))` equals the candidate's own `top_level_container`. An unplaceable reference (`declaring_type_of_reference` returns `None`) conservatively blocks narrowing (never assume safety from a reference we can't place).
- `Public -> narrower` (three-way): walk every reference; same-top-level-family contributes nothing; the declaring type itself or a member of `subtypes(declaring)` contributes "needs `Protected`"; anything else -- including an unplaceable reference -- means the candidate stays `Public`, checked immediately (no further narrowing possible once one reference proves it). Result: `Private` if no reference needed `Protected`, else `Protected`, else stays `Public` (and is not emitted as a candidate at all, since `required` must be strictly narrower than `current`).
- Both reimplemented directly against `top_level_container`/`subtypes` rather than through a new parameterized `SymbolTable::is_visible_from`-variant (ticket 32's option (a), the lower-blast-radius choice) -- `is_visible_from` stays exactly as it is today, used only for its existing actual-visibility resolution role; no new crate-wide `SymbolTable` surface is added for a computation only this one diagnostic needs.

**Message wording**: `"{kind} '{name}' is declared '{current}' but could be '{required}'"`, e.g. `"Method 'foo' is declared 'public' but could be 'private'"` -- states both the current and the target explicitly (unlike `dead_code_diagnostics`'s `"{kind} '{name}' is never used"`, which names only the defect) so the message is self-contained without needing to look at the declaration. `WARNING` severity, no `DiagnosticTag` (already settled on the map before this ticket).

**Implement ticket**: [ticket 34](34-visibility-narrowing-implement.md) already exists, split off during charting; its body is being tightened now to this locked design rather than split anew.
