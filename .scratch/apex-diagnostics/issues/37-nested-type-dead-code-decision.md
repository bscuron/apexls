## Question

Given [the research ticket](35-nested-type-candidacy-research.md)'s findings, decide whether and how to extend `dead_code_diagnostics` to flag a nested type (`Class`/`Interface`/`Enum`) that's itself never referenced anywhere -- a real, but much smaller and differently-shaped gap than nested-type narrowing (see [ticket 36](36-nested-type-narrowing-decision.md), the sibling decision ticket ticket 35's research also fed).

Already established by ticket 35 (do not re-investigate, use as given):

- Real NPSP corpus: only 13 of 725 real nested types (~1.8%) have zero references anywhere -- a real but small opportunity, roughly two orders of magnitude smaller than nested-type narrowing's own candidate pool (684 nested types with an explicit visibility keyword) and the original member-level dead-code/narrowing checks.
- `references_to`/`references_to_in_file` and the existing `Private`-is-file-scoped logic reuse **completely unchanged** for a type-level candidate -- `ReferenceTable`/`BoundProgram::references_to` are fully generic over `SymbolId`, confirmed by direct code reading, and ticket 32's own finding that `private` is genuinely file-scoped across a whole nested-class type family (not just the literal declaring class) applies identically to a nested type's own `private` visibility.
- `has_platform_invocation_annotation` does **not** generalize as-is: `PLATFORM_INVOCATION_ANNOTATIONS` (`@AuraEnabled`, `@InvocableMethod`, `@InvocableVariable`, `@RemoteAction`, `@Http*`) only ever annotates a method/property, never a class declaration itself (`annotations_of`, `dead_code.rs:129-163`, returns empty for anything but `Method`/`Property`/`Constructor`/`Field`) -- a type-level exemption channel needs new (but cheap) logic: does the type directly declare (`members_of(id)`) any member carrying one of these annotations, since the platform reaches such a member without a textual reference to the *type* either.
- `is_visualforce_referenced` only ever proves the *top-level* class's own name (`top_level_container`-keyed) -- confirmed empirically that no real VF page in the NPSP corpus ever names a nested class (zero dotted `controller`/`extensions` values across all 80 real `.page` files), and this binder's own VF-parsing (`apex_metadata::visualforce::controller_and_extension_classes`) has no dot-aware parsing path at all. Not conclusively proven from official Salesforce documentation (would need a real page-render test, out of ticket 35's `sf`-CLI-deploy-only methodology) -- flagged as not 100% certain if it matters later.
- `is_platform_invoked_test_method` is **structurally inapplicable**, not just non-generalizing -- confirmed via `sf` CLI that `@isTest`/`@TestSetup` and `static` are both illegal on a nested type (two separate real deploy errors: `"IsTest can only be used on a top level type"`, `"static can only be used on methods of a top level type"`). A nested type can never itself be a platform-invoked test class; this whole exemption channel should be dropped entirely for type-level candidacy, not ported.

Resolve, with the user:

- **Worth building at all**, given the real corpus opportunity is only 13 flaggable candidates in a 725-nested-type, 1,070-file real corpus (~1.8%)? Weigh against: the new logic needed is genuinely small (one new `members_of`-iterating annotation check; everything else reuses unchanged or is dropped outright), so the cost side is also small -- this isn't a "big investment for a tiny payoff" tradeoff the way e.g. cross-method bulkification (ticket 12, deferred) was.
- **If worth building, lock the candidate-kind filter**: research already sketched `matches!(symbol.kind, Class | Interface | Enum) && symbol.container.is_some() && matches!(visibility, Public | Private)` (`Protected` excluded since it's flatly illegal to declare in the first place, per ticket 35 -- there would never be a `Protected` nested type to check anyway; `Global` excluded matching `dead_code.rs`'s own existing "unprovable by local analysis regardless" reasoning for member-level `Global`, independent of the new global-requires-global-outer constraint ticket 35 also found). Confirm/amend.
- **Lock the new type-level platform-invocation-annotation exemption's exact shape** -- e.g. `fn type_has_platform_invoked_member(program, type_id) -> bool { program.symbols.members_of(type_id).iter().any(|&m| has_platform_invocation_annotation(program, program.symbols.get(m))) }` or equivalent; confirm whether this should also recurse into a nested type's *own* nested types (a doubly-nested class), or stop at direct members only.
- **Module/function placement and output shape**: does this become a new function in `dead_code.rs` returning the existing `DeadSymbol` shape (already has a `kind: SymbolKind` field that already supports `Class`/`Interface`/`Enum` without a struct change), folded into `dead_symbols_in_file`'s existing output, or a clearly-separated sibling? `kind_label` (`dead_code.rs:453-466`) would also need new `Class`/`Interface`/`Enum` arms (currently falls through to the generic `"declaration"` label for any kind it doesn't explicitly match).
- **Deletion-range computation**: `compute_deletion_range` (`dead_code.rs:330-369`) currently has no `Class`/`Interface`/`Enum` arm (falls through to `_ => None`, meaning no `deletion_range` would ever be computed, silently excluding every such candidate from `dead_symbols_in_file`'s actual output even if candidacy passed) -- deleting a whole nested type is a single, simple whole-node range (no comma-separated-declarator complexity fields/locals have), but confirm the exact line-alignment behavior needed (leading doc comment, modifiers) matches `Method`/`Property`/`Constructor`'s existing `line_aligned_deletion_range` treatment.
- **Split off this diagnostic's own implement ticket** once the above is resolved, per this map's established design-ticket -> implement-ticket pattern -- or, if the "worth building at all" question resolves no, record that decision and stop here (matching e.g. ticket 12's own deferred-not-built precedent).

Out of scope: nested-type visibility narrowing (see [ticket 36](36-nested-type-narrowing-decision.md)); re-litigating any of ticket 35's own settled findings above.
