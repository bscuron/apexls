## Question

Implement nested-type visibility narrowing per [ticket 36](36-nested-type-narrowing-decision.md)'s locked design, extending `visibility_narrowing_diagnostics` to also flag a nested `Class`/`Interface`/`Enum` whose own declared visibility could be narrowed. Concrete shape, per ticket 36 (do not redesign, implement exactly):

- New candidate-kind filter in `crates/apex-binder/src/visibility_narrowing.rs`: `matches!(symbol.kind, SymbolKind::Class | SymbolKind::Interface | SymbolKind::Enum) && symbol.container.is_some() && symbol.modifiers.visibility == Visibility::Public`. `Public` only -- no `Protected | Public` disjunction the way the member-level filter has, since `Protected` is flatly illegal on a nested type (ticket 35 §1). No interface-body exclusion needed (a nested type inside an interface body isn't a legal Apex shape at all).
- New `required_visibility_for_type(program: &BoundProgram, id: SymbolId, declaring_top_level: SymbolId) -> Option<Visibility>`: a two-way check, no `subtype_set` parameter. Walk `program.references_to(id)`; any reference whose `declaring_type_of_reference` doesn't share `declaring_top_level` (or can't be placed at all) means the type stays `Public`, not narrowable (`None`); if every reference shares the top-level family, the type narrows to `Private` (`Some(Visibility::Private)`).
- New sibling function `type_narrowing_candidates_in_file(program: &BoundProgram, file: FileId) -> Vec<NarrowingCandidate>` alongside the existing `narrowing_candidates_in_file`, reusing the existing `NarrowingCandidate` struct unchanged. Reuses `declaring_type_of_reference`/`top_level_container` from the existing module completely unmodified (ticket 35 §3 confirmed both generalize with zero changes). No exemption chain applies at the type level -- no `overrides_or_implements` equivalent, no platform-invocation-annotation/Visualforce/test-method exemptions (ticket 35 §4: none of these can legally apply to a nested type itself).
- Wire `type_narrowing_candidates_in_file`'s output into `apexls-server/src/capabilities.rs::visibility_narrowing_diagnostics`, merged with the existing member-level candidates into one `Vec<Diagnostic>`. Same `WARNING` severity, no `DiagnosticTag`, same message format: `"{kind} '{name}' is declared '{current}' but could be '{required}'"` (e.g. `"Class 'Foo' is declared 'public' but could be 'private'"`).

Definition of done, per this map's own standing practice (see Notes):
- Benchmark against the real NPSP corpus before landing -- confirm zero false positives across the full corpus. Ticket 35's real-corpus scan (684 nested types with an explicit visibility keyword, 499 already `Public`) is a starting signal, not a substitute for running the real implementation.
- Any disputed real-Apex-compiler-behavior question hit during implementation gets settled via the `sf` CLI against a connected org, not guessed.
- Follows ticket 36's locked message wording, severity, candidate-kind filter, and `required_visibility_for_type` algorithm exactly.

## Answer

Shipped exactly per ticket 36's locked candidate-kind filter, placement, and message wording -- but ticket 36's own `required_visibility_for_type` algorithm turned out to be **wrong**, caught only once real implementation started, not during design:

**The two-way check is unsound as locked.** Ticket 36 argued dispatch-through-a-public-type is handled "for free" because `references_to(type_id)` never sees an external reference when a caller only ever names a wrapping interface. That's true for the interface case, but a real `sf` CLI deploy (not guessed, per this map's own standing practice) found a second, distinct shape it missed entirely: a same-family public accessor whose **declared return type is the concrete nested type itself** (not wrapped in anything) still requires that type's visibility once an external caller chains a call off it -- `Foo.make().greet()` fails to deploy once `Secret` (the real return type of `Foo.make()`) is narrowed to `Private`, with the real compiler error `"Method return type Foo.Secret is not visible for: Foo.Secret Foo.make()"`, even though the external caller's own source never writes `Secret` by name. The leaking reference (the return-type slot inside `make()`) is itself a same-family reference, so ticket 36's plain same-family check never caught it. A second real deploy confirmed `extends` does **not** share this hazard (a public `Sub extends Secret`, with only `Sub` referenced externally, deploys fine) -- inheritance doesn't require the base type's own visibility the way a declared-type slot does, so the fix's scope is deliberately narrower than "every same-family reference."

**Fix**: `required_visibility_for_type` now also rejects a same-family reference when it sits in a still-externally-reachable member's own declared-type slot (a method's return type, or a field/property/parameter's own type) -- new `signature_slot_leaks`, walking to the nearest enclosing `Block` (body position, safe) or `MethodDecl`/`ConstructorDecl`/`FieldDecl`/`PropertyDecl` (a signature slot; blocks narrowing only if that member itself has a real reference from outside the family, matching this diagnostic's whole-map "prove from real usage" philosophy -- a same-family-only accessor's own narrow usage stays genuinely safe to narrow through). Deliberately excludes a class/interface/enum's own supertype clause, per the second deploy above.

A second `/code-review` pass (this map's own established practice) caught a real bug in that first fix: `FieldDecl` needs its own case, not the plain range-match the other three decl kinds share. A `Field` symbol's own `ptr` is its narrower `VarDeclarator` node (`collect::collect_field`), never equal to the whole `FieldDecl`'s range -- and a field's declared type is `FieldDecl`'s own direct child, a *sibling* of each `VarDeclarator` (`public Secret a, b;`'s shared `Secret` belongs to neither declarator alone), so the naive match silently no-op'd the leak guard for every field-shaped leak. Fixed by checking every `Field` symbol sharing that `FieldDecl` and leaking if any is externally reachable. The same review pass raised a real but non-blocking O(references × symbols) performance concern about `signature_slot_leaks`/`has_external_reference`'s nested scans; measured against the real corpus (release build) at 0.50s for the whole type-level sweep -- matching this file's existing linear-scan precedent (`declaring_type_of_reference`, `overrides_or_implements`) and not a real regression at this diagnostic's actual scale, so left as-is rather than adding caching infrastructure nothing currently needs.

**Verification**: 12 new `apex-binder` unit tests for the type-level check (30 total in the module, including the pre-existing member-level ones) plus 1 new protocol-level `apexls-server` test, covering same-family narrowing, cross-family staying-public, the interface-dispatch bypass, the return-type leak (blocked) vs. internal-only-accessor (still narrows), the field-type leak (single and co-declared), and the extends non-leak. Real NPSP corpus: 510 `Public` nested-type candidates (matching ticket 35's ~499 estimate), 182 (36%) flagged as narrowable -- comfortably under this map's 50% conservative-ratio sanity bar. Full `cargo test --workspace` (debug and release) passes clean.
