Type: research
Status: resolved

## Question

What are the most important features apexls is missing to become a genuinely useful tool like rust-analyzer, specifically in code intelligence and diagnostics (not build tooling, not project scaffolding, not unrelated LSP plumbing like workspace-folder handling)?

## Answer

### Summary: apexls is already far more feature-complete than a "missing everything" framing assumes

Before ranking gaps, the single biggest finding of this research is that apexls's own `initialize` handler (`crates/apexls-server/src/lib.rs:657-765`) already advertises, and `crates/apexls-server/src/capabilities.rs` already implements, most of the LSP surface a developer would associate with rust-analyzer: hover (`hover_provider`, `lib.rs:676`, backed by `capabilities::describe_symbol`), goto-definition (`definition_provider`, `lib.rs:684`), find-all-references (`references_provider`, `lib.rs:685`), document highlight (`lib.rs:686`), rename with `prepareRename` (`lib.rs:693-696`), document symbols and workspace symbols (`lib.rs:697-698`), folding range and selection range (`lib.rs:699-700`), code actions (quickfix + refactor-rewrite, `lib.rs:704-712`), call hierarchy (prepare/incoming/outgoing, `lib.rs:713-717`), inlay hints (`lib.rs:718`), completion (`lib.rs:724-728`), signature help (`lib.rs:679-683`), and both push (`publishDiagnostics`) and pull (`textDocument/diagnostic`, `lib.rs:750-757`) diagnostics. Ten diagnostic sources are already merged in `capabilities::diagnostics_for_file` (`capabilities.rs:1140-1156`): `syntax_error`, `dead_code`, `unresolved_reference`, `unknown_schema`, `modifier`, `bulkification`, `unreachable_code`, `missing_implementation`, `type_mismatch`, and `visibility_narrowing` (which itself covers both member- and nested-type-level narrowing, `capabilities.rs:2048-2050`). This means the real gap analysis is not "what capability category does apexls lack entirely" in the broad sense the question's own framing worried about (most categories exist) -- it's narrower: which *specific*, high-value LSP capabilities are still entirely unadvertised, and which *existing* diagnostics ship with no attached remediation, despite already having every fact needed to build one.

Ranked by "biggest code-intelligence/diagnostics win per unit of new `apex-binder` modeling required," reusing data the binder already computes rather than needing new inference:

| Rank | Gap | rust-analyzer/LSP precedent | apexls today | New modeling needed |
|---|---|---|---|---|
| 1 | Semantic tokens (semantic highlighting) | LSP `textDocument/semanticTokens`; ra's own "Semantic Syntax Highlighting" feature | Not advertised at all -- no `semantic_tokens_provider` in `ServerCapabilities` (`lib.rs:657-759`) | None -- reuses the exact `symbol_at`/`resolution_at` pair `hover` already calls per position |
| 2 | Quick-fixes attached to existing diagnostics (esp. visibility-narrowing auto-apply, missing-implementation stub generation) | ra's `Diagnostic` struct has a first-class `fixes: Option<Vec<Assist>>` field | `code_action` only ever produces fixes for one of ten diagnostic sources (`dead_code_actions`, `capabilities.rs:2152-2198`) plus one unrelated refactor (`parameter_reorder_actions`) | Little to none -- both target diagnostics already compute the exact fix payload as part of the diagnostic message itself |
| 3 | Type hierarchy (`prepareTypeHierarchy`/`supertypes`/`subtypes`) | LSP 3.17 `textDocument/prepareTypeHierarchy`, `typeHierarchy/supertypes`, `typeHierarchy/subtypes` | Not advertised -- no `type_hierarchy_provider` in `ServerCapabilities` | None -- `inherited_chain`/`direct_super`/`subtypes` already exist on `SymbolTable` (`symbol_table.rs:111,136,367,380,406`) |
| 4 | Go to Implementation | ra's own named feature: "Navigates to impl items of types" (`Ctrl+F12`) | Not advertised -- no `implementation_provider`; `definition`/`references` only resolve textual references, never an override/interface-satisfaction graph | Little -- the override-matching logic already exists (`missing_implementation_diagnostics`'s `has_required_override`, `capabilities.rs:1928ff`; `visibility_narrowing`'s interface-satisfaction exclusion) |
| 5 (lower) | Code lens ("N references"/"N implementations" above a declaration) | LSP `textDocument/codeLens` | Not advertised -- no `code_lens_provider` | None -- pure UI sugar over `references_to`/`subtypes`, already fully queryable via existing requests |

Everything below expands on each ranked item, cites the exact code proving absence/presence, and explains why it ranks where it does given apexls's own stated destination (`map.md`) and zero-false-positive bar. Items already decided or ticketed elsewhere on the map (a general per-expression `Ty` layer, `Resolution::Candidates`-as-diagnostic, stdlib-interface implementation checking, cross-method bulkification, per-diagnostic config) are deliberately **not** re-recommended here -- see "Explicitly not re-recommended" at the end.

### 1. Semantic tokens (semantic highlighting) -- highest-value, lowest-cost gap

**What rust-analyzer does.** rust-analyzer's own feature-list page names this a first-class, distinctly-branded capability: "Semantic Syntax Highlighting" -- it "assigns a tag (like `struct`) and a set of modifiers (like `declaration`) to each token" so the client can color-map beyond what a static TextMate grammar can express (a TextMate grammar can't tell a mutable local from an immutable one, or a builtin type name used as a value from a real user type) (https://rust-analyzer.github.io/book/features.html, "Semantic Syntax Highlighting" section). The LSP protocol itself defines this as `textDocument/semanticTokens` (full/range/delta variants), advertised via a `semanticTokens` server-capability field (https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/, "Semantic Tokens" section).

**What apexls has today.** Nothing. `ServerCapabilities` in `crates/apexls-server/src/lib.rs:659-758` has no `semantic_tokens_provider` field set at all (confirmed by reading the full struct literal -- every field that *is* set is enumerated above; `semantic_tokens_provider` is simply absent, meaning `ServerCapabilities::default()`'s `None` is what ships). `git grep -n "semantic_tokens\|SemanticTokens"` across `crates/apexls-server/src/` returns zero matches. Apex syntax highlighting in any editor talking to apexls today is whatever static grammar that editor ships, with zero awareness of what the binder actually resolved.

**Why it ranks #1.** This is the purest "already-modeled data, zero new inference" win on the whole list. `Backend::hover` (`lib.rs:861-911`) already does exactly the per-position classification a semantic-tokens handler would need -- `program.symbol_at(file, offset)` for a declaration, then `program.resolution_at(file, offset)` (matching on `Resolved`/`Candidates`/`StdlibMember`/`Label`/`VisualforcePage`) for a reference -- and `Symbol::kind` (`symbol.rs:182`, a `SymbolKind` enum already covering Class/Interface/Enum/Method/Field/Property/Constructor) is already exactly the vocabulary a token-type mapping needs (class/interface/enum/method/property/parameter token types are all standard LSP semantic-token types). Building this is walking every identifier token in a file once, calling the same two functions `hover` already calls per-token, and mapping `SymbolKind`/`Resolution` variant to a standard token type/modifier -- no new binder pass, no new stored fact, nothing that could introduce a false positive (a diagnostics-adjacent property this project cares about elsewhere per `map.md`'s Notes, even though highlighting itself isn't a diagnostic). It would visibly and immediately upgrade the editing experience in exactly the way a developer expects from "like rust-analyzer" -- distinguishing a resolved stdlib call from a project method, an unresolved reference from a resolved one, a static reference from an instance one -- all already known facts the binder throws away today the moment `hover`/`definition` finish answering one query.

### 2. Quick-fixes attached to existing diagnostics

**What rust-analyzer does.** rust-analyzer's `ide-diagnostics` crate models a diagnostic's `fixes` as a first-class struct field, not an afterthought bolted on separately: `Diagnostic { code, message, range, severity, fixes: Option<Vec<Assist>>, ... }` (from the crate's own module doc/source, `crates/ide-diagnostics/src/lib.rs` on rust-lang/rust-analyzer's `master` branch). The module doc's own stated design goal is to preserve enough internal structure "so that we have all the info to make fixes" -- fixes are treated as inseparable from the diagnostic itself, not a separate feature bolted on later.

**What apexls has today.** `Backend::code_action` (`lib.rs:1436-1463`) calls exactly two functions: `capabilities::dead_code_actions` (a "Remove unused X" quickfix, `capabilities.rs:2152-2198`, tagged `CodeActionKind::QUICKFIX`) and `capabilities::parameter_reorder_actions` (a "Rotate parameters left/right"/"Remove parameter" refactor, `capabilities.rs:2200-2245`, tagged `CodeActionKind::REFACTOR_REWRITE` and *not* tied to any diagnostic at all). Of the ten diagnostic sources merged in `diagnostics_for_file`, only `dead_code_diagnostics` has a matching quickfix. The other nine -- `syntax_error`, `unresolved_reference`, `unknown_schema`, `modifier`, `bulkification`, `unreachable_code`, `missing_implementation`, `type_mismatch`, `visibility_narrowing` -- surface a squiggle and nothing else.

Two of those nine are concretely, cheaply fixable with data the diagnostic-producing code already has in hand, which is why this ranks above net-new-modeling items:

- **`visibility_narrowing_diagnostics`** (`capabilities.rs:2041-2071`, backed by `apex_binder::narrowing_candidates_in_file`/`type_narrowing_candidates_in_file`). Each candidate already carries `candidate.current` and `candidate.required` (`Visibility` values) and `candidate.name_range` -- the diagnostic message itself is literally `"{kind} '{name}' is declared '{current}' but could be '{required}'"` (`capabilities.rs:2060-2066`). A quickfix here is a single-token text replacement (swap the visibility keyword at the modifier's own range for `visibility_keyword(candidate.required)`, the same helper the message already calls, `capabilities.rs:2107-2115`) -- structurally identical in shape to `dead_code_actions`'s existing "compute a `WorkspaceEdit` from data the diagnostic already proved" pattern, just replacing text instead of deleting it. Because `map.md`'s own Notes describe this diagnostic's underlying fact as "provably-safe" (the same zero-false-positive bar as every other check on the map), auto-applying it carries no more risk than the diagnostic already accepted by existing design.
- **`missing_implementation_diagnostics`** (`capabilities.rs:1928-1996`). The diagnostic-construction loop already resolves, per missing member, the ancestor's method name, arity, and whether `override` is required (`capabilities.rs:1967-1994`), and `SymbolTable::params(member_id)` (`symbol_table.rs:414`) already returns each parameter's own `Symbol` (each with its own `name` and cached `type_name: Option<SmolStr>`, `symbol.rs:187,217`) plus the member's own `type_name` for the return type. A "Generate stub" quickfix synthesizing `public ReturnType methodName(ParamType paramName, ...) { }` (with `override` when required) is mechanical text assembly from data already gathered for the diagnostic message -- not new inference. This mirrors an extremely common rust-analyzer/IDE assist shape ("implement missing trait members").

**Why it ranks #2, not #1.** It's slightly more implementation work than semantic tokens (constructing valid Apex syntax text for a stub, versus a token-type lookup table), and it improves diagnostics UX rather than baseline editing UX -- but it's the most direct, literal answer to "diagnostics" specifically named in the question, and rust-analyzer's own architecture treats fixes as inseparable from diagnostics, not a separate feature.

### 3. Type hierarchy

**What rust-analyzer/LSP define.** LSP 3.17 added a dedicated three-request protocol: `textDocument/prepareTypeHierarchy` (find the type(s) at a position), then `typeHierarchy/supertypes` and `typeHierarchy/subtypes` to expand a given type item in either direction, advertised via a `typeHierarchy` server-capability field (https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/, "Type Hierarchy" section). This is structurally the same three-request "prepare, then expand-on-demand in one of two directions" shape LSP already defines for call hierarchy.

**What apexls has today.** Nothing advertised (`git grep -n "type_hierarchy\|TypeHierarchy" crates/apexls-server/src/` returns zero matches; no `type_hierarchy_provider` field in `ServerCapabilities`). But the underlying data has existed in `apex-binder` for a long time and is exercised daily by other diagnostics: `SymbolTable::inherited_chain(id)` (`symbol_table.rs:367-372`, the flattened, cycle-guarded ancestor chain), `SymbolTable::direct_super(id)` (`symbol_table.rs:380-383`), and `SymbolTable::subtypes(id)` (`symbol_table.rs:406-410`, "the reverse of `inherited_chain`" per its own doc comment at `symbol_table.rs:404`) are all `pub` today.

**Why this is close to a mechanical port, not new design.** apexls's own `call_hierarchy.rs` (`crates/apex-binder/src/call_hierarchy.rs`) is the existing precedent for exactly this shape: its own module doc comment (`call_hierarchy.rs:1-9`) states it's "computed entirely on demand per request" because "LSP's call-hierarchy protocol is itself lazy/expand-on-demand (prepare, then incoming/outgoing calls per node the user drills into)" -- and then wires `prepare_call_hierarchy`/`incoming_calls`/`outgoing_calls` (`capabilities.rs:2561,2585,2629`) into the matching `Backend` handlers (`lib.rs:1187-1265`). A type-hierarchy sibling module would do the identical prepare/expand-two-directions dance, just walking `direct_super`/`subtypes` instead of a call graph -- the "ambiguous resolution" wrinkle `call_hierarchy.rs`'s own doc comment calls out doesn't even apply here, since inheritance edges (unlike call sites) are never ambiguous in this binder's model.

**Why it ranks #3, below the two above.** It's a smaller everyday-usefulness win than semantic highlighting or diagnostic fixes -- valuable specifically when navigating an Apex codebase's class hierarchy (common in NPSP-style code with deep `fflib_SObjectSelector`-style inheritance and interface satisfaction), but a narrower slice of daily editing than the top two items.

### 4. Go to Implementation

**What rust-analyzer does.** Named explicitly as its own feature, distinct from "Go to Definition": "Navigates to impl items of types" via `Ctrl+F12` (https://rust-analyzer.github.io/book/features.html, "Go to Implementation" section) -- from an interface/trait method, jump to every concrete implementation, the inverse direction of "go to definition."

**What apexls has today.** Nothing. No `implementation_provider` field in `ServerCapabilities`; `Backend::definition` (`lib.rs:1004-1051`) only ever follows `program.resolution_at`'s textual-reference resolution (`Resolved`/`Candidates`/`SchemaObject`/`Label`/`VisualforcePage`) -- there is no path from "cursor on an abstract/interface method's own declaration" to "every concrete override," since that's not a *reference* in the `ReferenceTable` sense at all, it's an override relationship. That relationship is, however, already computed: `missing_implementation_diagnostics`'s own `has_required_override` helper and `visibility_narrowing`'s override/interface-satisfaction exclusion (per `map.md`'s ticket 33/34 entries) both already walk exactly this graph today, just to decide whether to *suppress* a diagnostic, never exposed as its own navigable query.

**Why it ranks #4.** Genuinely useful in an Apex codebase with heavy interface/abstract-class use (NPSP's own `fflib_*` selector/domain layer, `StubProvider` implementers, etc.), but the underlying "which concrete methods satisfy which abstract requirement" matching logic, while it exists, is currently private, diagnostic-specific matching code (`capabilities.rs`'s `has_required_override`), not a general-purpose queryable primitive the way `inherited_chain`/`subtypes` already are for type hierarchy -- so this needs a small real extraction/generalization step first, more than items 1-3 do.

### 5 (lower priority). Code lens

**What LSP defines.** `textDocument/codeLens`, advertised via `codeLensProvider` (https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/, "Code Lens" section) -- an inline, clickable annotation above a declaration (rust-analyzer's own "Annotations" feature: "annotations above items for looking up references or impl blocks and running/debugging binaries," https://rust-analyzer.github.io/book/features.html).

**What apexls has today.** Nothing (no `code_lens_provider` in `ServerCapabilities`). Ranked last because it's pure UI sugar over data already fully reachable through existing requests (`references_to` already backs `references`/`document_highlight`; `subtypes` would back type hierarchy once built) -- a "N references" lens above a method is strictly less information than actually invoking `textDocument/references`, which apexls already serves. Worth doing eventually, not urgent.

### Explicitly not re-recommended (already decided or out of scope elsewhere)

Per this ticket's own instructions, the following are real, known gaps but are **not** re-litigated here because `map.md` already has a live decision or an explicit exclusion covering them:

- **A general per-expression stored `Ty` layer** (hover-style "type of this arbitrary expression," not just a declared symbol's own type) -- `map.md`'s ticket 09 already decided **Option B** (checkpoint-only, inline, no general stored map) "not needed yet." Recommending a general type layer here would contradict a decision already made with more context than this ticket gathered.
- **`Resolution::Candidates` as its own diagnostic** (ambiguous-overload-as-error) -- already listed under `map.md`'s "Not yet specified," with its own stated reason (shape not sharp enough to ticket, real false-positive risk against this project's no-guessing discipline). Not re-proposed here.
- **Stdlib-interface implementation checking** (`Database.Batchable`, `Comparable`, etc.) and **cross-method bulkification** -- both already researched and explicitly **deferred** on the map (tickets 18/20 and 11/12 respectively), each for concrete, already-documented cost reasons. Not re-recommended.
- **General Salesforce security/style lints** (hardcoded IDs, SOQL injection shape, missing `with sharing`) and **a general per-diagnostic config/opt-out mechanism** -- both explicitly listed under `map.md`'s "Out of scope," for reasons unrelated to this ticket's own findings (a different, heuristic-not-provable bar; no proven need yet). Not re-recommended.
- **Formatting** (`textDocument/formatting`/`rangeFormatting`/on-type formatting) -- rust-analyzer's own formatting support is a thin wrapper delegating to `rustfmt`, an external formatter; Apex has no equivalent de-facto-standard formatter to delegate to, and building one from scratch is a large, independent, heuristic-heavy (not "provably correct") effort closer to a style tool than code intelligence -- out of this research's scope by the same reasoning `map.md` already applies to style lints.
