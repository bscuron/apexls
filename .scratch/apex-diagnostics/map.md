Label: wayfinder:map

## Destination

A decision on whether and how to promote `apex-binder`'s walker-internal `Ty` type (`crates/apex-binder/src/ty.rs` -- currently just per-expression type chaining during Pass 2 body resolution, never stored on `BoundProgram` or exposed outside the walker) into a real, queryable, stored type layer, together with a prioritized, zero-false-positive-only spec of new diagnostic checks (structural/flow checks that don't need it, type-checking-flavored checks that do, and provably-safe refactor suggestions like visibility narrowing) to wire into `apexls-server`'s merged `publish_diagnostics` (`crates/apexls-server/src/lib.rs`), alongside the existing sources (`syntax_error_diagnostics`, `unresolved_reference_diagnostics`, `dead_code_diagnostics`, `type_mismatch_diagnostics`). Sequencing between the type-layer decision and the no-inference-needed checks is intentionally left open -- discovered from how tickets actually end up blocking each other, not asserted up front.

## Notes

- Every diagnostic must clear the same zero-false-positive bar `dead_code_diagnostics` already established for this codebase -- never flag unless provably correct. No confidence-graded WARNING/ERROR escape valve (unlike `unresolved_reference_diagnostics`'s existing pattern) unless a specific ticket's own resolution decides otherwise.
- Consult `apex-grammar-oracle-sf-cli` practice (the `sf` CLI against a connected org) for any disputed real-Apex-compiler-behavior question, same as this project's established norm.
- Benchmark any new binder pass against the real NPSP corpus before landing, matching `resolution_regression_baseline.rs`'s existing practice -- this is baked into each implementation ticket's own definition of done, not tracked as a separate cross-cutting ticket.
- BACKLOG.md was **deleted** now that every ticket on this map is resolved -- it was superseded, messy documentation debt once this map became the live planning surface. (Its section 3, "Further diagnostic sources," was this map's starting reference input.)
- This map's destination isn't limited to "the compiler found a bug" checks -- it also covers provably-safe refactor suggestions (e.g. visibility narrowing) as long as they clear the same zero-false-positive bar. General Salesforce security/best-practice lints (hardcoded record IDs, SOQL-injection-shaped queries, missing `with sharing`) stay out of scope regardless (see Out of scope) -- those are heuristic, not provable, a different bar entirely.
- **Required visibility**: the narrowest `Visibility` value (`Private`/`Protected`/`Public`/`Global`, `crates/apex-binder/src/symbol.rs:72-79`) a symbol's actual, real references prove is legally sufficient -- the core concept `visibility_narrowing_diagnostics` computes per candidate. Reuses the existing `Visibility` enum as its value type rather than inventing separate bucket/tier vocabulary.

## Decisions so far

- [Confirm real-org behavior for duplicate/conflicting Apex modifiers](issues/02-modifier-diagnostic-research.md): real org rejects duplicate modifiers (`private private`) and conflicting modifiers (`private public`, `static`+`abstract`) as **semantic deploy-time errors** with specific messages ("Duplicate modifier: X", "Declarations can only have one scope", "static methods cannot be abstract") -- never syntax errors -- so [the implementation ticket](issues/03-modifier-diagnostic-implement.md) belongs as a new `apexls-server` diagnostic, not an `apex-parser` grammar restriction.
- [Survey inherit.rs's existing interface-implementation coverage](issues/06-missing-interface-impl-research.md): `inherit.rs` resolves a flattened, cycle-guarded ancestor-*id* chain but never a flattened "required methods" view; the real blocker for [the implementation ticket](issues/07-missing-interface-impl-implement.md) is that every `implements`/indirect-`extends` name that fails to resolve is silently dropped with zero signal, making every standard-library interface a class implements (`Comparable`, `Iterator`, `Database.Batchable`, ...) invisible today since `SymbolTable` only holds project-local declarations -- not generics or default methods, which Apex has neither of.
- [Survey Ty-promotion feasibility](issues/08-ty-promotion-research.md): `Ty` is computed and thrown away at exactly the spots that matter most (`LocalVarDecl`'s declared-vs-initializer types, `Return`'s expression-vs-method-return-type, and `narrow_by_overload` skipping its own `type_compatible` check whenever arity alone leaves one candidate); the real structural gap for [the architecture-decision ticket](issues/09-ty-promotion-architecture-decision.md) is that `Ty` has no notion of "which expression" (unlike `ReferenceTable`, nothing keys it to a `SyntaxPtr`) and conflates unmodeled-system-types with real schema SObjects -- while NPSP shows the checker must tolerate implicit numeric widening, `Object`-typed variables absorbing dynamic values, and uncast collection covariance, all of which `conversions.rs`'s existing, org-verified rules already model correctly, just not as a validation gate today.
- [Wire the unknown-SOQL/SOSL-schema diagnostic](issues/01-unknown-schema-diagnostic.md): shipped as `unknown_schema_diagnostics`, scoped to `ptr.kind() == SyntaxKind::SoqlFieldName` specifically to avoid a guaranteed false positive on the `<Object>.fields.<Field>` describe-token shorthand (a different, non-error `UnknownSchema` producer). Surfaced and fixed a real, general binder bug along the way: a local custom object's implicit `Name` field (declared via `.object-meta.xml`'s `<nameField>`, never a regular `fields/*.field-meta.xml` file) was never captured by `apex_metadata::discover_sobjects` at all, so every `Level__c.Name`-shaped real-NPSP query misfired -- fixed generally in the shared metadata layer (`apex_metadata::xml::parse_object_meta_name_field`), not patched per-diagnostic.
- [Implement the duplicate/conflicting-modifier diagnostic](issues/03-modifier-diagnostic-implement.md): shipped as `modifier_diagnostics`, purely syntax-tree-based (reads the raw pre-collapse modifier-token list, not the binder's `ModifierSet`). Three rules: duplicate modifier (generalized to any keyword), conflicting visibility, and `static`+`abstract` (scoped to `MethodDecl` only -- the one shape actually org-verified). Zero matches for every triggerable pattern across the whole real NPSP corpus, confirming no false-positive risk.
- [Design the DML/SOQL-in-loop diagnostic](issues/04-dml-soql-in-loop-diagnostic.md): the direct (same-loop-body) rule needs no exemptions at all -- there's no legitimate "already-bulk-operand" escape hatch, so "textually inside a loop body" is exact, not an approximation. `WARNING` severity (a runtime governor-limit risk, not a certain compile-time defect like every other check shipped so far). Covers both keyword-form DML/SOQL and programmatic `Database.*` calls. Cross-method/transitive bulkification is in scope for the eventual diagnostic but needs new call-graph machinery the binder has nowhere today, so it's split into [a research ticket](issues/11-cross-method-bulkification-research.md) blocking [an architecture decision](issues/12-cross-method-bulkification-decision.md) rather than specced here; the direct rule ships independently via [ticket 10](issues/10-dml-soql-in-loop-implement.md).
- [Implement the direct DML/SOQL-in-loop diagnostic](issues/10-dml-soql-in-loop-implement.md): shipped as `bulkification_diagnostics`. Found and handled one real precision issue not foreseen at design time: a naive "any ancestor is a loop" check would have flagged Apex's own canonical bulkified idiom (a SOQL query as a `for`-each loop's own iterable, evaluated once, not per iteration) -- fixed by distinguishing a loop's `body()` from its condition/init/update/iterable positions, while still correctly catching that same query when *its own* loop sits nested inside an outer loop's body (the real N+1 case). Zero false positives across real NPSP files using the SOQL-for-loop idiom.
- [Design the unreachable-code diagnostic](issues/05-unreachable-code-diagnostic.md): v1 is a recursive "definitely terminates" predicate scoped to `Block`/`IfStmt` only (an `if` terminates only with an `else`, both branches terminating), treating `return`/`throw`/`break`/`continue` uniformly as terminators. `ERROR` severity (a certain defect, not a runtime risk). `TryStmt`/`SwitchStmt`/loop-body reasoning is real but gnarlier, deliberately deferred to [its own decision ticket](issues/14-unreachable-code-try-switch-decision.md) rather than attempted now; the narrow slice ships independently via [ticket 13](issues/13-unreachable-code-implement.md).

- [Research nested-type candidacy for visibility narrowing and dead code](issues/35-nested-type-candidacy-research.md): confirmed via `sf` CLI against a real connected org that `protected` is flatly illegal on a nested type ("protected is not allowed on classes") while `global` is legal only when the *enclosing* type is itself `global`; separately confirmed a real "blast radius" hazard the map's own fog note only suspected -- narrowing a nested type's visibility can turn a currently-legal external reference into a compile error even when every individual member's own visibility stays untouched, specifically when the *type itself* leaks into an external declared-type slot (a return type, a variable type), though dispatch through a publicly-visible interface/base type bypasses this entirely. `ReferenceTable` already records type-symbol references via the exact same mechanism as member references (confirmed at every real call site: `resolve_type_ref_base`, `bind_new_expr`, `instanceof`, `extends`/`implements` binding) -- `declaring_type_of_reference`/`top_level_container` generalize to type candidates unchanged, but `required_visibility` does **not**: its `Public` branch can suggest `Protected`, an illegal state for a nested type, so a type-level variant needs its own three-way disjunction. On the dead-code side, `references_to`/`references_to_in_file` and private-file-scoping reuse unchanged, but `is_platform_invoked_test_method` is structurally inapplicable (confirmed via `sf` CLI: `@isTest`/`static` are both illegal on nested types) and `is_visualforce_referenced` only ever proves the top-level class's name (confirmed empirically: zero dotted controller/extensions shapes across all 80 real NPSP `.page` files). Real corpus: the narrowing opportunity (684 nested types with an explicit visibility keyword, 499 already `public`) is roughly two orders of magnitude larger than the dead-code one (13/725 nested types, ~1.8%, have zero references) -- research recommends, without deciding, splitting into two independent decision/implement chains given how differently sized and differently shaped (narrowing carries real correctness hazards dead-code doesn't share) the two gaps turned out to be.

- [Decide nested-type visibility-narrowing's architecture](issues/36-nested-type-narrowing-decision.md): locked a `Public`-only candidate-kind filter (`Class | Interface | Enum`, no `Protected` starting state exists to check for) with no type-level analogue needed for the member-level filter's interface-body exclusion (a nested type declaration inside an interface body isn't a legal Apex shape at all). Built and ran a real fixture confirming, concretely rather than by argument alone, that `references_to(type_id)` already produces zero external references when outside code dispatches only through a public interface, never naming the concrete type -- so the interface-dispatch-bypass hazard ticket 35 §1 found is already handled for free, no new interface-aware logic needed. Since `Protected` is never legal for a nested type, `required_visibility_for_type` collapses to a genuine two-way check with no `subtype_set` parameter at all (any external reference, of any origin, blocks narrowing entirely -- there's no inheritance-only intermediate tier the way `Protected` serves members). Placement: a new sibling function `type_narrowing_candidates_in_file` in the same module, not folded into `narrowing_candidates_in_file` itself, merged by the server-side caller -- the two candidates' filters/exemptions/algorithms differ too much to share one function body cleanly. Message wording and severity stay identical to the existing member-level diagnostic, deliberately not editorializing about the type-level breaking-change risk beyond what the proven-fact message already states. [Ticket 38](issues/38-nested-type-narrowing-implement.md) split off for implementation.

- [Implement `type_narrowing_candidates_in_file`](issues/38-nested-type-narrowing-implement.md): shipped per ticket 36's locked filter/placement/message, but ticket 36's own `required_visibility_for_type` algorithm turned out unsound, caught only during implementation, not design -- a real `sf` CLI deploy found a same-family public accessor whose declared return type is the concrete nested type itself (not wrapped in an interface, unlike ticket 36's own tested bypass) still requires that type's visibility for an external caller chaining a call off it, even though the caller never writes the type's name (`Foo.make().greet()` fails once `Secret` narrows, real error: `"Method return type Foo.Secret is not visible for: Foo.Secret Foo.make()"`); a second deploy confirmed `extends` does *not* share this hazard. Fixed with a new `signature_slot_leaks` check blocking narrowing when a same-family reference sits in a still-externally-reachable member's own declared-type slot (return/field/property/param type only, not a supertype clause). A second `/code-review` pass then caught a real bug in that fix itself: a `Field` symbol's own `ptr` is its narrower `VarDeclarator` node, never equal to the whole `FieldDecl`'s range its own declared type is a sibling of (shared across co-declared fields), so the naive range-match silently no-op'd the guard for every field-shaped leak -- fixed by checking every field sharing one `FieldDecl`. A raised O(references × symbols) performance concern measured at 0.50s for the whole real-corpus sweep (release build), matching this file's existing linear-scan precedent, left as-is rather than adding unneeded caching. Real NPSP corpus: 510 `Public` nested-type candidates (matching ticket 35's ~499 estimate), 182 (36%) flagged narrowable.

## Out of scope

- **Salesforce security/best-practice lints** (hardcoded record IDs, SOQL-injection-shaped dynamic query construction, a class missing `with sharing`) -- BACKLOG.md itself calls this a different *kind* of feature (style/security-review, PMD/Salesforce-Code-Analyzer territory) than "the compiler found a bug." - **A general per-diagnostic configuration/opt-out mechanism** (e.g. `.apexls.toml`, LSP `initializationOptions` severity overrides) -- none of the three existing diagnostic sources have this today; it's an orthogonal config-plumbing feature, not diagnostic *analysis*, and not needed unless a specific shipped check proves it's needed (see Not yet specified).
