Label: wayfinder:map

## Destination

A decision on whether and how to promote `apex-binder`'s walker-internal `Ty` type (`crates/apex-binder/src/ty.rs` -- currently just per-expression type chaining during Pass 2 body resolution, never stored on `BoundProgram` or exposed outside the walker) into a real, queryable, stored type layer, together with a prioritized, zero-false-positive-only spec of new diagnostic checks (both structural/flow checks that don't need it, and type-checking-flavored checks that do) to wire into `apexls-server`'s merged `publish_diagnostics` (`crates/apexls-server/src/lib.rs`), alongside the three existing sources (`syntax_error_diagnostics`, `unresolved_reference_diagnostics`, `dead_code_diagnostics`). Sequencing between the type-layer decision and the no-inference-needed checks is intentionally left open -- discovered from how tickets actually end up blocking each other, not asserted up front.

## Notes

- Every diagnostic must clear the same zero-false-positive bar `dead_code_diagnostics` already established for this codebase -- never flag unless provably correct. No confidence-graded WARNING/ERROR escape valve (unlike `unresolved_reference_diagnostics`'s existing pattern) unless a specific ticket's own resolution decides otherwise.
- Consult `apex-grammar-oracle-sf-cli` practice (the `sf` CLI against a connected org) for any disputed real-Apex-compiler-behavior question, same as this project's established norm.
- Benchmark any new binder pass against the real NPSP corpus before landing, matching `resolution_regression_baseline.rs`'s existing practice -- this is baked into each implementation ticket's own definition of done, not tracked as a separate cross-cutting ticket.
- BACKLOG.md is to be **deleted entirely** once every ticket on this map is resolved -- it's superseded, messy documentation debt once this map is the live planning surface. (BACKLOG.md section 3, "Further diagnostic sources," was this map's starting reference input.)

## Decisions so far

- [Confirm real-org behavior for duplicate/conflicting Apex modifiers](issues/02-modifier-diagnostic-research.md): real org rejects duplicate modifiers (`private private`) and conflicting modifiers (`private public`, `static`+`abstract`) as **semantic deploy-time errors** with specific messages ("Duplicate modifier: X", "Declarations can only have one scope", "static methods cannot be abstract") -- never syntax errors -- so [the implementation ticket](issues/03-modifier-diagnostic-implement.md) belongs as a new `apexls-server` diagnostic, not an `apex-parser` grammar restriction.
- [Survey inherit.rs's existing interface-implementation coverage](issues/06-missing-interface-impl-research.md): `inherit.rs` resolves a flattened, cycle-guarded ancestor-*id* chain but never a flattened "required methods" view; the real blocker for [the implementation ticket](issues/07-missing-interface-impl-implement.md) is that every `implements`/indirect-`extends` name that fails to resolve is silently dropped with zero signal, making every standard-library interface a class implements (`Comparable`, `Iterator`, `Database.Batchable`, ...) invisible today since `SymbolTable` only holds project-local declarations -- not generics or default methods, which Apex has neither of.
- [Survey Ty-promotion feasibility](issues/08-ty-promotion-research.md): `Ty` is computed and thrown away at exactly the spots that matter most (`LocalVarDecl`'s declared-vs-initializer types, `Return`'s expression-vs-method-return-type, and `narrow_by_overload` skipping its own `type_compatible` check whenever arity alone leaves one candidate); the real structural gap for [the architecture-decision ticket](issues/09-ty-promotion-architecture-decision.md) is that `Ty` has no notion of "which expression" (unlike `ReferenceTable`, nothing keys it to a `SyntaxPtr`) and conflates unmodeled-system-types with real schema SObjects -- while NPSP shows the checker must tolerate implicit numeric widening, `Object`-typed variables absorbing dynamic values, and uncast collection covariance, all of which `conversions.rs`'s existing, org-verified rules already model correctly, just not as a validation gate today.
- [Wire the unknown-SOQL/SOSL-schema diagnostic](issues/01-unknown-schema-diagnostic.md): shipped as `unknown_schema_diagnostics`, scoped to `ptr.kind() == SyntaxKind::SoqlFieldName` specifically to avoid a guaranteed false positive on the `<Object>.fields.<Field>` describe-token shorthand (a different, non-error `UnknownSchema` producer). Surfaced and fixed a real, general binder bug along the way: a local custom object's implicit `Name` field (declared via `.object-meta.xml`'s `<nameField>`, never a regular `fields/*.field-meta.xml` file) was never captured by `apex_metadata::discover_sobjects` at all, so every `Level__c.Name`-shaped real-NPSP query misfired -- fixed generally in the shared metadata layer (`apex_metadata::xml::parse_object_meta_name_field`), not patched per-diagnostic.
- [Implement the duplicate/conflicting-modifier diagnostic](issues/03-modifier-diagnostic-implement.md): shipped as `modifier_diagnostics`, purely syntax-tree-based (reads the raw pre-collapse modifier-token list, not the binder's `ModifierSet`). Three rules: duplicate modifier (generalized to any keyword), conflicting visibility, and `static`+`abstract` (scoped to `MethodDecl` only -- the one shape actually org-verified). Zero matches for every triggerable pattern across the whole real NPSP corpus, confirming no false-positive risk.
- [Design the DML/SOQL-in-loop diagnostic](issues/04-dml-soql-in-loop-diagnostic.md): the direct (same-loop-body) rule needs no exemptions at all -- there's no legitimate "already-bulk-operand" escape hatch, so "textually inside a loop body" is exact, not an approximation. `WARNING` severity (a runtime governor-limit risk, not a certain compile-time defect like every other check shipped so far). Covers both keyword-form DML/SOQL and programmatic `Database.*` calls. Cross-method/transitive bulkification is in scope for the eventual diagnostic but needs new call-graph machinery the binder has nowhere today, so it's split into [a research ticket](issues/11-cross-method-bulkification-research.md) blocking [an architecture decision](issues/12-cross-method-bulkification-decision.md) rather than specced here; the direct rule ships independently via [ticket 10](issues/10-dml-soql-in-loop-implement.md).
- [Implement the direct DML/SOQL-in-loop diagnostic](issues/10-dml-soql-in-loop-implement.md): shipped as `bulkification_diagnostics`. Found and handled one real precision issue not foreseen at design time: a naive "any ancestor is a loop" check would have flagged Apex's own canonical bulkified idiom (a SOQL query as a `for`-each loop's own iterable, evaluated once, not per iteration) -- fixed by distinguishing a loop's `body()` from its condition/init/update/iterable positions, while still correctly catching that same query when *its own* loop sits nested inside an outer loop's body (the real N+1 case). Zero false positives across real NPSP files using the SOQL-for-loop idiom.
- [Design the unreachable-code diagnostic](issues/05-unreachable-code-diagnostic.md): v1 is a recursive "definitely terminates" predicate scoped to `Block`/`IfStmt` only (an `if` terminates only with an `else`, both branches terminating), treating `return`/`throw`/`break`/`continue` uniformly as terminators. `ERROR` severity (a certain defect, not a runtime risk). `TryStmt`/`SwitchStmt`/loop-body reasoning is real but gnarlier, deliberately deferred to [its own decision ticket](issues/14-unreachable-code-try-switch-decision.md) rather than attempted now; the narrow slice ships independently via [ticket 13](issues/13-unreachable-code-implement.md).
- [Research cross-method bulkification detection](issues/11-cross-method-bulkification-research.md): real NPSP data (not grep) shows one-hop coverage would miss 62.5% of real cross-method cases (chains run up to depth 9), genuine call cycles exist (`fflib_Criteria`'s composite pattern) alongside `Resolution::Candidates` artifacts that look like self-recursion, 8% of in-loop local calls resolve ambiguously via `Candidates`, and `apex_binder::outgoing_calls` already provides the needed call-graph primitive -- but the transitive fact would need a new Pass 3 (depends on Pass 2's project-wide `Resolution` data) with a materially harder incremental-invalidation story than existing passes, since it's keyed on method-body content rather than declarations. Feeds [the architecture-decision ticket](issues/12-cross-method-bulkification-decision.md).
- [Implement the narrow-slice unreachable-code diagnostic](issues/13-unreachable-code-implement.md): shipped as `unreachable_code_diagnostics`, built on a `stmt_terminates` recursive predicate (`Return`/`Throw`/`Break`/`Continue` always terminate; `Block` terminates if any statement in it does; `IfStmt` terminates only with an `else` where both branches terminate; `try`/`switch`/loops never do). Walks every `Block` independently so nested blocks inside a non-terminating container still get their own unreachable code found. Zero diagnostics across the entire real NPSP corpus (1,035 files, not just a sample).
- [Decide the try/switch/do-while unreachable-code extensions](issues/14-unreachable-code-try-switch-decision.md): build all three despite near-zero real-world frequency in NPSP (zero `switch` statements, zero terminating-`finally` blocks, only 2 `do-while` loops project-wide) -- each is individually sound, and completeness matters for other real Apex codebases. Since the corpus can't validate `finally`/`switch`, [the follow-on implementation](issues/15-unreachable-code-try-switch-implement.md) uses hand-authored tests instead of real-corpus confirmation, an explicit departure from every other check on this map.
- [Implement the try/switch/do-while unreachable-code extensions](issues/15-unreachable-code-try-switch-implement.md): all three wired into `stmt_terminates` exactly per ticket 14's rules, via a small shared `block_terminates` helper. 9 new hand-authored tests (no real corpus examples exist, as anticipated); zero new false positives on a full re-scan of the real NPSP corpus.
- [Decide the cross-method bulkification architecture](issues/12-cross-method-bulkification-decision.md): **deferred**, not built -- the real payoff (226 net-new flaggable loops) doesn't clear the bar against the real cost, an *unsolved* incremental-invalidation design problem (a body-content-keyed transitive fact `apex-binder`'s existing per-file dirty-tracking has no analog for invalidating). The direct-only rule (ticket 10) ships as the complete v1 feature. Transitive-depth and `Resolution::Candidates`-policy answers ticket 11 already found are preserved for whenever this reopens. Follow-on: [research the incremental-invalidation gap itself](issues/16-incremental-invalidation-research.md), a real problem worth solving independent of this one diagnostic.
- [Design the missing-interface/abstract-method-implementation diagnostic](issues/07-missing-interface-impl-implement.md): scoped to **project-local-only** for v1 (zero `apex-binder`-core changes, safely zero-false-positive using existing `inherited_chain` data) -- stdlib-interface coverage (`Database.Batchable`, `Comparable`, ...) is real and arguably more common in practice but needs genuine `apex-binder`-core surgery (recording every failed `implements`/chain-hop resolution, not just the existing single-direct-`extends` signal), split into [its own research ticket](issues/18-stdlib-interface-extension-research.md). Two satisfaction rules confirmed against this project's own existing test fixtures: interface methods need no `override`, abstract-superclass methods require it. Implementation split into [ticket 17](issues/17-missing-interface-impl-implement-task.md).
- [Implement the project-local-only missing-implementation diagnostic](issues/17-missing-interface-impl-implement-task.md): shipped as `missing_implementation_diagnostics`, the first diagnostic on this map bridging syntax tree to real symbol-table data (`inherited_chain`/`members_of`/`params` via `BoundProgram::symbol_at`). The real NPSP corpus check caught a genuine false positive ticket 06's own research missed: an abstract method with **no explicit visibility modifier** (`fflib_SObjectSelector`'s real shape) can be overridden with no `override` keyword at all -- confirmed against a real org, distinct from the explicit-modifier case which does require it. Fixed by keying the override requirement on the abstract declaration's own visibility being explicit. Zero diagnostics on the full corpus after the fix (down from 16 before it).
- [Research the stdlib-interface extension](issues/18-stdlib-interface-extension-research.md): worthwhile in principle (121 of 324 NPSP classes with an `implements` clause name a real stdlib interface) but blocked by concrete gaps in the bundled stdlib snapshot (`Messaging.InboundEmailHandler`, `Database.Stateful`, `Database.AllowsCallouts` entirely unscraped) plus real `apex-binder`-core work: a new unresolved-implements signal, a restored `kind` field on `StdlibClass`, and type-aware overload matching for a genuine `execute()` name collision across `Schedulable`/`Queueable`/`Finalizer`. Inherently unvalidatable via corpus sampling (the real compiler already rejects incomplete stdlib-interface implementations at deploy time). No follow-on decision ticket created yet -- left for whoever picks this back up.

## Not yet specified

- **Type-checking-flavored diagnostics gated by the Ty-promotion decision** (assignment type-mismatch, wrong-argument-type beyond current arity/overload narrowing, etc.) -- can't be scoped until [Decide the Ty-promotion / type-inference-layer architecture](issues/09-ty-promotion-architecture-decision.md) resolves.
- **`Resolution::Candidates` as an error diagnostic** -- genuinely unclear shape (not just "not built yet"): under what conditions an unresolved-overload ambiguity in this binder actually corresponds to a real compiler error is not yet phrased sharply enough to ticket. BACKLOG.md flags real false-positive risk against this project's own no-guessing discipline; needs the `Candidates` cases themselves surveyed before even a research question can be stated.
- **Per-diagnostic opt-out for a specific noisy check** -- e.g. if the bulkification (DML/SOQL-in-loop) check turns out too noisy for some real projects once shipped. Only worth a ticket if and when a specific check's own resolution surfaces this as a real problem; not a general mechanism to build speculatively (see Out of scope).

## Out of scope

- **Salesforce security/best-practice lints** (hardcoded record IDs, SOQL-injection-shaped dynamic query construction, a class missing `with sharing`) -- BACKLOG.md itself calls this a different *kind* of feature (style/security-review, PMD/Salesforce-Code-Analyzer territory) than "the compiler found a bug." This destination is scoped to compiler-error-shaped correctness diagnostics only.
- **A general per-diagnostic configuration/opt-out mechanism** (e.g. `.apexls.toml`, LSP `initializationOptions` severity overrides) -- none of the three existing diagnostic sources have this today; it's an orthogonal config-plumbing feature, not diagnostic *analysis*, and not needed unless a specific shipped check proves it's needed (see Not yet specified).
