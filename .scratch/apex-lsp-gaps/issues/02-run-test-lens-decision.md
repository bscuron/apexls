## Question

Decide the concrete design for `research.md` §3 item 2's "Run Test" code lens (Debug Test excluded -- see the map's Out of scope), reusing test-method detection that already exists purely for dead-code exemption (`ModifierSet::is_testmethod`, `symbol.rs:102,139`; `@isTest`/`@TestSetup` annotation detection, `dead_code.rs:91-117`):

- **Placement.** A `codeLensProvider` lens above every `@isTest` method and every `@isTest` class -- confirm both shapes, and whether a class-level lens (run every test in the class) is distinct from each method-level lens (run just that one method).
- **Invocation mechanism.** Does apexls implement `workspace/executeCommand` itself and shell out to `sf apex run test --tests ClassName.methodName` server-side, or does the lens's `command` field name a client-side command the editor must itself implement? The latter would be non-portable across LSP clients, unlike every other capability apexls ships today -- weigh that against precedent.
- **Result surfacing.** Does apexls parse `sf apex run test`'s own output (JSON via `--result-format json`, or text) and route pass/fail back to the client (a notification, a diagnostic, a lens re-label), or is stdout/exit-code left entirely to whatever the client does with the `executeCommand` response?
- **Confirm the real command shape** via the `sf` CLI directly (per this project's own apex-grammar-oracle-sf-cli practice) -- exact flags, exact output shape, and whether `sf` requires a pre-authenticated default org or needs one specified per-invocation -- rather than guessing.

## Answer

**Placement.** Both shapes, distinct. A class-level `CodeLens` on every `@isTest`-annotated class (its own annotation, not inherited from an outer class), and a method-level `CodeLens` on every `@isTest`/`@TestSetup`/legacy-`testMethod` method -- both computed by one new `capabilities::run_test_lenses` walking `program.symbols.iter().filter(|(_, s)| s.file == file)`, reusing `apex_binder::dead_code::is_platform_invoked_test_method` (newly exported; was `pub(crate)`-only, method-level) and a new sibling `apex_binder::dead_code::is_test_class` (class-level, same `annotations_of`/`has_annotation` plumbing extended with a `SymbolKind::Class` arm). The class-level lens runs every method in the class; the method-level lens runs just that one -- distinct `sf apex run test --tests` argument shapes (`ClassName` vs `ClassName.methodName`), matching `sf`'s own documented class-vs-class.method semantics confirmed via `sf apex run test --help`.

**Invocation mechanism -- server-side `workspace/executeCommand`, reversing this ticket's own initial framing.** apexls declares `executeCommandProvider: { commands: ["apexls.runTest"] }`, and `Backend::execute_command` spawns `sf apex run test` itself via `tokio::process::Command` (the `"process"` Cargo feature was already enabled in `apexls-server/Cargo.toml` but unused in source until now). The lens's own `command` field names this one apexls-owned command with `[className]` or `[className, methodName]` arguments -- no client-side extension needs to implement anything, unlike the rejected alternative (a client-owned command id such as `sf.test.view.run`, which only works in clients that ship a matching extension, e.g. VS Code + Salesforce Extension Pack, and is a silent dead button everywhere else). This was chosen over the ticket's originally-floated concern that server-side would (a) block the async runtime and (b) require apexls to reimplement `sf`'s own default-org resolution: (a) is a non-issue -- `tokio::process::Command`'s `.wait_with_output().await` doesn't block the executor, same non-blocking shape every other `BoxFuture`-returning handler in `lib.rs` already has, no `spawn_blocking` needed since a subprocess wait isn't CPU-bound; (b) is avoided entirely by never passing `-o`/`--target-org` -- see next.

**Org resolution.** `-o`/`--target-org` is never passed. `sf apex run test`'s own `--help` confirms `-o` is "not required if the target-org configuration variable is already set" -- apexls omits it and lets `sf` resolve its own already-authenticated default org exactly as it would from a terminal. Confirmed live: this machine's `sf config get target-org` currently returns empty (no default configured), and `sf apex run test` without `-o` in that state fails with `sf`'s own clear error -- which is exactly the behavior wanted, since `Backend::execute_command` surfaces whatever `sf` reports without apexls ever needing its own "which org" logic, org-config-file parsing, or error-message duplication.

**Exact command.** `sf apex run test --tests <ClassName[.methodName]> --result-format json --json --synchronous`. `--synchronous` is valid here because every invocation targets exactly one class (a class-level lens's whole-class run and a method-level lens's single method are both "one class" per `sf`'s own synchronous-mode restriction) -- avoids polling a test-run ID entirely, one subprocess call gets the final result inline. Both `--result-format json` (frames the *test result* as JSON) and the top-level `--json` (frames the *CLI's own* success/error envelope as JSON) are passed together: confirmed live against the connected org that this combination gives one uniform top-level shape for both outcomes -- `{"status", "result": {"summary": {...}, "tests": [...]}, "warnings": []}` when tests actually ran (confirmed with a real failing test, `LispValueTest`, which failed on a genuine Apex visibility error), and `{"status", "message", "name", ...}` (no `result` key) when `sf` rejects the invocation before running anything (confirmed with an invalid class name) -- so `execute_command` has exactly one JSON parse path, no text-scraping fallback for CLI-level errors.

**Result surfacing.** `Backend::execute_command` parses stdout as JSON: if `result.summary` is present, build a one-line pass/fail summary from `summary.outcome`/`testsRan`/`passing`/`failing` plus each failing test's `MethodName: Message` from `result.tests[]`, and send it via `window/showMessage` (`MessageType::INFO` on an all-passing outcome, `MessageType::ERROR` otherwise); if `result` is absent, use the envelope's own `message` field instead (the CLI-level rejection case). No diagnostics, no per-test codeLens re-labeling, and no `$/progress` reporting around the run in v1 -- deliberately skipped: `workspace/codeLens/refresh`-based re-labeling and a progress Begin/End cycle (mirroring `begin_rebuild_progress`) are both real, addable follow-ups, but a single `window/showMessage` on completion is the minimum that actually closes the loop for v1, and every client shows *something* while an `executeCommand` request is outstanding regardless. Add either if a real client's UX gap asks for it.
