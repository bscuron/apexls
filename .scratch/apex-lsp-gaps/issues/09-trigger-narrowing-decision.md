## Question

Decide the concrete design for `research.md` §3 item 6: narrowing `Trigger.new`/`Trigger.old`/`Trigger.newMap`/`Trigger.oldMap` to the trigger's own declared `on <Object>` type, instead of falling through to the stdlib's generic `List<SObject>`/`Map<Id,SObject>` entry (`apex_reference.json:98173-98226`):

- **Confirm real compiler behavior** for accessing custom fields off `Trigger.new[0].CustomField__c` via the `sf` CLI against a connected org (per this project's own apex-grammar-oracle-sf-cli practice), rather than assuming it works the way it's expected to.
- **Where the narrowing hook belongs** in `resolve.rs`'s `TriggerUnit` handling (lines 519-541) -- special-casing these four property names against the enclosing `TriggerUnit`'s own object type before falling through to the generic stdlib-static-member path.
- **The list/map element type itself.** Does the diagnostic/hover/completion surface need to show `List<Account>` instead of `List<SObject>`, requiring `Ty`/schema-SObject-type plumbing to carry a concrete object identity through the list-element position -- and if so, what's the smallest change to `ty.rs` that does this without a broader `Ty`-layer redesign?
- **Completion-side interaction.** `completion.rs`'s existing `TriggerUnit`-adjacent scope/`enclosing_type` plumbing (`completion.rs:528-539`) -- does narrowing need its own completion-side change too, or does it fall out for free once `resolve.rs` produces the narrower type?

## Answer

**Confirmed real compiler behavior via a live connected org** (`sf project deploy start`, per this project's own apex-grammar-oracle-sf-cli practice), a probe trigger deployed and then removed:

- `trigger T on Account (before insert) { Object x = Trigger.new[0].ThisFieldDefinitelyDoesNotExist__c; }` fails to deploy: `"Variable does not exist: ThisFieldDefinitelyDoesNotExist__c"`.
- Decisive control: `Trigger.new[0].Email` -- `Email` is a real field, just not on `Account` (it's on `Contact`/`Lead`/`User`) -- **also** fails with `"Variable does not exist: Email"`. This rules out the alternative explanation that the compiler merely checks "does this field name exist anywhere in the schema" (which a genuinely untyped `List<SObject>` element could still do, since Apex allows dynamic dot-access on a bare `SObject` as long as the name matches *some* real field): the rejection is specific to `Account`'s own schema, proving `Trigger.new`'s element type is concretely `Account`, not generic `SObject`.
- Positive control: `Trigger.new[0].Name` and `Trigger.newMap.values()[0].Name` (`Name` is real on `Account`) both compile and deploy successfully.

This settles the "is narrowing real" question the ticket's own question raised skepticism about -- it is, unambiguously.

**Where the hook belongs.** Not `resolve.rs:519-541` as the ticket's own question guessed (no `TriggerUnit` literal exists there); the real hook is `apex_binder::resolve::BodyBinder::bind_field_expr`, which already special-cases every other piece of Apex's field-access compiler magic (`.class`, `Label.*`, `Page.*`, `SObjectType.*`, `*.fields.*`) as early intercepts keyed on the receiver's resolved `Ty` and member name, before falling through to the generic stdlib-property lookup. `Trigger.new`/`.old`/`.newMap`/`.oldMap` get one more such intercept, checked when the receiver's `Ty` is `System { name: "Trigger", .. }` and the member name matches one of the four, placed immediately before the existing generic `self.stdlib.class(&object)` / `StdlibIndex::property_of` fallback (`resolve.rs`, ~line 2900) that currently answers all four generically.

The trigger's own declared object comes from `self.enclosing_type`: `lib.rs`'s `SymbolKind::Trigger` arm already passes the trigger's own `SymbolId` as `enclosing_type` into `bind_trigger_body` (contrary to `BodyBinder::enclosing_type`'s own doc comment, which claims it's `None` for a trigger body -- that comment is stale/wrong, not this ticket's concern to fix beyond noting it), and `completion.rs`'s `SyntaxKind::TriggerUnit` arm independently sets the identical `enclosing_type = Some(trigger_symbol_id)` for completion's own receiver-type inference. Both paths already converge on the same fact needed here.

The trigger's declared object *name* itself isn't captured anywhere on the `Trigger` symbol today (`collect_trigger_unit` leaves `type_name: None`) -- add it: `collect_trigger_unit` sets `type_name` to `tu.object_ref()`'s token text (the bare `ON <object>` identifier, already parsed and available, just discarded after `bind_object_ref` resolves it against `schema` once). Reusing the existing `type_name: Option<SmolStr>` field, already present on every `Symbol` for exactly this "declared type text" purpose, needs no new field.

**The list/map element type -- no `Ty`-layer redesign needed, not even a small one.** `Ty::System { name, args }` already carries generic type arguments (`List<Account>` is already representable as `Ty::System { name: "List", args: [Ty::System { name: "Account", args: [] }] }` -- this shape is exactly how every other schema-SObject-typed variable already gets represented, e.g. a plain `Account a;` local). And every downstream consumer of that shape is already generic on `args`, not hardcoded to any particular element type:

- `Expr::Index` (`resolve.rs:2308-2315`) already extracts `args.into_iter().next()` for any `List<T>`-shaped `Ty::System`, regardless of what `T` is -- `Trigger.new[0]` narrows to `Account` for free the instant `Trigger.new` itself resolves to `List<Account>`.
- `crate::generics::builtin_generic_member_type`'s `Map` arm already models `.values()` as `List<V>` and `.get(key)` as `V` generically over `args` -- `Trigger.newMap.values()[0]`/`Trigger.newMap.get(id)` both narrow to `Account` for free too, once `Trigger.newMap` itself resolves to `Map<Id, Account>`.

So the whole fix is: (1) capture the trigger's declared object name at collect time, (2) one new early intercept in `bind_field_expr` that, given a `Trigger` receiver + one of the four member names + a resolvable `self.enclosing_type` naming a `Trigger` symbol whose `type_name` is a real `self.schema.object(...)`, returns `Ty::system_with_args("List", [Ty::system_owned(object, [])])` (`new`/`old`) or `Ty::system_with_args("Map", [Ty::system("Id"), Ty::system_owned(object, [])])` (`newMap`/`oldMap`) instead of falling through to the generic scraped-property type. The `Resolution` recorded stays the identical `Resolution::StdlibMember(StdlibMemberRef { class_name: "Trigger", member: Some("new"), .. })` shape the existing `trigger_context_variables_resolve_to_stdlib_members` test already pins -- hover/goto-definition for `Trigger.new` itself is unaffected; only the *propagated type* for further chaining changes. Falls through unchanged to today's generic `List<SObject>`/`Map<Id,SObject>` behavior whenever the trigger's object name isn't known/registered (defensive, not expected to ever actually trigger in practice, matching this function's existing style of only intercepting when confidently applicable).

**Completion-side interaction -- falls out for free, no `completion.rs` change needed.** `completion.rs`'s `body_binder_for_completion` (used for a receiver like `Trigger.new.|`) builds its throwaway `BodyBinder` with the identical `enclosing_type` completion's own `SyntaxKind::TriggerUnit` ancestor-walk already computes (`completion.rs:528-539`, confirmed already setting `enclosing_type = Some(sym)` to the trigger's own id), then calls the very same `bind_expr`/`bind_field_expr` this decision changes. Once `resolve.rs` narrows the type, completion's receiver-type inference narrows identically with zero code change on the completion side -- exactly the scenario its own doc comment describes reusing `bind_expr` for.
