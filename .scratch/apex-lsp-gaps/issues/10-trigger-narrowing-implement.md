## Answer

Shipped exactly as ticket 09 settled it, three small changes:

- `apex_binder::collect::collect_trigger_unit` now sets the `Trigger` symbol's `type_name` to `tu.object_ref()`'s token text (the `ON <Object>` identifier) instead of leaving it `None` -- reusing the existing field rather than adding a new one.
- `apex_binder::resolve::BodyBinder` gained one new private method, `narrowed_trigger_context_ty(&self, member: &str) -> Option<Ty>`: `None` unless `self.enclosing_type` names a real `SymbolKind::Trigger` symbol whose `type_name` is a real, registered `self.schema.object(..)`, in which case `new`/`old` narrow to `Ty::system_with_args("List", [object])` and `newMap`/`oldMap` narrow to `Ty::system_with_args("Map", [Id, object])`.
- `bind_field_expr` calls it as one more early intercept (same style as the existing `.class`/`Label.*`/`Page.*`/`SObjectType.*` special cases), immediately before the generic `self.stdlib.class(&object)` property fallback that previously answered all four names unconditionally as the scraped `List<SObject>`/`Map<Id,SObject>` types. The recorded `Resolution` is unchanged (still `StdlibMember { class_name: "Trigger", member: Some("new"), .. }`) -- only the propagated `Ty` narrows.

No `ty.rs` change and no `completion.rs` change, exactly as ticket 09 predicted: `Ty::System`'s existing `args` already carry a `List<Account>`/`Map<Id,Account>` shape, `Expr::Index` and `crate::generics`'s `Map` arm are already generic over those `args`, and `completion.rs`'s `SyntaxKind::TriggerUnit` ancestor-walk already sets the identical `enclosing_type` completion's own `body_binder_for_completion` needs to hit the same narrowing through the same `bind_field_expr` call.

**Tests.** New `crates/apex-binder/tests/trigger_context_narrowing.rs`, 4 tests: `Trigger.new[0].Name` and `Trigger.newMap.values()[0].Name` both narrow to `Resolution::SchemaObject { object: "Account", field: Some("Name") }` on an `on Account` trigger (previously these would resolve as `Resolution::Unresolved`, since generic `SObject` has no field model at all); a second trigger declared `on Contact` narrows `Trigger.old[0].LastName` to `Contact`, not a hardcoded default, proving the object comes from each trigger's own declaration; and `Trigger.new` itself still resolves as the identical `StdlibMember` reference the pre-existing `trigger_context_variables_resolve_to_stdlib_members` test already pins, confirming hover/goto-definition on `Trigger.new` is unaffected. All 4 pass; the existing test also still passes unchanged (its fixture references `Trigger.oldMap`/`.isBefore` from inside an ordinary class method, not a real `.trigger` file, so `narrowed_trigger_context_ty` correctly falls through to the generic path there).

**Validation.** Full `cargo test -p apex-binder` (127+ tests across every suite) and `cargo test --workspace` both pass with zero failures, including `resolution_regression_baseline`'s pinned real-NPSP-corpus never-regress counters and `symbol_table_smoke`'s "every real NPSP declaration collects and every pointer resolves" full-corpus sweep -- zero panics. A throwaway harness (`examples/tmp_trigger_narrowing_sweep.rs`, deleted before commit, matching ticket 01/02's own precedent) additionally swept every file's `program.type_mismatches(file)` directly: **0 total type mismatches across all 1,066 real corpus files, 0 in any `.trigger` file** -- confirms the narrower type introduces zero new false positives. (NPSP's own 26 real triggers all route `Trigger.new`/`.old` straight into a generic `TDTM_Config_API.run(...)` dispatcher rather than accessing fields directly in the trigger body itself, so the corpus doesn't exercise the positive case directly -- the new unit tests are what demonstrate the actual narrowing; the corpus sweep demonstrates it introduces no regressions.) `cargo check --workspace` passes.

**Code review caught one real, unintended side effect before landing:** `apexls-server/src/capabilities.rs`'s `document_symbols` unconditionally sets `detail: s.type_name.as_ref().map(|t| t.to_string())` for every outline-kind symbol, and `Trigger` was never excluded from `is_outline_kind` -- so populating `Trigger`'s `type_name` (needed for the narrowing above) would have silently started showing the declared object name as the outline/breadcrumb `detail` for every `.trigger` file, an untested UI change nobody asked for. Fixed by excluding `SymbolKind::Trigger` from that `detail` mapping specifically (`collect_trigger_unit`'s own comment already says this reuse of `type_name` "isn't a real declared type" -- the presentation layer needed to actually honor that). Pinned with a new unit test, `capabilities::tests::a_triggers_outline_entry_has_no_detail_despite_its_repurposed_type_name` (first `#[cfg(test)] mod tests` in `capabilities.rs`), confirming a real trigger's outline entry still has `detail: None`. Re-ran the full workspace suite after the fix -- still zero failures.
