## Decisions so far

- [Implement semantic tokens](issues/01-semantic-tokens-implement.md): shipped as commit `ddb82b9`, deriving every token-type/modifier index from the `SemanticTokensLegend` arrays' own positions instead of hardcoding -- unlike a discarded, in-flight attempt on a since-deleted fleet branch that this ticket's spec was originally recovered from -- and including the encoding-sanity test that attempt was found to have skipped.
- [Research SOQL/SOSL completion's architecture](issues/04-soql-completion-research.md): `apex-syntax` already has a distinct `SyntaxKind` per SOQL clause, so cursor-position detection is a small ancestor-walk addition to `completion.rs::complete_at`, not new architecture -- two real gaps found along the way feed [the decision ticket](issues/05-soql-completion-decision.md): `SchemaIndex` has no object-enumeration method (needed for `FROM`-position completion), and the relationship-chain object-hopping logic lives only as a private single-purpose loop inside `soql.rs::resolve_field_path` (needs extracting into a reusable prefix-lookup helper). Bound-expression (`:var`) positions need no new resolution logic at all -- they already route through the ordinary Apex expression binder. Real NPSP corpus confirms both bare and relationship-chain field lists and heavy `:var` usage in `WHERE`.
- [Research metadata-awareness diagnostic candidates](issues/11-metadata-awareness-research.md): three of the four candidate shapes ($Resource.X, FeatureManagement.checkPermission, named-credential callout:) have **zero real occurrences** anywhere in the ~1,044-file real NPSP corpus; the fourth (`__mdt` custom-metadata usage) is real and common but every occurrence is either ordinary schema-level SOQL already covered by existing discovery, a variable-bound filter, or test-fixture object construction -- never the one literal-string record-lookup pattern that would actually be checkable. Recommends [the decision ticket](issues/12-metadata-awareness-decision.md) conclude "don't build any of them," since there's no real corpus example to develop or validate against -- a recommendation, not a resolution; the decision itself is still open.
- [Decide the Run Test lens's design](issues/02-run-test-lens-decision.md): server-side `workspace/executeCommand` (apexls spawns `sf apex run test` itself via `tokio::process::Command`), reversing this ticket's own initial framing that leaned client-side-command for portability -- server-side turned out to have neither of the two costs that framing worried about (async-runtime blocking is a non-issue since a subprocess wait isn't CPU-bound; org resolution needs no new apexls logic since `-o` is simply never passed, letting `sf` resolve its own already-authenticated default org exactly as it would from a terminal, confirmed live against a connected org with no default configured). Exact command and JSON envelope shape (uniform across both an executed-and-failing run and a CLI-level rejection) confirmed live via the `sf` CLI against a real connected org, per this project's `apex-grammar-oracle-sf-cli` practice, rather than guessed from docs.
- [Research semantic tokens' v1 non-goals](issues/14-semantic-tokens-nongoals-research.md): delta encoding's client-support leg of ticket 01's own reopening criterion is actually already met -- Neovim, Eglot, and VS Code's language client all carry ready-to-use delta code paths today, confirmed by reading each client's own source; apexls's own `full: Bool(true)` capability declaration is the only reason none of them use it. The perf leg doesn't clear the bar on its own (3.66-5.24ms per full computation on the largest real NPSP files, already fast), but the new client-support fact is enough to promote delta encoding to [its own decision ticket](issues/15-semantic-tokens-delta-encoding-decision.md); the other four non-goals (dynamic registration, `workspace/semanticTokens/refresh`, per-token tooltips, extra modifiers) stay deferred with no new ticket -- no real client gap or demand signal found for any of them.
