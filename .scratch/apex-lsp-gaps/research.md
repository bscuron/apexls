## Question

Investigate, against primary sources (apexls's own `apexls-server`/`apex-binder`/`apex-metadata`/`apex-stdlib` source first, then the LSP 3.17 specification itself, then Salesforce's own tooling repos/docs, then rust-analyzer as a maturity comparison point), what is genuinely still missing from apexls to make it feel like a "really great" Apex language server -- both protocol-mechanics gaps against the LSP spec's own capability surface, and Apex/Salesforce-domain gaps against what a professional Apex developer already gets from Salesforce's own VS Code extensions. This is background research only -- no application code was written, built, or refactored.

## Answer

### 1. apexls's current LSP capability surface (grounded in source)

apexls is built on `async-lsp` + `lsp-types = "0.95.0"` (`crates/apexls-server/Cargo.toml`), chosen explicitly over `tower-lsp`/`tower-lsp-server` because `async-lsp` processes notifications *synchronously*, matching what the spec requires for ordering (`crates/apexls-server/src/lib.rs:1-11`). There is no `handshake.rs`/`hover_definition.rs`/etc. file split as separate modules -- the whole LSP crate is four files: `lib.rs` (1454 lines, the `Backend`/`LanguageServer` impl and document-sync/rebuild-worker plumbing), `capabilities.rs` (3072 lines, every capability's pure-analysis-to-LSP-type translation, one `pub(crate) fn` per feature), `line_index.rs` (UTF-8/UTF-16/UTF-32 position-encoding negotiation and conversion), and `main.rs` (18 lines, entry point).

`Backend::initialize` (`crates/apexls-server/src/lib.rs:629-747`) declares the following `ServerCapabilities` (`..ServerCapabilities::default()` at line 739 means every field not listed below is `None`/unset):

- `text_document_sync`: `TextDocumentSyncKind::FULL` (line 676-678) -- a **deliberate, tracked choice**, not an oversight (module doc comment, lines 13-18, 670-676): "the simplest correct baseline for this first pass... worth doing [incremental] once there's a binder-backed feature that would actually benefit from it."
- `position_encoding`: negotiated per client (line 685), via `line_index::PositionEncoding::negotiate` reading `general.position_encodings` from `InitializeParams` (lines 642-647).
- `hover_provider: Simple(true)` (line 686) -- `Backend::hover` (line 842).
- `signature_help_provider`, trigger chars `(`/`,` (lines 689-693) -- `Backend::signature_help` (line 902).
- `definition_provider: Left(true)` (line 694) -- `Backend::definition` (line 985); only follows a *reference's* resolution, never a declaration's own name (doc comment, lines 980-984).
- `references_provider: Left(true)` (line 695) -- `Backend::references` (line 1038).
- `document_highlight_provider: Left(true)` (line 696) -- `Backend::document_highlight` (line 1068), same-file only.
- `rename_provider` with `prepare_provider: Some(true)` (lines 703-706) -- `Backend::prepare_rename` (line 1099) + `Backend::rename` (line 1135), both refusing (`ResponseError`, not silent `None`) via `capabilities::rename_target`'s eligibility check.
- `document_symbol_provider: Left(true)` (line 707) -- `Backend::document_symbol` (line 1250).
- `workspace_symbol_provider: Left(true)` (line 708) -- `Backend::symbol` (line 1278); per its own doc comment (lines 1275-1277), a case-insensitive **substring** match, not fuzzy.
- `folding_range_provider: Simple(true)` (line 709) -- `Backend::folding_range` (line 1299), pure-CST, no bind needed.
- `selection_range_provider: Simple(true)` (line 710) -- `Backend::selection_range` (line 1328).
- `code_action_provider` with exactly two kinds, `QUICKFIX` and `REFACTOR_REWRITE` (lines 711-722) -- `Backend::code_action` (line 1375): dead-code quick-fixes (`capabilities::dead_code_actions`) and parameter-reorder/remove refactors (`capabilities::parameter_reorder_actions`) only.
- `call_hierarchy_provider` (lines 723-727) -- `Backend::prepare_call_hierarchy`/`incoming_calls`/`outgoing_calls` (lines 1168, 1197, 1223).
- `inlay_hint_provider: Left(true)` (line 728) -- `Backend::inlay_hint` (line 961); `capabilities::inlay_hints` (`capabilities.rs:2977-3010`) emits **only** `InlayHintKind::PARAMETER` labels before call arguments -- no other hint kind exists in this codebase (Apex has no local type inference to hint anyway, since every local requires an explicit declared type).
- `completion_provider`, trigger char `.` only, `resolve_provider: Some(false)` (lines 734-738) -- `Backend::completion` (line 932); `capabilities::completion` (`capabilities.rs:2848`) wraps `apex_binder::complete_at`.

Diagnostics are **push-only**: `publish_diagnostics` (`lib.rs:595-623`) is called from the background rebuild worker after every successful rebuild (`lib.rs:559`), merging nine sources (`syntax_error_diagnostics`, `dead_code_diagnostics`, `unresolved_reference_diagnostics`, `unknown_schema_diagnostics`, `modifier_diagnostics`, `bulkification_diagnostics`, `unreachable_code_diagnostics`, `missing_implementation_diagnostics`, `type_mismatch_diagnostics` -- all in `capabilities.rs`, doc comment lines 585-589 of `lib.rs`) into one `textDocument/publishDiagnostics` notification per open file. There is no `textDocument/diagnostic` (pull) handler and no `diagnostic_provider` capability field at all.

Request cancellation (`$/cancelRequest`) needs no server code: `async_lsp`'s `ConcurrencyLayer` (wired in `run_server`, `lib.rs:1429-1435`) intercepts it and aborts the matching in-flight future automatically (module doc comment, `lib.rs:33-41`) -- confirmed by reading `async-lsp`'s own source per that comment, though the doc comment itself admits there's no end-to-end test of it actually cancelling something yet, "since every request handler so far completes near-instantly."

Every request handler snapshots `documents.version`, awaits `wait_for_rebuild` (`lib.rs:340-348`) on it, then reads `bind.program` -- a correctness mechanism (closing a real, previously-observed stale-read race, doc comment `lib.rs:213-229`), not a capability, but worth noting because it means every capability request can block on an in-flight full-project rebuild with **no progress feedback to the client at all** (see gap list below).

### 2. Gap list

#### 2a. Protocol-mechanics gaps (against LSP 3.17)

Spec citations below are drawn directly from fetching `https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/` (the request/notification/`ServerCapabilities`-field enumeration), not a summary of it.

- **Semantic tokens** (`semanticTokensProvider`, spec 3.16+, `textDocument/semanticTokens/full`+`/range`). Not present: `git grep -niE "semantic_token|semanticTokens"` across `crates/apexls-server/src` and `crates/apexls/src` returns zero hits. This is the single largest "editor feels dumb" gap versus rust-analyzer, whose manual/feature page (`https://rust-analyzer.github.io/book/features.html`) opens with "Semantic Syntax Highlighting" as a headline feature: token-level highlighting driven by the binder's own resolved symbol kinds (a field vs. a local vs. a static call) rather than TextMate-grammar guesswork, which is exactly the kind of thing `apex-binder`'s `SymbolTable`/`Resolution` types already have the data for.
- **Code lens** (`codeLensProvider`, `textDocument/codeLens`). Not present (same grep, zero hits). Salesforce's own official Apex Language Server client wires a **code-lens middleware** (`provideCodeLenses`, confirmed by fetching `https://raw.githubusercontent.com/forcedotcom/salesforcedx-vscode/develop/packages/salesforcedx-vscode-apex/src/languageServer.ts`) specifically to surface "Run Test"/"Debug Test" actions above `@isTest` methods and classes (corroborated by search results describing the CodeLens-driven test runner at `https://developer.salesforce.com/docs/platform/sfvscode-extensions/guide/apex-testing.html`). apexls already has the exact symbol data needed to place these lenses (`ModifierSet::is_testmethod`, `symbol.rs:102,139`; `@isTest`/`@TestSetup` annotation detection, `dead_code.rs:91-117`) -- it just never turns that into a lens (or a command to run/debug, which would need org connectivity apexls doesn't have -- see 2b).
- **Document links** (`documentLinkProvider`). Not present (zero hits for `document_link|DocumentLink`). No candidate use surfaced in this pass beyond a possible future "click a custom-label reference to open its `.labels-meta.xml`" -- which `definition_provider`'s `label_location` (`capabilities.rs:132-144`) already covers via goto-definition, so this is low-value.
- **Type hierarchy** (`typeHierarchyProvider`, `typeHierarchy/supertypes`+`/subtypes`, spec 3.17). Not present (zero hits for `type_hierarchy|TypeHierarchy`). `call_hierarchy_provider` exists but its type-level sibling doesn't, despite the binder already tracking supertype/interface-implementation edges for override/inheritance resolution (`crates/apex-binder/src/inherit.rs` exists as a distinct pipeline pass) -- the underlying graph this feature needs is already built for a different purpose.
- **Moniker** (`monikerProvider`, spec 3.16, cross-repo symbol identity for multi-repo tooling like managed-package consumers). Not present. Low priority for a single-workspace tool.
- **Linked editing range** (`linkedEditingRangeProvider`, spec 3.16 -- e.g. renaming a variable name and its declaration site together as you type, before commit). Not present. `rename_provider` already exists as the heavier-weight equivalent; this is a nice-to-have, not a gap that blocks anything.
- **Pull diagnostics** (`diagnosticProvider`, `textDocument/diagnostic`, spec 3.17). Not present -- diagnostics are exclusively server-push (`publish_diagnostics`, `lib.rs:595-623`), which is a legitimate, common architecture (rust-analyzer itself defaults to push), so this is a minor, not major, gap.
- **`window/workDoneProgress` / `$/progress`** (spec 3.15). Not present: zero hits for `WorkDoneProgress|\$/progress` anywhere in `crates/apexls-server/src`. Every capability request can block on `wait_for_rebuild` (`lib.rs:340-348`) for as long as a full-project rebuild takes -- independently measured at **~588ms cold** on the real NPSP corpus (`.scratch/apex-performance/research.md`, citing `target/criterion/corpus/bind_npsp_full/.../estimates.json`) -- with zero client-visible feedback (no "Indexing..." status-bar message) during that window. `start_watcher`'s own doc comment already documents a related ~330ms filesystem-watcher registration cost with no progress reporting either (`lib.rs:365-396`).
- **`declaration_provider` / `type_definition_provider` / `implementation_provider`** (spec 3.14/3.6/3.6). Not set in the `ServerCapabilities` struct (absent from `lib.rs:669-739`, confirmed by reading the full block). `definition_provider` covers the "go to where this is used from" case; the declaration/type-definition/implementation distinctions LSP offers on top of it (e.g. "go to interface method's implementation(s)", relevant given Apex interfaces/abstract classes are common) have no dedicated capability, though `call_hierarchy` and `references` partly substitute.
- **Formatting** (`documentFormattingProvider`/`documentRangeFormattingProvider`/`documentOnTypeFormattingProvider`, `colorProvider`, `executeCommandProvider`). None set. Notably, `apex-printer` (`crates/apex-printer/src/lib.rs:1-14`) is a **lossless round-trip renderer only** (`render(parse(source)) == source`, byte-for-byte) -- it has zero reindentation/pretty-printing logic, confirmed by reading its full ~25-line implementation (`SyntaxNode::text()` concatenation). It is only ever invoked from the `apexls` CLI's `ast.rs:42` for AST-dump verification, never from `apexls-server`. A real formatter is not "not wired up" -- it doesn't exist as a capability at all yet.
- **`workspace.fileOperations`** (`willRenameFiles`/`didRenameFiles`/etc., spec 3.16) and **`workspace.workspaceFolders`** (spec 3.6). Not set (`ServerCapabilities.workspace` is `None`, confirmed via the same full-block read) -- consistent with the module doc comment's explicit **single-root-only, by design** stance (`lib.rs:20-31`): apexls ignores every workspace folder past the first, so multi-folder-aware capabilities like `workspace.workspaceFolders` would be actively misleading to advertise.
- **`notebookDocumentSync`, `inlineValueProvider`** (both spec 3.17). Not present; not applicable to Apex (no notebook format, and `inlineValue` is a debug-session feature apexls has no debug adapter to pair with -- see 2b).

#### 2b. Apex/Salesforce-domain gaps

- **No SOQL/SOSL-aware completion.** `crates/apex-binder/src/completion.rs:11-15`'s own module doc comment states outright: "v1 scope (see `BACKLOG.md`'s completion entry): member-access and bare-identifier contexts only -- no SOQL/SOSL completion, no snippets, no auto-import, no `completionItem/resolve`." This is despite SOQL/SOSL field-chain *resolution* already existing and being fairly deep -- `crates/apex-binder/src/soql.rs` resolves dotted field chains (`Owner.Name`) against `SchemaIndex`, hopping through `reference_to` relationships, and binds `:var` expressions back into the enclosing Apex scope. The gap is specifically that none of this resolved schema data is surfaced as completion candidates while typing inside `[SELECT ... FROM ...]`. Salesforce's own official Apex extension treats this as important enough to gate behind a whole companion extension (`enableEmbeddedSoqlCompletion`, confirmed in `languageServer.ts` fetched above) -- apexls has the harder half (resolution) already built and is missing only the completion-surface half.
- **No `completionItem/resolve`.** Same doc comment (`completion.rs:11-15`) plus `lib.rs:736`'s `resolve_provider: Some(false)`: documentation is deliberately never fetched per candidate (`CompletionCandidate`'s own doc comment, referenced but not embedded in `completion.rs`), for perf reasons stated inline. Reasonable tradeoff, but means completion popups never show a stdlib method's doc text the way most real IDEs do (apexls already has the doc text -- `apex_reference.json`'s scraped `description` fields -- just doesn't surface it lazily here; `describe_stdlib_member`, `capabilities.rs:312`, does show it in *hover*, so the data exists, only the completion-resolve wiring is missing).
- **Trigger context variables typed generically, not narrowed to the trigger's own object.** `crates/apex-stdlib/data/apex_reference.json:98173-98226` (the scraped `System.Trigger` class entry) types `Trigger.new`/`Trigger.old` as the literal string `"List<SObject>"` and `Trigger.newMap`/`oldMap` as `"Map<Id,SObject>"` -- generic, not parameterized per trigger. `git grep -n '"Trigger"'` across `crates/apex-binder/src` and `crates/apex-parser/src` returns **zero** matches, and neither `resolve.rs` nor `completion.rs` contains any `TriggerUnit`-specific narrowing logic beyond scope/`enclosing_type` plumbing (`resolve.rs:519-541`, `completion.rs:528-539`) -- so `Trigger.new` almost certainly resolves through the same generic stdlib-static-member path as any other `System.*` class reference, meaning `Trigger.new[0].AccountField` (a very common real-world pattern for a trigger declared `on Account`) would only expose generic `SObject` members via that chain, not the trigger's actual custom fields. Not confirmed end-to-end by a live test in this pass -- flagged as a strong inference from the data model plus the absence of any narrowing code, not a directly observed failure.
- **Metadata types entirely excluded from discovery: permission sets, static resources, custom metadata *records* (as opposed to type schema), profiles, flows, layouts, named credentials, custom permissions, and more.** `crates/apex-discover/src/skip.rs:42-90` lists all of these by name in its `SKIP` phf-set, pruned from every directory walk. Custom object/field *schema* -- including for `__mdt` custom metadata type definitions, which live under the same `objects/` tree -- is still picked up, since `should_skip_dir_keep_metadata_dirs` explicitly excludes `objects`/`fields`/`pages`/`labels` from pruning (`skip.rs:1-6`, `104-110`ish). The genuinely lost surface is narrower than "everything's missing": it's specifically things an Apex expression can reference by string literal or merge field with no structural schema to check against today -- e.g. a Visualforce `$Resource.MyStaticResourceBundle` merge field, a `FeatureManagement.checkPermission('My_Custom_Permission')` string argument, or a `Named_Credential__c`/`callout:My_Named_Credential` callout endpoint -- none of which apexls can validate exists, because the underlying XML is never even parsed.
- **No managed-package symbol resolution.** No code anywhere models an installed managed package's namespace-prefixed classes/objects (only `strip_namespace_prefix` exists, `conversions.rs:207,226,276`, which *strips* a namespace prefix for stdlib-parameter-name comparison purposes -- unrelated to resolving a symbol that actually lives in another package). A real Salesforce dev project referencing `MyPackage.SomeGlobalClass` would see that reference go `Unresolved` in apexls today, since there's no local source and no bundled snapshot for a third-party package the way there is for standard objects/stdlib. This is a fundamentally hard problem (no local source, and apexls explicitly has zero org connectivity -- see next point) with no cheap fix.
- **No org connectivity at all -- by design, and mostly already compensated for.** `crates/apex-metadata/src/lib.rs:14-24`'s module doc comment frames "standard objects/fields have no local metadata... resolving needs either a bundled snapshot... or a live describe call against a connected org" as "deliberately left as an open decision" -- but this doc comment is **stale**: `crates/apex-stdlib/src/lib.rs:1-14` confirms the bundled-snapshot path was actually taken (`standard_sobjects()`/`standard_classes()`, scraped from Salesforce's own docs via `tools/salesforce-doc-scraper`, embedded at compile time, ~11MB `standard_objects.json` + ~3.8MB `apex_reference.json` under `crates/apex-stdlib/data/`). So the *standard*-schema half of "no org connection" is already solved well; what's left unaddressed is anything genuinely org-specific and undeployed-to-source: a managed package's own symbols (previous bullet), live org-side customizations not yet in the repo, and anything requiring the Tooling API at runtime (which the codebase's own dev practice already uses `sf apex run` for -- see `conversions.rs:14`, `resolution_regression_baseline.rs:308,692` -- but only as an offline *oracle* to verify hand-written binder rules against, never as a runtime dependency of the shipped server).
- **No test-run/debug integration of any kind.** No code anywhere invokes `sf`/Tooling API to run a test, no code lens for "Run Test"/"Debug Test" (see 2a), no Apex Replay Debugger equivalent (no Debug Adapter Protocol implementation at all in this repo -- confirmed by the absence of any `dap`/`debug_adapter` crate or dependency in the workspace `Cargo.toml`/any crate's `Cargo.toml`). Salesforce's own `salesforcedx-vscode-apex-replay-debugger` extension (README fetched from `https://raw.githubusercontent.com/forcedotcom/salesforcedx-vscode/develop/packages/salesforcedx-vscode-apex-replay-debugger/README.md`) replays a downloaded debug log "similarly to an interactive debugger," and its sibling docs describe checkpoints capturing heap dumps at up to five lines (`https://www.avenoir.ai/...`/search-corroborated; the canonical doc page 403'd to automated fetch but the GitHub README and search results corroborate the same feature set). This is a large, separate subsystem (DAP + debug-log parsing + org connectivity), not a small gap.
- **No Anonymous-Apex execution command.** apexls already *parses* anonymous blocks (`tests/golden/anonymous-blocks/` exists as a golden-test category), but there's no `workspace/executeCommand`-style "run this as anonymous Apex against my org" the way Salesforce's official extension exposes via its separate `apex-anon` language id (confirmed in `languageServer.ts`: `{ language: 'apex-anon', scheme: 'file' }` as a distinct registered document selector). This is inherently an org-connectivity feature, same caveat as test-run integration.

### 3. Synthesis: what would move the needle most (opinion, not sourced fact)

This section is my own ranking, not a claim any source makes -- it weighs developer-experience impact against how much of the needed underlying data apexls's existing parser/binder/stdlib/metadata layers already provide (i.e., "cheap because the hard part is already built" vs. "cheap because the feature itself is small").

1. **Semantic tokens (`semanticTokensProvider`).** Highest DX impact per unit of new code: `apex-binder`'s `SymbolTable`/`Resolution`/`Ty` types already classify every identifier occurrence precisely (a field vs. local vs. static call vs. unresolved), which is exactly rust-analyzer-grade semantic highlighting's core input. Client-side, this alone changes an editor from "generic Apex syntax colors" to "colors that reflect what your code actually resolves to" -- a difference every rust-analyzer/clangd/gopls user would immediately notice is missing. Cost: moderate (a new token-type/modifier scheme, an LSP capability declaration, a walk over each file's already-resolved references), no new binder work needed.
2. **A "Run Test"/"Debug Test" code lens, even without org integration at first.** `ModifierSet::is_testmethod` and `@isTest`/`@TestSetup` detection already exist (`symbol.rs:102,139`; `dead_code.rs:91-117`) purely for dead-code exemption -- reusing that same data to place a lens is nearly free. Even a lens that just shells out to `sf apex run test --tests ClassName.methodName` (matching the exact workflow professional Apex devs already use daily, per the official extension's CodeLens-driven test runner) would close one of the most-felt gaps versus Salesforce's own tooling, without requiring apexls to grow real org-awareness or a DAP implementation.
3. **Progress reporting (`$/progress`/`window/workDoneProgress`) around rebuilds.** Cheap, mechanical (the rebuild worker already knows exactly when it starts/finishes, `lib.rs:467-569`), and directly addresses a real, already-measured latency window (~588ms cold, ~330ms watcher registration) that currently gives the user zero feedback. Low implementation risk, no interaction with the ongoing salsa migration.
4. **SOQL/SOSL-aware completion.** The resolution engine (`soql.rs`) already does the hard part; only the completion-surface wiring (`completion.rs`) is missing, by that module's own admission. This is likely the single most Apex-developer-visible "why doesn't this basic thing work" gap, since writing a SOQL query inline is one of the most common things an Apex developer does, constantly, and today gets zero completion assistance inside the query itself.
5. **Type hierarchy (`typeHierarchyProvider`).** `apex-binder`'s `inherit.rs` pass already computes the supertype/interface graph this needs. Given Apex's heavy use of interfaces and abstract base classes (dependency-injection patterns, trigger-handler frameworks), a supertypes/subtypes view is a natural, low-risk addition riding on data that already exists for a different pass.
6. **Narrowing `Trigger.new`/`Trigger.old` to the trigger's declared object type.** Narrower in scope than the above, but a real correctness/usefulness gap for one of the most common Apex code shapes (every trigger touches `Trigger.new`). Needs a small, targeted addition in `resolve.rs`'s `TriggerUnit` handling to special-case these four properties against the trigger's own `on <Object>` clause rather than falling through to the generic stdlib entry -- a contained, well-scoped change given the binder's existing architecture.
7. **Permission-set/static-resource/custom-metadata-record awareness** (validating `$Resource.X`, `FeatureManagement.checkPermission('X')`, etc.) is real but lower-leverage: it requires parsing several more metadata XML shapes for comparatively rare validation payoff versus the items above, and (per the zero-false-positive diagnostic bar this codebase already holds itself to, per its own diagnostics-map conventions) would need careful scoping to avoid false positives on dynamically-constructed resource names.
8. **Managed-package symbol resolution and full org/test/debug integration** are real, named gaps but are large, cross-cutting subsystems (org auth, Tooling API client, DAP implementation, debug-log parsing) rather than incremental features -- correctly last on a leverage-vs-cost ranking given everything else on this list is buildable directly on data apexls already has in-process.
