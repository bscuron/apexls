## Question

Investigate, against primary sources (apexls's own source/benches/profiling harnesses first, then the upstream projects it's built on -- rowan, salsa, rayon, and rust-analyzer as the closest architectural precedent), what would dramatically improve apexls's performance. This is a standalone survey, not a continuation of the `.scratch/apex-diagnostics/` wayfinder map's ticket chain (that map's own destination is scoped to diagnostics + the binder's staged salsa migration specifically) -- it does not re-litigate anything tickets 16/21/25/27/28/30/31 already settled about salsa's staged adoption, but it does flag where an opportunity found here overlaps with that map's still-open Stage 4 (Pass 2/Resolve) work.

Establish, concretely, for each opportunity: what it is, why it matters for apexls specifically (tied to a real hot path, doc comment, or benchmark number already in this codebase), the primary source backing it, and a rough cost/risk sense -- ranked by leverage, not just listed.

## Answer

### Grounding: what apexls's own numbers and doc comments already say

- Cold full-project bind (`corpus/bind_npsp_full`, ~1,044-1,070 real NPSP files): **~588ms** measured mean (`target/criterion/corpus/bind_npsp_full/clean-master/estimates.json`, `mean.point_estimate` = 588027950ns; a `new` run in the same tree measures 598033500ns).
- Warm rebind after one file's edit (`corpus/warm_rebind_after_one_file_edit`): **~6.3-7.0ms** measured mean (`target/criterion/corpus/warm_rebind_after_one_file_edit/{clean-master,new}/estimates.json`).
- `crates/apex-binder/examples/mem_profile.rs:1-10`'s own doc comment: apexls-server's steady-state resident memory is **~180-200MB** against the real NPSP corpus, and the harness exists specifically to attribute it to "a `BindCache` *and* a separately-owned `BoundProgram` snapshot alive at once" in `apexls-server`'s `BindState` (`crates/apexls-server/src/lib.rs`'s `program: RwLock<Option<BoundProgram>>` plus `cache: Mutex<BindCache>`, both held for the process's whole lifetime).
- `crates/apexls-server/src/lib.rs:1-68`'s module doc comment: document sync is **full, not incremental**, by explicit tracked choice; request cancellation only aborts LSP *request* futures via `async-lsp`'s `ConcurrencyLayer` (confirmed by reading `async-lsp`'s own source, not tested end-to-end because "every request handler so far completes near-instantly"); the background rebuild worker itself has **no cancellation or debouncing** of a rebuild a newer edit has already superseded -- it coalesces bursts into "one more rebuild after the current one finishes" (`BindState::rebuild_requested`'s doc comment, `crates/apexls-server/src/lib.rs:241-264`) but never aborts an in-progress rebuild.
- `crates/apex-binder/src/lib.rs:1-19` + `db.rs`'s own comments: the three-pass pipeline (Collect/Inherit/Resolve) is salsa-tracked through **Stage 3** (indices, per-file parse+collect, Pass 1.5/Inherit's early-cutoff trigger); **Pass 2 (Resolve, `resolve.rs`, 3,767 lines -- the single largest module in the binder) is still the old `rayon`-parallelized, `BindCache`-diffed path**, unconditionally re-run for every file whenever any file's declarations change (per the diagnostics map's own ticket 16 finding, `crates/apex-binder/src/lib.rs:228-233`-area comment). This is tracked in the diagnostics map as "Stage 4, not yet specified."
- `crates/apex-binder/src/lib.rs:276-716` already has per-stage `hotpath::measure_block!` instrumentation (`discover_and_build_schema`, `stage_1a_check_freshness`, `pass1_collect_dirty_files`, `pass1_5_inherit_and_rebuild_indices`, `pass2_bind_symbol_bodies`, `pass2_bind_supertypes`, `pass2_merge_bodies`) and a runnable `cargo run -p apex-binder --release --features hotpath,hotpath-alloc --example cpu_profile` harness -- but no stored breakdown output exists in this checkout, so which of those stages actually dominates the ~588ms cold bind is not yet known from data on disk; running that harness is a near-zero-cost first step before investing in any of the opportunities below.
- Root `Cargo.toml` has **no `[profile.release]` section at all** (confirmed by reading the file in full) -- every release build uses Rust's stock release defaults (`opt-level = 3`, `codegen-units = 16`, `lto = false`, `panic = "unwind"`, `debug = false`). No global allocator override exists in either production binary (`crates/apexls/src/main.rs`, `crates/apexls-server/src/main.rs`); `mimalloc`/`dhat`/`hotpath::CountingAllocator` only appear in dev-only profiling examples (`crates/apex-binder/examples/{cpu_profile,mem_profile}.rs`), never wired into the shipped `apexls`/`apexls-server` binaries.
- `crates/apex-binder/src/lib.rs:176-178`: the stdlib index (`global_stdlib_index()`) is a process-wide `OnceLock<Arc<StdlibIndex>>`, built once and deliberately excluded from `BindCache`'s own rebuild/invalidation entirely -- already effectively infinite-durability and outside any per-edit cost, so salsa's own "durability" feature (below) would add nothing here; it's already solved better than durability solves it.

### Ranked opportunities

**1. Add a `[profile.release]` to the workspace `Cargo.toml` (thin LTO, `codegen-units = 1`, `panic = "abort"` for the binaries).**
Why it matters: apexls ships two real binaries (`apexls`, `apexls-server`) that run release builds with the Rust compiler's *default* release profile -- `codegen-units = 16` deliberately sacrifices cross-unit inlining for parallel compile time, which is the wrong tradeoff for a shipped binary that's compiled once and run many times, especially across `apex-lexer`/`apex-parser`/`apex-binder`'s tight, hot, call-graph-heavy code (large recursive-descent parser, per-token lexer loop, per-body resolution walk). This is a pure build-configuration change, touches zero source code, and is the single highest-leverage-for-effort item on this list.
Source: this is a standard, well-documented Cargo mechanism (`[profile.release] lto = "thin"` or `"fat"`, `codegen-units = 1`, `panic = "abort"`) -- confirmed absent from this repo's own `Cargo.toml` by direct inspection; not sourced from a third party since the claim being verified is "apexls doesn't already do this," not general LTO advice.
Cost/risk: low. `panic = "abort"` changes unwind-based behavior (`crates/apexls-server/src/lib.rs`'s own tests rely on `parking_lot`'s non-poisoning locks surviving a `catch_unwind`'d panic inside the *test* process -- verify that test still makes sense/still runs under `panic = "unwind"` in the `dev`/`test` profile, which is unaffected by a `[profile.release]`-only change; the LSP server itself has no documented reliance on catching a panic in production, so `abort` there is likely fine, but confirm before flipping it, and consider `lto = "thin"` first since `"fat"` sometimes regresses debug/incremental build times or has unexpected inlining side effects that would need a `cargo bench` re-baseline per the map's own established practice). Independent of the salsa migration -- can land any time.

**2. Once Pass 2 (Resolve) migrates onto salsa (Stage 4), add an explicit `db.unwind_if_revision_cancelled()` cancellation checkpoint inside its per-body walk, replacing "coalesce the next rebuild" with "abort the current one."**
Why it matters: `crates/apexls-server/src/lib.rs`'s own doc comments describe the *only* existing mitigation for "an edit lands while a rebuild is in flight" as coalescing -- letting the current rebuild finish, then running exactly one more covering everything since. On a large real project (NPSP-scale, ~588ms cold) a burst of fast keystrokes during an expensive Pass 2 walk still waits out the full in-flight rebuild before the next one starts, which is exactly the kind of input-lag tail salsa's cancellation model exists to remove. Salsa's own tuning guide states plainly that automatic cancellation only fires at query-call boundaries -- "long loops without intermediate query calls won't be automatically cancelled... manually invoke `db.unwind_if_revision_cancelled()`" (https://salsa-rs.netlify.app/tuning) -- so a naive migration of Pass 2's per-body loop onto salsa would *not* get this for free; it has to be added deliberately inside `resolve.rs`'s own body-walk loop. rust-analyzer's own architecture doc confirms this is exactly the mechanism it relies on: "The salsa database maintains a global revision counter. When applying a change, salsa bumps this counter and waits until all other threads using salsa finish... [queries] panic with a special cancellation marker, caught at the `ide` boundary" (https://rust-analyzer.github.io/book/contributing/architecture.html, "Cancellation" section); salsa's own cancellation is documented as panic-based, caught via `Cancelled::catch` (https://docs.rs/salsa, confirmed via `salsa-rs/salsa`'s own `tests/parallel/cancellation.rs` and open issue discussion at https://github.com/salsa-rs/salsa/issues/447 on `unwind_if_revision_cancelled`'s naming/visibility history).
Source: salsa's own tuning guide + rust-analyzer's own architecture doc, both primary.
Cost/risk: medium -- this is squarely inside Stage 4's own not-yet-designed scope (the diagnostics map's "Salsa migration, Stage 4's own ticket" entry under "Not yet specified"), so it shouldn't be built standalone; flag it as a concrete requirement to fold into that ticket's own design once it's written, not a separate effort. It also changes `apexls-server`'s worker semantics (an aborted rebuild publishes nothing for that revision, so `bound_version`'s "always an honest floor" invariant, `crates/apexls-server/src/lib.rs:213-229`, needs re-verifying against a world where a rebuild can be thrown away mid-flight rather than only ever completing).

**3. Wire a non-default global allocator (`mimalloc`) into the two shipped binaries, matching the choice already validated (for profiling purposes) in `crates/apex-binder/examples/mem_profile.rs`/`cpu_profile.rs`.**
Why it matters: `hotpath`'s own `CountingAllocator` and `dhat`'s allocator are already pulled in as dev-dependencies for profiling, meaning apexls's own team has already reached for allocator-level tooling to understand its memory behavior -- but the *shipped* binaries (`crates/apexls/src/main.rs`, `crates/apexls-server/src/main.rs`) use the system allocator, unconditionally. Given the binder's own workload -- Pass 1/Pass 2 both `rayon`-parallelized (`crates/apex-binder/src/lib.rs:429,522,648,677`), meaning many threads allocating/freeing small `SmolStr`/`Vec`/`FxHashMap` entries concurrently during a bind -- a concurrent-allocator-aware allocator (mimalloc, already a workspace-adjacent concept via the profiling examples) is a well-known, low-effort win for exactly this shape of workload (many small, short-lived, cross-thread allocations).
Source: this is a general Rust-ecosystem technique, not sourced from apexls-specific docs, so weight it lower than items directly grounded in this codebase's own measured numbers -- listed because the codebase already gestures at allocator-awareness via its profiling harnesses, making this a natural, cheap next step, not because a source claims a specific speedup for apexls.
Cost/risk: low -- add `mimalloc = "..."` and a `#[global_allocator]` static to the two `main.rs` files, `cargo bench` before/after against the existing `corpus/bind_npsp_full` and `warm_rebind_after_one_file_edit` benchmarks (the map's own established re-baselining practice) to confirm a real win on this workload rather than assuming one.

**4. Shrink apexls-server's ~180-200MB steady-state footprint by removing the `BindCache`/`BoundProgram` double-storage `mem_profile.rs`'s own doc comment already names as the reason that harness exists.**
Why it matters: this isn't a hypothesized problem -- `crates/apex-binder/examples/mem_profile.rs:1-10`'s doc comment states outright that the harness exists to attribute apexls-server's own measured ~180-200MB resident size to "a `BindCache` *and* a separately-owned `BoundProgram` snapshot alive at once." `BindCache` retains per-file `Parse` trees and other intermediate caches (confirmed present per the diagnostics map's ticket 29: "kept `BindCache::file_parses` despite this ticket's own text calling for its deletion"); `BoundProgram` is the separately-materialized merged output `apexls-server::BindState` also keeps alive for the process's whole lifetime (`program: RwLock<Option<BoundProgram>>`). Running `cargo run -p apex-binder --release --example mem_profile` (already a working harness, no new code needed) and inspecting the resulting `dhat-heap.json` at https://nnethercote.github.io/dh_view/dh_view.html would turn "known to be duplicated, un-quantified" into a concrete per-allocation-site number, which is the natural first step before deciding whether to Arc-share overlapping data between the two rather than materializing it twice.
Source: apexls's own doc comment, a primary first-party source.
Cost/risk: measurement step is free (the harness already exists and just needs running); the actual fix (restructuring `BindCache`/`BoundProgram` to share rather than duplicate retained data) is a real, non-trivial `apex-binder`-core change whose size depends entirely on what the `dhat-heap.json` breakdown shows -- don't scope the fix before running the harness.

**5. Regain lost Pass 2 (Resolve) `rayon` parallelism inside a salsa-tracked Stage 4 using `BindDatabase: Clone` + per-task cloning (Stage 2's own already-solved pattern), rather than falling back to sequential resolution the way Stage 1 did.**
Why it matters: Stage 1's own implementation ticket (26) found that salsa 0.28's thread-local "attached database" model conflicts with handing tracked-fn calls to `rayon`'s shared global thread pool, and worked around it by reading Stage 1's four queries *sequentially* -- accepted there because a same-machine `cargo bench` comparison showed no statistically significant regression for that specific, small workload. Stage 2's own design ticket (27) found the real fix instead of that workaround: "restore `Clone` on `BindDatabase` and clone it once per `rayon` task... with one load-bearing gotcha: per-file inputs must all be set sequentially on one db handle before any parallel read phase, never mutated inside it," which ticket 29 then implemented and confirmed (`BindDatabase`'s `Clone` restored, every parallel task gets its own pre-cloned handle). Pass 2/Resolve is by far the largest, most parallelism-sensitive stage (3,767-line `resolve.rs`, walking every method/constructor/property-accessor body project-wide) -- unlike Stage 1's small indices, sequentializing this stage the way Stage 1 did would very likely show a real, measurable regression on the ~588ms cold-bind number, not the "no significant difference" Stage 1 got away with. This means Stage 4's own design should default to Stage 2's clone-per-task pattern from the start rather than re-deriving it, and should explicitly `cargo bench` a would-be sequential fallback against the clone-per-task version before ever accepting the sequential path the way Stage 1 did.
Source: this codebase's own diagnostics map, tickets 26/27/29 (already-resolved, first-party, direct citations above) -- primary source is this project's own resolved design history, not an external one.
Cost/risk: this is Stage 4 territory entirely, not an independent action item -- listed here specifically as a risk to flag *into* that not-yet-written design ticket (a concrete regression this project's own precedent shows is plausible if the ticket defaults to "just sequentialize it, measure later" rather than "default to the already-proven clone-per-task shape").

**6. Rowan's own `NodeCache` interning: confirm whether Pass 2/Resolve or the LSP-layer `line_index.rs`/hover/completion paths ever re-parse or re-walk a `SyntaxNode` where a `SyntaxPtr` resolve would do, now that Stage 2's own prototype (ticket 28) already validated thread-local `NodeCache` reuse as a 7-33% win on cold full-corpus parse.**
Why it matters: rowan's own docs describe `NodeCache` as an "Interner for GreenTokens and GreenNodes" (https://docs.rs/rowan/latest/rowan/) -- deduplicating identical syntax subtrees (a real, common shape in Apex code: repeated boilerplate like `public void` method signatures, common annotation combinations) both within a file and, when the same `NodeCache` is reused, *across* files. Ticket 28 already measured this win for cold full-corpus parsing specifically; whether apexls-server's own request-handling paths (hover, completion, goto-definition, rename -- `crates/apexls-server/src/capabilities.rs`, 139KB, the single largest file in the LSP crate) ever construct a fresh `NodeCache` per lookup rather than reusing one is unverified by this research pass and worth a direct code check before treating it as settled.
Source: rowan's own docs (primary) for what `NodeCache` does; this codebase's own ticket 28 (primary, first-party) for the specific reuse pattern and measured win already banked for parsing -- the *request-handling*-path question above is this research's own open question, not yet answered by either source, flagged honestly as such rather than asserted.
Cost/risk: low to check (a direct grep/read of `capabilities.rs`'s request handlers for `NodeCache::new()`/`parse` calls), unknown cost to fix until that check is done.

**7. LSP-layer: move off full-document sync (`TextDocumentSyncKind::FULL`, `crates/apexls-server/src/lib.rs:648`) to incremental sync once a real justification exists, but not preemptively.**
Why it matters: apexls's own module doc comment (`crates/apexls-server/src/lib.rs:13-18`) already states this was a **deliberate, tracked choice**, not an oversight, and points to `Backend::initialize`'s own doc comment for the rationale (not re-read in full during this pass -- worth reviewing before treating this as an open opportunity at all). Full-document sync means every keystroke sends the entire buffer over stdio and apexls re-derives the whole file's text client-side; on very large real Apex files this is a real, if probably secondary, cost relative to the ~588ms full-corpus bind number, and the LSP spec itself documents `TextDocumentSyncKind.Incremental` as the alternative (`lsp-types` crate, already a direct dependency at `crates/apexls-server/Cargo.toml`, models both variants). Given the existing doc comment explicitly frames this as already-decided, this is listed for completeness and lowest priority, not as a recommendation to reopen it without first reading why it was decided.
Source: apexls's own doc comment (primary, first-party) establishing this is a known, considered tradeoff already, not a gap.
Cost/risk: unknown until `Backend::initialize`'s own doc comment (not read in this pass) is reviewed for the original rationale -- do that before scoping any work here.

### Overlap with the diagnostics map's Stage 4 (not yet designed)

Opportunities **2** and **5** are not independent action items -- they are concrete requirements/risks that should be folded directly into Stage 4 (Pass 2/Resolve)'s own design ticket once someone sits down to write it, per the diagnostics map's own "Not yet specified" section. Opportunity **6**'s LSP-request-handling half may also intersect Stage 4 if Pass 2's migration changes how/when syntax trees get re-resolved during a hover/completion request.
