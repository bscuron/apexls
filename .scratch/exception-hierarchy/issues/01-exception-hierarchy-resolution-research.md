## Question

`apexls`'s `classify_unresolved` (`crates/apexls-server/src/capabilities.rs:1554-1620`) flags `catch (Exception e)` at `fflib_QueryFactoryTest.cls:729` as a likely false positive, attributing it to the `SyntaxKind::QualifiedName` arm's documented gap: "catch-clause/switch-value/upsert-field type lookups resolve only against project-local types, with no standard-library or schema fallback." Given that Salesforce's own docs describe a real `Exception` hierarchy, and this crate's own bundled `apex_reference.json` already has a hand-corrected `Exception` entry, what's the smallest viable fix, and do catch-clause/switch-value/upsert-field genuinely share one root cause?

## Answer

### 1. Salesforce's own Exception hierarchy (primary source)

The canonical page is Salesforce's Apex Reference Guide, "Exception Class and Built-In Exceptions" (`apex_classes_exception_methods`). `WebFetch` against `developer.salesforce.com` returns HTTP 403 for every variant of the URL tried (the rendered page, and the `get_document` content-API endpoint the site's own SPA uses) — this is a known, already-documented condition in this repo: `tools/salesforce-doc-scraper/src/http.rs:6-26` confirms Salesforce's Akamai front end 403s any request whose `User-Agent` doesn't start with a handful of allow-listed client names (`curl`, `wget`, `python-requests`, ...), which `WebFetch`'s own UA doesn't satisfy and which `WebFetch` provides no way to override. However, this repo's scraper already fetched and cached the exact page previously, at `tools/salesforce-doc-scraper/.cache/https___developer_salesforce_com_docs_get_document_content_apexref_apex_classes_exception_methods_htm_en_us_262_0.cache` — read directly, this is the real, unmodified primary-source JSON+HTML response (`id: "apex_classes_exception_methods"`, `title: "Exception Class and Built-In Exceptions"`), not a re-derivation.

That page lists **38 built-in `System`-namespace exception subtypes** in one flat table (no per-type reference pages exist — confirmed, matching `apex_stdlib`'s own doc comment): `AssertException`, `AuraException`, `AuraHandledException`, `AsyncException`, `BigObjectException`, `CalloutException`, `DataWeaveScriptException`, `DmlException`, `DuplicateMessageException`, `EmailException`, `ExternalObjectException`, `FatalCursorException`, `FinalException`, `FlowException`, `HandledException`, `IllegalArgumentException`, `InvalidHeaderException`, `InvalidParameterValueException`, `LimitException`, `JSONException`, `ListException`, `MathException`, `NoAccessException`, `NoDataFoundException`, `NoSuchElementException`, `NullPointerException`, `QueryException`, `RequiredFeatureMissing`, `SearchException`, `SecurityException`, `SerializationException`, `SObjectException`, `StringException`, `TransientCursorException`, `TypeException`, `UnexpectedException`, `VisualforceException`, `XmlException` (plus further per-namespace exception lists linked out for `Cache`/`Canvas`/`Compression`/`ConnectApi`/`DataSource`/`Reports`/`Site`, not covered here).

The page's "Common Exception Method" table lists exactly 7 instance methods common to **every** exception: `getCause() -> Exception`, `getLineNumber() -> Integer`, `getMessage() -> String`, `getStackTraceString() -> String`, `getTypeName() -> String`, `initCause(Exception cause) -> Void`, `setMessage(String s) -> Void`. `DmlException`/`EmailException` additionally get `getDmlFieldNames`, `getDmlFields`, `getDmlId`, `getDmlIndex`, `getDmlMessage`, `getDmlStatusCode` (deprecated), `getDmlType`, `getNumDml`; `QueryException` additionally gets `getInaccessibleFields`.

**On whether Salesforce's docs describe this as a real inheritance hierarchy**: not in `extends`/`subclass` language anywhere on this page — it only ever says "there are several different types of exceptions" and lists them as a flat table. The closest it comes is `getTypeName`'s own description ("Returns the type of exception, such as DmlException, ListException, MathException, and so on") and the worked example catching `System.DmlException` and calling the common `getMessage`-family methods on it. The *behavioral* hierarchy (every subtype is a real `Exception` and inherits these 7 methods) is demonstrated by example and cross-reference, not asserted in prose — consistent with `apex_reference.json`'s own doc comment (`crates/apex-stdlib/src/lib.rs:216-221`), which independently confirms the inheritance relationship empirically against a live connected org rather than from docs prose.

### 2. What data actually exists in this crate

`crates/apex-stdlib/data/apex_reference.json` has **exactly one** entry under the `Exception`/`DmlException`/... family: `System.Exception` itself (`kind: "Class"`, hand-corrected per `standard_classes`'s own doc comment, `crates/apex-stdlib/src/lib.rs:204-228`), with all 4 real constructors and all 7 common methods listed above (confirmed by direct read of lines 85768-85916 of the JSON; the DML/Email/Query-specific extra methods are *not* present, since those were never hand-added for a specific subtype). A `grep` for `"name": "DmlException"` / `"QueryException"` / `"NullPointerException"` across the whole file returns zero matches — **no scraped or hand-corrected data exists for any exception subtype**, only for bare `Exception`. This matches the classify_unresolved comment's premise exactly: the 38 subtypes above will never be individually confirmable by this crate without new scraper work (there is no per-subtype page to scrape), but bare `Exception` already has full, correct data.

### 3. Where stdlib resolution succeeds vs. fails today — and a correction to `classify_unresolved`'s own framing

`StdlibIndex::class(name)` (`crates/apex-binder/src/stdlib_index.rs:40-47`) and `class_in_namespace(ns, name)` (`:59-65`) are the two stdlib lookup entry points; `Exception` resolves through `class("Exception")` cleanly (single entry, namespaced `System`, real methods — no collision to break). Three call sites *do* already consult one of these as a fallback when `SymbolTable::resolve_dotted_name`/`resolve_dotted_name_from` fails:

- `resolve::type_of_symbol` (`resolve.rs:1568-1675`) — a symbol's *declared type* (e.g. `String s;`, a field, a catch variable's own declared type once `declare_local_with_type_name` stores its `type_name`) falls back to `stdlib.class_in_namespace` (namespaced) then implicitly to `Ty::system_owned` for a bare unmodeled name.
- `resolve::resolve_type_ref_base` (`resolve.rs:1064-1221`) — any `Type` AST node (parameter/return/field/local-variable-declaration type, generic type argument, **and the `when Account a` type-pattern form of a switch/`when` clause**) tries, in order: nested-type-visible-from-enclosing, project top-level, `stdlib.class_in_namespace` (2-segment dotted), `schema.object`, then **`stdlib.class(&name)` bare** (line 1195) before finally giving up as `Resolution::Unresolved` (line 1219). This bare fallback is exactly what would resolve `Exception` if a catch-clause routed through it — but it doesn't (next point).

The actual catch-clause exception-type reference (`resolve.rs:2048-2090`) does **not** go through either of the above. It's parsed as a `QualifiedName` (per the real Apex grammar: `catch (Type e)`'s `Type` production is a bare `qualifiedName`, not a full `typeRef` — confirmed in `crates/apex-syntax/src/ast/stmt.rs:243` and the parser at `crates/apex-parser/src/grammar/statements.rs`), and is resolved with exactly one call: `self.table.resolve_dotted_name(&name)` (`resolve.rs:2085`) — project-local only, with a comment explicitly noting "this reference alone deliberately stays project-only." **This is the one and only call site that actually produces `SyntaxKind::QualifiedName` at the node level with no stdlib fallback attempted**, and it's exactly what fired for `fflib_QueryFactoryTest.cls:729`.

**Correction to the classify_unresolved doc comment and to `resolution_at`'s own exhaustiveness doc**: the switch-value and upsert-field parts of that comment's framing do not match the current code:

- **Switch/`when`-value, type-pattern form** (`when Account a`, `WhenValue::type_ref()` returning a full `Type`, `crates/apex-syntax/src/ast/stmt.rs:120-122`) is bound via `self.resolve_type_ref(&ty)` in `Stmt::Switch`'s handler (`resolve.rs:1938-1940`) — i.e. it already gets the full schema+stdlib fallback chain described above. `when Exception e` would resolve today with **no fix needed**.
- **Switch/`when`-value, literal-list form** (`when ACTIVE, PENDING:`, an enum switch) parses each identifier-shaped literal through `qualified_name(p)` (`crates/apex-parser/src/grammar/statements.rs:158-160`), producing a real nested `QualifiedName` node inside `WhenLiteral`. But `Stmt::Switch`'s binder (`resolve.rs:1931-1957`) never calls `when.value().literals()` at all — a `grep` for `.literals()` across `crates/apex-binder/src/` returns zero call sites. These `QualifiedName` nodes are never visited by Pass 2 at all, so no `Resolution` (resolved *or* unresolved) is ever recorded for them.
- **Upsert external-id field** (`external_id_field()`, `crates/apex-syntax/src/ast/stmt.rs:318`, also a `QualifiedName`) is explicitly *not* consulted by `Stmt::Upsert`'s handler (`resolve.rs:2188-2196`), which has its own comment: "The external-ID field reference isn't resolved against schema in v1 -- it needs the DML target expression's type ... known first, which is exactly the inference v1 doesn't attempt." Also never gets a `Resolution` recorded.

`BoundProgram::resolution_at`'s own doc comment (`crates/apex-binder/src/lib.rs:1058-1061`) independently confirms this: "exactly ... `QualifiedName` (**a catch clause's exception type**) ... ever get registered at the node level" — it names only the catch-clause use, not switch-value or upsert-field, which is the more authoritative and (per this investigation) more accurate statement than `classify_unresolved`'s own three-way bundling.

**Net implication for the scope-check (task item 4): these three shapes do not share one root cause today.** Only catch-clause ever reaches `classify_unresolved`'s `QualifiedName` arm at all — switch-value's type-pattern form already resolves correctly (no gap), and both switch-value's literal form and upsert-field are simply never bound to any `Resolution`, so they can never produce this diagnostic in the first place (that's a separate, pre-existing gap in reference/hover/goto-def coverage for those two shapes, not a false-positive-diagnostic problem, and out of scope for this fix). `classify_unresolved`'s doc comment and match-arm message should be corrected to describe only the catch-clause shape once the catch-clause fix below lands (or earlier, as a documentation-only cleanup, since the bundling is inaccurate regardless).

### 4. Prior art: does the `stdlib-interfaces` mechanism transfer?

`.scratch/stdlib-interfaces/` (map + ticket 01, ADR 0001) designed and (per `c3596b9`/`fa94084`) already partially implemented a general mechanism for teaching `apex-binder` about stdlib *interface implementation*: a restored `StdlibKind { Class, Interface, Enum }` enum on `StdlibClass` (confirmed already live at `crates/apex-stdlib/src/lib.rs:106-111`, threaded from `RawClass::kind` in `to_stdlib_class`), plus a parallel `stdlib_implements: FxHashMap<SymbolId, Vec<&'static StdlibClass>>` index populated during `resolve_inheritance` (per the ADR, chosen over minting synthetic `SymbolId`s, following the precedent `Resolution::StdlibMember`/`ExternalKey::Stdlib` already set).

That mechanism is a good conceptual match for **whether a name is a stdlib type at all**, and `StdlibKind` is already general enough to distinguish "Class" (what `Exception` needs) from "Interface"/"Enum" — but it solves a different problem than catch-clause resolution needs. `stdlib_implements` answers "does project type X implement/extend stdlib interface Y" (an `inherited_chain`-shaped question, keyed by a project-local `SymbolId` that already exists); the catch-clause gap is "is this *raw type-name string* (which may have no project `SymbolId` at all, e.g. `Exception` itself) a real stdlib class" — exactly the question `StdlibIndex::class(name)` already answers directly, with no `SymbolId`/`inherited_chain` involvement needed. **The `stdlib-interfaces` machinery itself doesn't need to be reused or extended for this fix — its sibling primitive, `StdlibIndex::class`, called the same way `resolve_type_ref_base` already calls it, is sufficient.** The one thing worth reusing from that design is the *pattern*: representing "resolved, but to something with no `SymbolId`" via `Resolution::StdlibMember(Box<StdlibMemberRef>)` (`reference_table.rs:100-106,137-145`) rather than inventing a new resolution kind — this is the same idiom `resolve_type_ref_base` already uses for its own bare-stdlib-class fallback (`resolve.rs:1195-1207`, via `stdlib_member_ref(namespace, name, None, None, None)`).

### Recommendation

**Smallest viable fix**: at the one real call site, `resolve.rs:2085` (`Stmt::Try`'s catch-clause handling), add a stdlib fallback consulted only after `self.table.resolve_dotted_name(&name)` fails — mirroring `resolve_type_ref_base`'s own existing bare-class fallback (`resolve.rs:1195-1207`) rather than inventing new machinery:

```rust
match self.table.resolve_dotted_name(&name) {
    Some(id) => self.refs.set(ptr, Resolution::Resolved(id)),
    None => match self.stdlib.class(&name) {
        Some(class) => self.refs.set(ptr, Resolution::StdlibMember(Box::new(
            stdlib_member_ref(class.namespace.clone(), &class.name, None, None, None),
        ))),
        None => self.refs.set(ptr, Resolution::Unresolved),
    },
}
```

(`self.stdlib: &StdlibIndex` is already a `BodyBinder` field, `resolve.rs:821` — no new plumbing needed.) This resolves bare `catch (Exception e)` exactly like the reported `fflib_QueryFactoryTest.cls:729` case, using data this crate already has, with no scraper changes. It does **not** resolve `catch (DmlException e)` or any other individual subtype, since `StdlibIndex::class("DmlException")` still returns `None` — there is no scraped/hand-corrected data for any subtype, and (per section 1) Salesforce's own docs have no per-subtype reference page to scrape one from. That remaining gap stays exactly what `classify_unresolved`'s existing `SyntaxKind::Type if name.ends_with("Exception")` arm already covers correctly for the *declared-variable-type* shape (`System.DmlException caughtEx;`) — worth adding an equivalent `name.ends_with("Exception")` classification for `SyntaxKind::QualifiedName` too, once the `Exception`-specific case above no longer needs it, so a still-unresolvable `catch (DmlException e)` keeps its "likely a real Apex type, not a typo" signal instead of falling to the generic (lower-confidence) QualifiedName message.

Also recommended as a small follow-up cleanup, not a fix in itself: correct `classify_unresolved`'s doc comment (`capabilities.rs:1524-1537`) and its `QualifiedName` arm's message text (`:1556-1559`) to stop naming "switch-value"/"upsert-field" as sharing this gap, since (per section 3) neither ever reaches this code path today — the switch-value type-pattern form has no gap, and switch-value-literal/upsert-field are unbound entirely, a separate and larger pre-existing limitation (no `Resolution` at all, so no hover/goto-def/find-references either) that would need its own investigation and fix, not a stdlib-fallback tweak.
