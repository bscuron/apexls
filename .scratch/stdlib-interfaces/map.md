# Model Builtin Salesforce Apex Interfaces

## Destination

Model Salesforce's builtin/stdlib Apex interfaces (`Database.Batchable`, `Schedulable`, `Queueable`, `Comparable`, `StubProvider`, etc. -- the full catalog already scraped into `crates/apex-stdlib/data/apex_reference.json`, 68 interfaces) as real, general data in `apex-binder`'s core, general enough to cover any stdlib interface rather than a hardcoded async-job list. The concrete payoff: `crates/apex-binder/src/dead_code.rs` and `crates/apex-binder/src/visibility_narrowing.rs` both currently false-positive on a method that only satisfies a *stdlib* interface's contract (e.g. `execute()`/`start()`/`finish()` on a class implementing `Database.Batchable`), because both diagnostics' interface-satisfaction exemption walks `inherited_chain`, which `SymbolTable`/`resolve_inheritance` never populates for a stdlib `implements` target. This map is a spec/decision only -- tickets settle architecture questions; implementation happens after, not as part of resolving a ticket.

**Scope boundary**: the new stdlib-interface mechanism is designed generally (available to any future consumer), but this destination only wires it into `dead_code.rs` and `visibility_narrowing.rs`. Other real consumers of `inherited_chain` (`conversions.rs` type-compatibility, `resolve.rs` call/override resolution, call-hierarchy in `capabilities.rs`) have the identical blind spot but are deliberately not fixed here -- see Not yet specified.

## Notes

- Domain: apexls Rust workspace -- `apex-binder` (dead-code/visibility-narrowing diagnostics, symbol table, inheritance resolution), `apex-stdlib` (scraped Salesforce doc data, `StdlibClass`/`StdlibMethod`), `tools/salesforce-doc-scraper` (standalone offline tool that produces `apex-stdlib`'s checked-in JSON directly from Salesforce's own doc API).
- Per wayfinder default, consult the grilling and domain-modeling skills for the decision ticket; dispatch research subagents for codebase facts instead of asking the user anything checkable in the repo.
- **This repo already ran directly-adjacent prior art**: a now-deleted `.scratch/apex-diagnostics/` Wayfinder map (full history survives in git, directory removed from the working tree after that map's destination was reached) hit this same wall while designing `missing_implementation_diagnostics` (the "does this class implement every required interface method" diagnostic). Its ticket 18 (research, commit `f676def`) did a deep investigation of what teaching `apex-binder` about stdlib interfaces would require; ticket 20 (decision, commit `c2ec628`) then deferred extending that diagnostic to stdlib interfaces. Every finding below was reconfirmed against current HEAD this session (still accurate -- nothing from ticket 18 has since been built):
  - `inherit.rs`'s `filter_map` in `resolve_inheritance` silently discards every `implements`/non-direct-`extends` name that fails to resolve as project-local; only a single-slot `unresolved_direct_super` (direct `extends` only, `symbol_table.rs:135,384-396`) exists today. Minimal fix sketched: a `partition` instead, plus a new `set_unresolved_supertypes` mirroring the existing setter.
  - `raw_extends` (`collect.rs`) conflates `extends`/`implements` origin positionally -- no per-name clause tag recorded at collection time.
  - `StdlibIndex::class(name)` needs the bare trailing segment split off a dotted name (`Database.Batchable` -> `Batchable`) plus `class_in_namespace(namespace, tail)` for the qualified case; both accessors already exist on `StdlibIndex`, just unused for this purpose.
  - `StdlibClass` (`apex-stdlib/src/lib.rs:87-96`) drops `RawClass`'s raw `kind: String` (`"Class"`/`"Interface"`/`"Enum"`) entirely -- no public way today to ask "is X a stdlib interface."
  - `Messaging.InboundEmailHandler`, `Database.Stateful`, `Database.AllowsCallouts` are entirely unscraped in `apex_reference.json` (confirmed: not filtered, never scraped at all) -- real, commonly-implemented marker/callback interfaces (20 + 5 + 1 real NPSP implementers) with zero data today. `tools/salesforce-doc-scraper` is the known fix path (canonical-source, self-contained, designed to be manually re-run) -- not run as part of this map.
  - Real NPSP frequency: 121/324 classes with any `implements` clause name a real stdlib interface (202 sites); top implementers `StubProvider` (76), `Database.Batchable` (38), `Schedulable` (27), `Database.Stateful` (20), `Queueable` (14), plus 15 others with 1-5 implementers each.
  - A real name+arity collision exists across `Schedulable.execute(SchedulableContext)`/`Queueable.execute(QueueableContext)`/`Finalizer.execute(FinalizerContext)` -- matters for *attributing* which interface a method satisfies (needed by the missing-implementation diagnostic), likely does not matter for this map's exemption use case (checking membership against the specific interfaces a class's own `implements` clause names never needs cross-interface attribution).
- **`SymbolId` constraint** (found this session, not in ticket 18): `SymbolId { file: FileId, local: u32 }` -- real project symbols only, and code elsewhere assumes `symbol.file()` resolves to actual project syntax/text. Minting synthetic `SymbolId`s for stdlib interfaces to unify them into `inherited_chain` directly would fight that invariant.
- **Existing precedent for the parallel-structure approach** (found this session): `reference_table.rs`'s `Resolution` enum already keeps `Resolved(SymbolId)` (project-local) separate from `StdlibMember(Box<StdlibMemberRef>)` (stdlib, no `SymbolId`) via a parallel `ExternalKey` identity scheme -- the established idiom for "something real with no `SymbolId` to key by," not a novel design.
- `visibility_narrowing.rs`'s `overrides_or_implements` (confirmed this session, not in ticket 18) walks the identical `inherited_chain` and has the identical stdlib blind spot -- a second, independent consumer the design ticket must serve.

## Decisions so far

- [Design decision: stdlib-interface data model](issues/01-stdlib-interface-data-model-decision.md): fold the `StdlibIndex` cross-reference directly into `resolve_inheritance`'s existing pass, producing one new transitively-propagated `stdlib_implements: FxHashMap<SymbolId, Vec<&'static StdlibClass>>` index (keyed by the project type's own real `SymbolId`, no synthetic ids -- see [ADR 0001](../../docs/adr/0001-stdlib-interface-implementation-as-parallel-index.md)) plus a restored `StdlibKind` enum on `StdlibClass`; one new `SymbolTable::implements_stdlib_interface_method` query consumed as a genuine extension of `visibility_narrowing.rs`'s existing structural `overrides_or_implements` check, but as a brand-new "unprovable invocation channel" exemption in `dead_code.rs` (which had no structural interface-satisfaction check at all before this).

## Not yet specified

- Whether/how to also fix `conversions.rs` (type-compatibility/assignability, e.g. deciding if a class implementing `Comparable` is assignable where `Comparable` is expected), `resolve.rs` (call/override resolution), and `capabilities.rs`'s call-hierarchy navigation -- all real consumers of `inherited_chain` with the same stdlib blind spot, deliberately not fixed by this map. Revisit as a follow-on once the core mechanism this map designs exists, since extending it to these consumers should be far cheaper once it's real.
- Whether `tools/salesforce-doc-scraper`'s TOC crawl is missing `Messaging.InboundEmailHandler`/`Database.Stateful`/`Database.AllowsCallouts` because of a genuine crawl gap versus these pages not existing in Salesforce's doc site the same way -- not investigated; whoever implements should check before assuming a scraper bug.

## Out of scope

- Extending `missing_implementation_diagnostics` (flagging a class for NOT implementing a required stdlib interface method) to stdlib interfaces: already deferred once, in the prior `apex-diagnostics` map's ticket 20 (commit `c2ec628`), specifically because that diagnostic's failure mode is structurally unvalidatable against any real corpus (the Apex compiler already rejects incomplete implementations before code ships). That reasoning is untouched by this map's false-positive-suppression goal, so it stays out of scope even though this map's foundation work would make it easier later.
