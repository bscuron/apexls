# Model stdlib interface implementation as a parallel index, not synthetic SymbolIds

`apex-binder`'s `SymbolTable::inherited_chain` only ever holds real `SymbolId`s, and `SymbolId { file: FileId, local: u32 }` is relied on elsewhere to always resolve to real project syntax/text (`symbol.file()` is assumed dereferenceable). Salesforce's standard-library interfaces (`Database.Batchable`, `Schedulable`, ...) have no project file and thus no real `SymbolId` to mint. Rather than inventing a synthetic `SymbolId` for each stdlib interface so it could be folded directly into `inherited_chain`, we instead record "this project type implements these stdlib interfaces" in a separate index (`stdlib_implements: FxHashMap<SymbolId, Vec<&'static StdlibClass>>`, keyed by the project type's own real `SymbolId`), queried explicitly by consumers that need it. This follows the precedent `reference_table.rs`'s `Resolution::StdlibMember`/`ExternalKey::Stdlib` already set for "something real with no `SymbolId` to key by," and keeps `inherited_chain`'s existing "every entry is a real project symbol" invariant intact for every other consumer that already relies on it.
